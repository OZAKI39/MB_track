# 长停顿的进一步追查：Windows 与 WSL 同时记录

本轮比上一轮多拿到了 Windows 页文件读取记录，以及 WSL 磁盘请求从发出到完成的
记录。**已经查到可复现停顿的具体链路，但原先 1.76 秒和 157 ms 两个历史事件
仍没有重新出现，不能将它们写成已经逐事件查明。**

## 1. 图像转换：本轮主要慢点是准备内存时碰上宿主机回页

在 B 视频的重复回放中抓到了两次异常。这里的帧号是连续回放帧号，原视频帧号
及轮次保存在各运行目录的 `source_timing.csv`，不是重新采集的实验录像。

| 回放帧号 | 转换耗时 | Linux 线程 CPU 时间 | Linux 采样位置 | 对应 Windows 记录 |
| --- | ---: | ---: | --- | --- |
| 572 | 50.048 ms | 50.056 ms | 10 个区间内 CPU 样本均在清零新内存页 | 一个 WSL 宿主线程约 136 次回读页文件，累计约 39.9 ms |
| 3363 | 31.368 ms | 31.173 ms | 区间内样本同样主要在清零新内存页 | 主要宿主线程约 103 次回读，累计约 23.4 ms；另一个线程也有读取 |

用普通话解释：程序要把画面转换成新图像，于是首次访问一些内存页；Linux 要先
准备、清零这些页，而 Windows 此时又在从 `C:\pagefile.sys` 取回 WSL 的内存。
这条内存处理链路拖慢了转换，不能把整段耗时都解释成颜色计算本身很复杂。

证据链如下：

1. 第 572 帧在 Linux 中没有主动等待或被切走记录，出现 321 次软缺页；采到的
   10 个 CPU 样本均为 `libswscale → do_anonymous_page → 分配内存页 → clear_page_erms`。
   [原生调用栈](B_conversion_50ms_native.txt) 中多出来的区间外尾部样本不计入这 10 个。
2. Windows 在对应时段直接记录了 `vmmemWSL` 从 `pagefile.sys` 读取，集中在
   TID 22268 上；将对应窗口前后各扩大 15 ms，该线程的记录仍为 136 次。
3. 第二个慢点也出现了同类组合。其两个宿主线程的读取可能重叠，不能把二者累计
   用时简单相加后全部算给一个 Linux 线程。
4. 整次 Windows 跟踪中，`vmmemWSL` 共记录 16969 次硬缺页、读取约 971 MB。
   这是整个 WSL 宿主进程的记录，不能全部归到本项目的一张图像上。

这一结果**直接确认了宿主机为 WSL 回读页文件的现象，并对本轮转换慢点给出了很强的
对应证据**。没有采集虚拟机物理页与 Windows 地址的逐页映射，不能声称已经逐字节
证明每一次 Windows 读页都属于该图像，也不能把累计回页时间当作精确分解后的算法时间。

### 对之前判断的补充

Linux 中“线程 CPU 时间接近总耗时”“没有 Linux 磁盘缺页”，不足以排除 Windows
在虚拟机外部引入的等待。本轮就是实际例子：Linux 记录 `major_faults=0`，同时
Windows 明确记录了 WSL 的页文件读取。以前只依赖 Linux CPU 计时进行分类不够完整。

**原先 157 ms 的具体事件仍缺少当时的 Windows/原生调用栈记录。** 它与当前内存
准备、宿主机回页机制相容，但不能把本次 50 ms 或 31 ms 当作同一次 157 ms 的复现。

## 2. 数据库：本轮长等待明确发生在磁盘刷新请求发出以后

额外进行了约 264 秒的 A 视频重复回放，抓到一次 **102.875 ms** 提交。
保存线程自身 CPU 时间只有 **0.168 ms**。关键步骤有完整的 WSL 块设备事件：

| 步骤 | WSL 共同计时器（秒） | 说明 |
| --- | ---: | --- |
| 开始提交 | 205926.272719528 | 保存线程已进入数据库提交阶段 |
| 数据写入请求发出 | 205926.272793868 | 40 KiB 写入 |
| 数据写入请求完成 | 205926.272900511 | 写入本身约 0.107 ms |
| 刷新缓存请求发出 | 205926.272936961 | 要求底层确认刷新完成 |
| 刷新缓存请求完成 | 205926.375492977 | 该请求耗时 **102.556 ms** |
| 文件系统同步返回 | 205926.375548454 | 完成后约 0.055 ms 即返回 |
| 提交计时结束 | 205926.375594958 | 没有额外的长调度延迟 |

等待链路为：`SQLite 提交 → fdatasync → ext4_sync_file → blkdev_issue_flush →
submit_bio_wait`。区间内连续 10 个内核等待样本都落在刷新等待上。
送帧和分析线程在这段时间内仍继续推进，保存线程的 Linux 调度等待计数没有增长。

因此，对于这一次 103 ms，可以明确说：**保存线程在等已经发出的虚拟磁盘刷新请求
完成；不是等待提交队列，也不是 Python 一直占着锁，更不是整个程序被停了 103 ms。**

证据：[块设备事件](long_commit_103ms_system.txt)、
[等待栈和调度计数](long_commit_103ms_waits.json)、
[保存线程原生记录](long_commit_103ms_native.txt)。

### 同时发现的外部读盘干扰

这次刷新等待期间，同一虚拟磁盘还处理了 **307 次、合计约 1.20 MiB 的读请求**。
请求线程为 PID 385861，当前进程信息和此前检查均对应 VS Code 的 Pylance
（Python 后台分析程序）。原始进程信息和逐条读请求已保存在
[background_io_evidence.json](background_io_evidence.json)。

这证明存在后台读盘竞争，值得在后续对照时排除；**仅有并发记录还不能证明
Pylance 是刷新变慢的唯一原因**。本轮没有暂停、关闭或修改用户的 VS Code/Pylance。
较长回放期间也进行了前轮日志整理，所以它是故障定位记录，不是隔离所有后台负载
后的正式速度验收。

### Windows 跟踪提供了什么，以及没有提供什么

前面的 180 秒 Windows 跟踪覆盖 A、B 各约 66 秒的运行。其间 F 盘记录 9516 次
刷新，最慢 13.699 ms；没有秒级刷新。另观察到一次 `F:\WSL\Ubuntu\ext4.vhdx`
读取耗时约 297 ms，但发生在这两组回放结束后，不能归到某次数据库提交。

103 ms 是在后来仅保留 WSL 跟踪的较长回放中出现的；Windows 跟踪已按授权限时
结束。因此，本轮还不能把这 102.556 ms 再分成 Windows 存储驱动、虚拟磁盘与
物理 SSD 各自耗时。更不能据此宣布 SSD 损坏。

**原先 1.76 秒为何延长到那个程度，仍未完全查明。** 原始记录只确定提交阶段以等待
为主，没有当时的磁盘请求和 Windows 系统记录；本轮最长为 102.875 ms，不能用
较短事件代替历史 1.76 秒事件。现在已有具体候选链路与背景竞争证据，但尚缺原事件
或秒级同类事件的两侧完整现场。

## 3. 两侧时间是怎么对应的

没有直接相减 Windows 和 WSL 的程序计时值。由 WSL 发请求，Windows 在回复中
返回 QPC 计数；WSL 保存发出和收到回复的时间。共保留 120 组记录，首次 PowerShell
启动样本排除后，往返用时中位数为 0.853 ms、最大 1.743 ms。

Windows 跟踪头的 QPC 起点为 2190168972202，频率为 10000000 Hz。每次慢点由
相邻两组请求/回复作时间插值，并保留不依赖插值的前后采样包围区间。
不能把小往返时间直接当成全程同步误差：全段抽掉一个采样点再预测的误差最大约
13.93 ms；两次转换附近该误差分别小于约 0.6 ms 和 0.2 ms。

表内 136/103 次是插值窗口内的对应统计，不是物理同步的精确分解。报告同时保存
了窗口前后扩展 15 ms 的敏感性检查；15 ms 是检查范围，不是经过证明的同步误差上限。
详情：[clock_bridge.csv](clock_bridge.csv)、
[cross_layer_summary.json](cross_layer_summary.json)、
[analyze_cross_layer.py](analyze_cross_layer.py)。

- 共送入 23760 帧，分析并提交保存的 23741 帧全部写入，三个数据库的快速完整性

- 相关 **75 项测试通过**。Windows 配置解析、PowerShell 语法检查及一次实际采集

- 新增 Windows 限时诊断脚本和配置，并补充诊断说明；识别、追踪、数据保存规则与
  数据库安全设置保持原样。没有操作相机、AFG/PZT，没有改驱动或服务，没有推送 Git。

## 5. 后续应针对什么处理

目前已确认的转换慢点应优先从减少新内存申请、复用转换缓冲区及宿主机内存条件
入手。当前没有实施这些优化，也没有声称它们已消除 157 ms 异常。

数据库方面，不应把扩大队列或关闭安全写入当成查清原因。可将编辑器后台读盘隔离
作为下一组有针对性的对照；要最终解释秒级事件，仍需要它出现时同时保留 Windows
和 WSL 的记录。历史事件没有采集的底层现场，事后无法从现有日志恢复。

采集配置及解释参考 Microsoft 官方文档：
[WPR 系统诊断记录](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/recording-for-basic-system-diagnosis)、
[Xperf 分析动作](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/actions)、
[硬缺页记录](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/the-hard-fault-action)。
本报告的数值和结论来自本机原始记录，文档不作为实验现象的替代证据。
