# 平滑结果内存复用验证

本轮已把约 5 MiB 的平滑结果图改为启动时准备、逐帧重复使用。相同画面的单独
对照确认平滑更快；完整回放的日常处理速度变化较小，不能称为整套程序明显提速。
A、B 全视频的像素、轮廓、编号、事件及背景一致，未发现结果被下一帧覆盖。

本轮全部是 WSL 中的离线视频验证，没有连接相机或 AFG，没有改变 Windows 部署。
真实相机与录像并行时的表现尚未验证。

## 1. 实际改动

- `online_tracking.py`：每个分析实例持有一张 `float32` 平滑图，大小为
  1024 × 1280 × 4 = 5,242,880 字节，即 5 MiB。
- 实际分析线程的 `start()` 写完这块空间，原有 3 次预热也直接写入它；预热完成后
  清空，再发出准备完成记录。背景、正式目标编号和帧号不因预热改变。
- `bubble_tracker.py`：`segment()` 新增可选的 `blurred_out`，传给
  `cv2.GaussianBlur(..., dst=blurred_out)`。仍使用同一函数、同一平滑强度、同一边缘
  处理，未改识别阈值、轮廓规则或追踪判断。
- 未提供 `blurred_out` 的原有调用仍得到独立图像。错误尺寸、数据类型、只读数组
  和与输入、背景、工作图重叠的数组会被拒绝。

使用顺序是：平滑 → 识别 → 追踪 → 背景更新 → 提交记录 → 下一帧。
背景更新同步用完平滑结果；保存线程只接收独立的轮廓字节、编号、位置及事件。
它不读取平滑图，所以这里不需要增加多张图的轮换队列。

核对本轮修改反向还原后的文件指纹，与修改前完全一致；没有覆盖先前未提交工作。
送帧、数据库及异步保存模块未改动，见 `scope_check.json`、`plan.json` 和
`code_after.json`。

## 2. 输入与测试方法

- 原始录像：`microbubble_tracking/data/raw/expA.mp4`、`expB.mp4`，各 1320 帧。
- 延续上一轮启动验证的固定参考：两段均使用 `results/B_offline/background.npy`，
  在首帧对齐后按原规则更新。不是为真实新实验提前使用未来画面。
- 对应时间和动作文件：`data/pzt/expA`、`data/pzt/expB`，全程只读。
- 环境：WSL2，Python 3.12.3，OpenCV 4.10.0，NumPy 2.2.6；OpenCV 24 线程、
  送帧转换 1 线程，沿用前次配置。完整环境与输入文件指纹保存在 `pixels/verification.json`。
- 修改生产代码之前先跑 A、B 各 3 次完整原速回放；修改后各 3 次。
  两组均只打开已有阶段计时，不启用逐帧线程扫描和深度诊断。
- 另各连续重复 5 遍，用于检查积压与内存；此时关闭阶段计时，使用正常运行设置。
  重复播放使用明确标注的测试时间轴，不把重复录像冒充新实验，也不重复关联真实 PZT 动作。
- 全视频逐像素对照使用同一当前分割函数：一份不传平滑输出数组，另一份传入复用数组。
  两份背景和追踪状态独立推进，不复制或执行旧版本源码。

## 3. 平滑本身的耗时和分配

从两段原视频各取 12 张分布于全程的画面，每张交错执行两种方式各 30 次：
每种方式共 720 次。两者输入相同，均已预热；计时不包含像素核对。

| 单次 GaussianBlur | 原方式：新结果图 | 复用结果图 |
| --- | ---: | ---: |
| 中位耗时 | 1.505 ms | 1.336 ms |
| P99（99% 不超过） | 2.435 ms | 1.725 ms |
| 最慢一次 | 2.768 ms | 2.086 ms |
| Python 可追踪的新增分配峰值 | 5,242,976 B | 44 B |
| 分析线程累计轻微缺页 | 173,340 | 0 |
| 分析线程累计重大缺页 | 0 | 0 |

中位耗时下降约 11.2%。这些数字只描述本次单独平滑测试，不是整帧提速比例。
“轻微缺页”是 Linux 为页面建立映射等工作，不等于从硬盘读取 Windows 页文件。
分配统计证明整幅输出图不再重新申请，不代表 OpenCV 内部没有任何临时分配；
本轮也没有采集 Windows 页文件活动。原始逐次数据在 `pixels/kernel_timing.csv`。

| 视频 / 步骤 | 修改前中位 | 修改后中位 | 修改前 P99 | 修改后 P99 | 修改前最大 | 修改后最大 |

| A 平滑 | 1.417 | 1.403 | 2.214 | 2.298 | 5.153 | 4.774 |
| B 平滑 | 1.438 | 1.420 | 2.457 | 2.227 | 4.605 | 3.947 |
| A 整帧处理 | 9.065 | 9.070 | 12.267 | 12.348 | 23.312 | 24.518 |

单位均为 ms。整帧中位耗时基本持平，不能声称已明显提高整体处理速度。
在正常回放中，原内存分配器本身也可能重复使用空间；单独测试与完整流程的缓存和
内存使用条件不同，所以不能直接把单独节省的时间从整帧耗时中扣除。

### 保留的单帧缺口

- 修改前 6 次：各 1320 帧全部处理并保存。
- 修改后 6 次：5 次全部处理；`after_A_2` 处理并保存 1319 帧。
- 视频第 1142、1143、1144 帧分别耗时 24.518、20.308、21.369 ms。
  等待时间从 0.575 ms 增至 9.141、13.393 ms；等待中的第 1145 帧（源帧 1419）
  被下一张画面替换，程序明确记录为 `replaced`。原始视频没有被修改。
- 这三帧平滑分别耗时 3.618、4.315、3.034 ms，暗度计算分别为
  5.776、5.600、5.317 ms。多个步骤连续变慢，不能把这次缺口直接归因于平滑。
- 本轮未开启底层诊断，无法据此确认这段变慢来自系统调度、内存或其他底层原因。
  也不能据此宣称修改后永远不会跳帧。

完整窗口在 `replay_gap_window.json`；原始记录在 `after_A_2/consumer_timing.csv`、
`source_timing.csv`、`frame_outcomes.csv`。该运行没有冒充“完整视频结果一致”。

## 5. 完整结果、持续运行与覆盖检查

两段视频的 **2640 帧逐位比较全部通过**，没有使用误差容限：平滑图、区域编号图、
轮廓点、逐帧追踪记录、事件、结束目标及每次更新后的背景均相同。
每帧的核对指纹和时间在 `pixels/pixels_A.csv`、`pixels/pixels_B.csv`。

5 次未缺帧的新回放，其数据库科学数据均与修改前对应结果一致，包括轮廓原始字节、
编号、事件及修订、源帧号和视频时间。输入动作表、视频时间表、动作对应范围及
初始/最终背景也一致。机器计算耗时、运行身份和准备记录不要求相同。

| 连续回放 | A | B |
| --- | ---: | ---: |
| 时长 | 110.000 s | 109.999889 s |
| 送入 / 处理 / 保存帧数 | 6600 / 6600 / 6600 | 6600 / 6600 / 6600 |
| 跳帧 / 过期帧 | 0 / 0 | 0 / 0 |
| 第一遍之后的内存范围 | 185.961–186.348 MiB | 185.500–185.676 MiB |
| 第二遍 / 最后一遍内存中位数 | 186.123 / 186.344 MiB | 185.619 / 185.672 MiB |
| 保存队列峰值 / 结束积压 | 2 / 0 帧 | 7 / 0 帧 |

在这两次约 110 秒测试中，内存趋于稳定，未出现持续随帧数增长的积压。
新短回放末端内存比基线约高 1–1.5 MiB；复用减少的是反复申请，不保证常驻内存更少。
不能把约 110 秒的检查外推成任意长时间的保证。

**213 项测试通过（21.93 秒）**，其中新增检查覆盖：

- float32/float64、不同平滑强度、非连续或只读输入，复用前后逐位一致。
- 错误形状、类型、只读输出及内存重叠被拒绝，原输入与背景不被修改。
- 旧调用保留的平滑图不会被下一帧覆盖。
- 故意阻塞保存线程，连续处理 10 帧，再把平滑工作图改成无效值；待保存轮廓、
  编号和位置仍正确，最后全部写盘。
- 准备完成信号、异常收尾、跳帧记录和原有自动清理规则继续通过已有测试。

汇总脚本最初误把 B 的实际时长要求成精确 110 秒，导致断言失败；现已保留实际
PTS 时长并使用小于 1 ms 的时长核对余量，没有改变帧时间和实验数据。最初日志也保留。
