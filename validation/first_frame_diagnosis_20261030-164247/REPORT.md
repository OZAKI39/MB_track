# 首帧变慢原因排查

日期：2026-10-30。只使用离线 A 视频，正式识别、追踪、保存和送帧代码保持不变。

**主要原因已经定位：送帧端虽然预热了图像转换，分析端仍有大块工作内存到首帧才第一次真正写入；另外，首次调用图像处理和形状计算时，偶尔还要等待所需页面调入。自动清理不是本次重现的首帧长停顿来源。**

本轮新增的是独立诊断脚本和对应测试，没有把诊断用的准备动作接入正式实验。

## 1. 先在现有回放流程中重现

用现有 `paced_replay.py`，每次重新启动进程，取 A 视频前 120 帧，分析线程配置 24、图像转换线程配置 1。主动打开已有的详细诊断，记录实际耗时、线程执行时间、缺页和自动清理。

| 独立启动 | 首帧总耗时 | 与首帧重叠的自动清理 |
| --- | ---: | ---: |
| 第 1 次 | 42.227 ms | 0 ms |
| 第 2 次 | 26.299 ms | 0.079 ms |
| 第 3 次 | 19.661 ms | 0 ms |

原始数据分别在 `detailed_1`、`detailed_2`、`detailed_3`。这说明首帧额外开销能够重现，但长停顿不是每次一样长。

第 1 次的主要耗时如下。后续耗时取同次回放第 5–59 帧的中位数；不同画面的区域数量会变化，这一列用于观察阶段差异，精确对照见下节。

| 步骤 | 首帧 | 后续典型耗时 | 首帧额外记录 |
| --- | ---: | ---: | --- |
| 输入转为计算用的小数格式 | 2.366 ms | 0.773 ms | 448 次无需磁盘读取的缺页 |
| 平滑图像 | 3.394 ms | 2.212 ms | 784 次无需磁盘读取的缺页 |
| 相对暗度除法 | 1.791 ms | 0.730 ms | 258 次无需磁盘读取的缺页 |
| 筛选候选区域、连接细小断口 | 18.157 ms | 1.119 ms | 线程实际执行 3.349 ms；1 次需要 I/O 的缺页 |
| 给连通区域编号 | 5.557 ms | 0.702 ms | 整个进程 865 次无需磁盘读取的缺页 |
| 追踪，包括区域形状计算 | 4.183 ms | 1.774 ms | 线程实际执行 2.033 ms；7 次需要 I/O 的缺页 |

这里“缺页”不是程序报错，而是进程访问的页面需要由系统准备或调入。无需 I/O 与需要 I/O 的两种计数含义来自 [Linux getrusage 官方手册](https://man7.org/linux/man-pages/man2/getrusage.2.html)。不能把所有缺页都说成读取 Windows 页文件。

18.157 ms 的候选区域步骤中，实际计算只有 3.349 ms，差值约 14.808 ms，同时出现需要 I/O 的缺页和主动让出处理器的记录。可以确认该段包含等待；本次没有记录这一笔 I/O 的开始和结束，不能把全部差值精确归给它，更不能断言它来自某一个 Windows 程序。

## 2. 主要工作区已经定位到具体代码

`bubble_tracker.py` 的 `SegmentationWorkspace.__init__()` 中：

```python
self._darkness = np.empty_like(background)
self.component_labels = np.empty(background.shape, np.int32)
```

这两块空间在初始化时申请，但没有全部实际写过。背景尺寸是 **1024 × 1280**，其中 `component_labels` 是 **5 MiB** 的区域编号图。首帧调用 `cv2.connectedComponentsWithStats()` 时，多个 OpenCV 工作线程才第一次写入这张图。

已有的“重复使用编号图”解决了之后每帧反复申请的问题，但没有完全解决首次使用时的内存准备工作。两者是不同阶段的问题。

另外，`OnlineProcessor._validate()` 中的 `image.astype(np.float32, copy=False)`，对当前 uint8 输入仍然需要创建小数格式的图像；`segment()` 的 `GaussianBlur` 也返回新图像。首帧还会遇到这些空间的首次准备开销。`copy=False` 不代表改变数据类型时可以完全不分配空间。

## 3. 分开对照，确认不是靠猜测

新增 `first_frame_diagnosis.py`，直接调用现有 `OnlineProcessor`。各组使用同样的 A 视频前 60 帧、背景和识别规则，分别重新启动进程；前五种基础条件轮换运行顺序，各重复 5 次。之后增加两个单块内存对照，各重复 3 次，共 **31 次独立启动**。

所有组都在计时前做一次相同的完整自动清理，运行中自动清理仍开启，排除清理时机差异。使用同样的详细计时；下面结果不包含额外的系统采样运行。

| 开始前额外做什么 | 启动次数 | 首帧耗时中位数 | 首帧耗时范围 | 区域编号耗时中位数 |
| --- | ---: | ---: | ---: | ---: |
| 不准备分析端，24 线程 | 5 | 18.590 ms | 18.435–22.077 ms | 5.066 ms |
| 只提前写过区域编号图 | 3 | 13.521 ms | 13.059–14.176 ms | 0.570 ms |
| 只提前写过暗度图 | 3 | 22.408 ms | 17.768–27.923 ms | 2.483 ms |
| 提前写过全部已有工作区 | 5 | 15.213 ms | 11.133–17.082 ms | 0.648 ms |
| 只试运行一次区域编号函数 | 5 | 15.823 ms | 14.988–19.266 ms | 1.116 ms |
| 试运行一次分割与临时追踪 | 5 | 12.491 ms | 9.916–14.171 ms | 0.593 ms |
| 不准备分析端，改为 1 线程 | 5 | 17.438 ms | 16.206–19.552 ms | 3.526 ms |

仅写过区域编号图，就把这一阶段的耗时由约 **5.07 ms 降到 0.57 ms**；同一阶段整个进程的无需 I/O 缺页次数中位数由 **848 降到 64**。这给出了针对具体内存的直接对照证据。

完整试运行后，首帧整个进程的无需 I/O 缺页次数中位数由 **3367 降到 326**。准备动作本身中位数耗时 **16.159 ms**，只是移到了正式处理第一帧之前，并不是这部分工作凭空消失。

只处理暗度图没有带来稳定的整帧收益，不能把它当作已验证的完整方案。不同组会改变内存布局和首次使用顺序，因此各组差值不能简单相加，也不能保证某一种准备顺序在所有机器上都最快。

1 线程组后续典型帧耗时约 **11.00 ms**，24 线程未预热组约 **9.42 ms**；单纯降低线程数也没有消除首帧额外开销，本轮没有修改正式线程配置。

这些分项对照保留所有 60 帧，帧时间使用 `帧号 / 视频标称帧率` 的诊断时刻表，没有最新帧替换队列。因此它们用于确认原因和核对结果，不能代替真实送帧和录像的零跳帧验收。早期隔离组元数据写作 `offline video PTS` 不够准确；以本报告这一说明为准，后续诊断脚本已改为明确的 synthetic diagnostic schedule。相机原始时间记录没有改动。

## 4. 系统级记录进一步确认了什么

另做两次独立的系统采样，不混入上表性能统计：

- `fault_trace` 使用现有回放流程，记录线程创建和大缺页事件。首帧处理区间内没有新建分析进程的线程。各个 24 线程隔离组准备前后也均为 101 个进程线程。因此不能把这次区域编号开销解释为“首帧才创建线程池”。
- `minor_trace` 对小缺页每 16 次采一次样。首帧区域编号区间有 49 个采样，全部落在 OpenCV 的 `cv2.abi3.so`，分布在多个工作线程；详细计数为 851 次进程小缺页。对应阶段约 7.06 ms，其中各线程执行时间合计约 83.45 ms。结合单独提前写编号图的对照，说明这一阶段确有并行首次访问内存的额外负担。

系统采样会增加开销，7.06 ms 不用于与无系统采样的条件直接比较。当前 perf 构建不能完整展开所采样的调用栈，报告保留共享库和指令偏移，不把未知符号补写成函数名。见 `component_fault_report.txt`、`minor_faults.data`、`major_faults.data`。

## 6. 可以得出的结论及边界

首帧仍慢的主要可重复来源，是**分析端没有像送帧端那样完成首次运行准备**。其中，区域编号图首次写入已经由单块内存对照确认；输入转换、平滑、暗度及轮廓工作空间也有额外首次使用成本。偶尔还会叠加需要 I/O 的页面调入，让本来约二十毫秒的首帧变得更慢。

本轮在现有回放中重现了 **42.227 ms** 首帧，并记录到上述等待。上一轮那次 **40.217 ms** 没有同样的细分记录，不能事后宣称已逐毫秒还原了那一次的全部原因。这里区分已经复现的机制与无法追溯的历史细节。

后续最有针对性的改进是：在分析端正式接帧前，准备实际使用的工作空间，并使用独立临时状态试运行一次识别与追踪，再从原始首帧和空编号开始正式处理。本轮诊断已确认这种方向有效且不改变识别结果；尚未接入正式回放/相机入口，也未验证真实录像、分析和 PZT 同时运行的首帧表现。

复现单组诊断：

```bash
.venv/bin/python -m customer_workspace.microbubble_tracking.first_frame_diagnosis \
  --condition labels --frames 60 --diagnostics \
  --output-dir customer_workspace/validation/first_frame_labels_new
```

输出目录必须不存在。`--condition` 可选 `cold`、`touch`、`labels`、`darkness`、`components`、`analysis`。这是独立离线诊断入口，普通实验仍不启用这些逐帧诊断。
