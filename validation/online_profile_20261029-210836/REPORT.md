# 计算、记录整理与保存：耗时分析

**主要耗时是寻找微泡的图像计算，以及每帧提交保存的等待。整理记录本身很快。**
本次增加分项计时，完成两段完整录像的前后对照，又按真实速度分别重复回放 3 次。
保留两处经过核查的小改动：只在轮廓附近收集像素；省去整数图像不必要的数值扫描。
未改变识别阈值、轮廓、匹配规则、保存内容或每帧确认提交的要求。

## 1. 时间分别花在哪里

下表是 A、B 两段各 1320 帧、合计 2640 帧逐帧处理的平均每帧耗时。
修改前后使用完全相同的画面和背景，完整保留所有帧，不用两个不同跳帧子集作分项对照。
输入仍沿用顺序回放的彩色画面，在接口内转灰度；视频解码、背景准备、最终表格导出不计入这里。

| 工作 | 修改前平均 (ms/帧) | 最终版本平均 (ms/帧) |
| --- | ---: | ---: |
| 输入检查与格式转换 | 1.831 | 1.518 |
| 识别微泡轮廓 | 10.085 | 9.964 |
| 收集区域像素、测形状、对应编号 | 3.893 | 1.466 |
| 更新背景 | 0.541 | 0.521 |
| 整理观测和返回记录 | 0.129 | 0.123 |
| 数据库登记及相关状态处理 | 0.217 | 0.215 |
| 等待这一帧正式提交保存 | 4.387 | 4.520 |
| 其余小段开销 | 0.006 | 0.005 |
| 完整处理 | 21.089 | 18.333 |

这些是平均值，便于各项相加；不是把各项中位数或 P99 相加。只有上表主阶段相加，
才等于完整处理。`seg_*` 和 `track_*` 是内部细分，不能再重复算进去。

由此可以判断：

- **图像计算是大头。** 识别轮廓本身约 10 毫秒，仍值得后续细查；本轮没有改它的识别规则。
- **追踪中的像素收集有明确浪费。** 原先每帧扫描整幅图，再按区域分组；现在只扫描每个轮廓的包围范围。
- **记录整理不是主要瓶颈。** 整理观测、轮廓字节、帧信息和返回结果合计约 0.12–0.13 毫秒，继续简化这部分收益很小。
- **提交保存有固定成本。** 每帧约 4.4–4.5 毫秒等待提交完成，偶尔更久；不能把这段时间全部归为 Python 代码慢。

`database_write_ms` 包含目标/事件的状态处理和数据库操作，不等于纯写入设备的时间。
`commit_ms` 是原有提交点的实际等待，包括同步写入及可能的数据库日志整理。
本次没有把保存改为较弱的模式、没有每隔几帧才提交，也没有在结果未保存时就返回成功。
没有进一步把提交等待拆成 WSL、操作系统缓存、物理磁盘各自所占时间，因此不能据此给磁盘性能下结论。

## 2. 实际保留了什么改动

**只扫描目标附近。** 原来收集区域像素每帧平均约 2.55–2.56 毫秒，现在为 0.13–0.15 毫秒。
这一步不只看外接矩形，还会核对矩形里的区域编号，因此不会把旁边区域或孔洞误算进来。
像素仍按原来的行、列顺序排列，位置、形状和匹配结果保持一致。

**省去没有必要的检查。** 8 位无符号整数图像本来就只能是 0–255，不可能有无穷大或无效小数。
这类图像不再逐像素重复检查这些条件。浮点图像仍保留完整检查；没有省去帧号、时间和实验身份核查。
输入检查与格式转换的总耗时还受灰度转换、数组转换和调度影响，不能把全部前后差值都归因于这一处改动。

完整顺序处理的平均耗时：A 从 20.865 降到 18.454 毫秒，B 从 21.313 降到 18.212 毫秒。
两段合并，这次对照平均减少约 2.76 毫秒，约 13.1%。各阶段有系统运行波动，主要可解释收益来自
区域像素收集；没有把未改动步骤的小幅波动当作新的优化成果。

另外试过复用亮度计算临时数组：这一步变快，但其他图像步骤明显变慢，整体收益不理想，已经撤回。
该试验保存在 `after_fixed_A` 和 `after_fixed_B`；最终采用的是 `final_fixed_A`、`final_fixed_B`。
没有确定临时数组改变为什么影响后续步骤，不能把可能的内存分配/缓存影响当成已证实根因。

## 3. 按真实速度送帧，实际改善多少

原录像仍按约 60 帧/秒发送，每段约 22 秒、1320 帧。发送与处理各自独立，等待槽仍只保留最新一张。
本次修改前先重新测 A、B 各一次；修改后 A、B 各重复 3 次，全部打开相同的分项计时。

| 测试 | 处理帧数 | 被替换帧数 | 平均处理帧/秒 | 完整处理 中位数 / P99 (ms) |
| --- | ---: | ---: | ---: | ---: |
| before_paced_A | 1026 | 294 | 46.64 | 20.50 / 29.59 |
| before_paced_B | 1059 | 261 | 48.14 | 19.88 / 29.35 |
| final_paced_A_1 | 1203 | 117 | 54.68 | 17.33 / 26.65 |
| final_paced_A_2 | 1194 | 126 | 54.27 | 17.47 / 25.25 |
| final_paced_A_3 | 1153 | 167 | 52.41 | 18.15 / 27.29 |
| final_paced_B_1 | 1202 | 118 | 54.64 | 17.40 / 26.41 |
| final_paced_B_2 | 1153 | 167 | 52.41 | 18.14 / 28.12 |
| final_paced_B_3 | 1185 | 135 | 53.86 | 17.58 / 26.93 |

**当前实际约 52–55 帧/秒，优于本次修改前的约 46.6–48.1 帧/秒，但仍未达到 60 帧/秒全部处理。**
修改后每次仍有 117–167 帧被替换，约占 8.9%–12.7%。这些画面在原录像里仍然保留，分析入口明确记录跳过。

实际送帧的晚点 P99 均小于一帧间隔，每张送入画面的去向均核对无误。
程序完整处理的中位数仍为 17.3–18.2 毫秒，超过 60 fps 的平均 16.67 毫秒预算，提交等待还会有较慢的个别帧。
因此暂时不能承诺每帧都处理，也不能承诺短暂合并/分离事件完全不漏。

顺序对照输入彩色图，真实速度回放的发送端先转灰度，所以两类测试的输入准备耗时略有不同。
实际帧率以真实速度回放的处理帧数计算，不能拿顺序测试耗时的倒数冒充在线结果。
上一轮和本轮修改前的速度也存在正常运行波动；这里的改善对比使用的是本轮重新测得的修改前结果。

## 4. 正确性与保存要求核查

45 项自动检查通过，包括跳帧时间、目标确认、取消、写盘失败回滚、区域孔洞/相邻编号/图像边缘、
浮点无效值拒绝、分项计时加总，以及测量开关不改变结果。

两段完整录像的全部 2640 帧，合计 39884 条区域观测，修改前后逐项相同：
轮廓字节、位置和形状数值、速度、编号、事件、状态历史、原始帧号/时间、最终背景、PZT 动作对应表。
也与第一轮的 `final_A`、`final_B` 完整记录核对相同。只排除本来就应该不同的运行耗时和本次运行身份。

SQLite 仍使用 WAL + FULL，每帧提交一次；现有数据库表结构不变。
原视频、参考背景及 PZT 原始时间文件的文件指纹已核对，未修改。
完整比对证据见 [final_verification.json](final_verification.json)；本次没有改写人工审查或旧分析结果。

这里证明的是“输入同样画面，计算结果未改变”。真实速度回放会跳过不同画面，不能宣称其事件记录
与完整处理完全一致。更高帧率有助于少漏画面，但本轮没有重新进行人工准确率审核。

## 6. 后续值得检查的部分

优先检查能否让计算与保存更好地配合，例如保存上一帧时计算下一帧，同时保证对外提供的结果已经保存。
这需要专门处理失败、取消和内存积压，不能简单把保存扔到后台就宣称完成。本轮未实施这项流程调整。
图像识别仍约 10 毫秒，也可以继续检查重复的整图读写；任何改动都应像本次一样用完整帧和精确结果比对验证。

当前不建议把精力放在重写编号字典或缩短说明字段上，因为实测这部分占用很少。
本轮没有关闭同步保存、删减轮廓、降低图像分辨率、调整识别阈值，或改变正式实验设备行为。

所有测试均为 WSL 软件回放，没有连接相机/AFG，没有同时录像或界面显示的负载。
环境沿用 Python 3.12.3、OpenCV 4.10.0、NumPy 2.2.6、PyAV 19.0.1；完整环境和线程设置见各真实速度回放的
`pacing_settings.json`。这些结果不能直接当作实机系统的性能保证。
