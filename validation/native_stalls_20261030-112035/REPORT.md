# 停顿原因追查与关闭其他程序后的对照

本次确认了**正在发生的内存处理开销和数据库等待位置**，但没有重新出现原先的
157.147 ms 转换和 1760.428 ms 提交。因此，不能把本次较短停顿的调用栈冒充那两次
历史事件的完整根因。

## 1. 关闭部分程序后的结果

用户自行关闭部分不用的程序；没有由诊断程序结束其他应用。关闭前后使用同一段 B
视频、相同参数与相同的轻量系统采样方式，按原速度连续回放三遍，总计约 66 秒、3960 帧。
这是已有视频的离线回放，不是新进行的相机/AFG 实验。

| 检查项 | 关闭前 | 关闭后 |
| --- | ---: | ---: |
| Windows 可用内存中位数（配套采样时段） | 666 MB | 2342.5 MB |
| 彩色图转换中位数 | 1.569 ms | 0.701 ms |
| 彩色图转换 P99 | 3.067 ms | 1.861 ms |
| 彩色图转换最慢一次 | 17.222 ms | 5.839 ms |
| 数据库提交中位数 | 4.079 ms | 4.076 ms |
| 数据库提交 P99 | 12.640 ms | 12.660 ms |
| 数据库提交最慢一次 | 20.118 ms | 32.104 ms |
| 实际分析并保存帧数 / 送入帧数 | 3894 / 3960 | 3959 / 3960 |

P99 表示约 99% 的记录不超过该值。颜色转换统计排除首次启动帧；数据库统计包括
所有提交批次。两组都用异步保存、队列容量 32、最多合并 4 帧，分析 OpenCV 24
线程，视频解码 1 线程、颜色转换 1 线程。没有改动识别规则。

另用 A 视频做独立启动对照：关闭前两次转换最大值分别为 20.943、14.083 ms；
关闭后三次为 5.424、7.740、4.904 ms。`repeat_A_3`、`repeat_A_4` 与用户关闭
程序的过程重叠，**不纳入前后比较**。

结果支持：释放 Windows 内存、减少其他应用负担，能减轻本次图像转换停顿；
但不能保证以后没有长停顿，也没有消除数据库的刷盘等待。关闭应用同时改变了
内存与其他负载，不能把它当成只改变单一因素的严格试验。

## 2. 图像转换到底慢在哪里

系统采样不再只看 Python 函数名称，而是追到函数正在调用的系统操作。

### 情况 A：转换时在为输出图像准备内存

`focused_default_B` 第 3206 帧的彩色图转换耗时 17.222 ms，线程 CPU 为 17.237 ms，
出现 960 次软缺页，没有主动等待或被切走的记录。软缺页在这里是为图像准备、映射
内存页，不等于从磁盘交换区读数据。

原生调用栈显示 `libswscale → 内存访问缺页 → do_anonymous_page →
__mem_cgroup_charge`，即颜色转换在访问新输出内存时进入了内存分配、记账过程。
这不是“像素算法突然复杂了”，也不是仅仅排队等其他转换线程。
采样只能说明采到的时间花在这些位置，不能把整段 17 ms 全部算成某一个函数。

证据：[conversion_allocation_stack.txt](conversion_allocation_stack.txt)。

### 情况 B：线程在等待内存页搬移完成

`deep_B` 第 3909 帧转换经过 31.034 ms，但自身 CPU 仅 0.773 ms。
连续三次系统采样显示线程处于等待状态，位置为 `migration_entry_wait_on_locked`。
同时 Linux 调度等待计数没有增加，说明这段已采到的等待是**内存页正在搬移，线程
要等它完成**，不能归为“CPU 没有排到这个线程”。

这里调用栈中的 `do_swap_page` 也会处理内存搬移标记，不能仅凭名字断言发生了
Linux 磁盘换页。触发这次搬移的上游任务仍未确定。

证据：[memory_events.json](memory_events.json) 中包含原始计时及三个等待样本。

### 情况 C：以前的“转灰度”计时还包含释放旧图像

`deep_B` 第 756 帧原“转灰度”步骤耗时 37.818 ms、CPU 37.538 ms。
采样显示实际经过 `av_buffer_unref → free → systrim → brk → 内核解除内存映射/
释放内存页`。也就是说，记录在转换步骤中的一部分慢点，实际来自释放图像缓冲区。

现已将日志拆成 `compute_gray`、`release_previous_gray` 和 `release_bgr`，
保持原来的像素计算。证据：[gray_slow_stack.txt](gray_slow_stack.txt)。

额外尝试了仅在一个子进程中禁用 libc 自动收缩堆的对照。它没有带来可靠改善：
B 转换中位数 1.590 ms、最大 15.087 ms。该选项会改变内存分配策略，不能解释成
仅去掉一次释放操作，**未采用到正式默认设置**。

### 对原先 157 ms 的判断边界

原记录中线程 CPU 约 158 ms、没有线程切换，所以不像“绝大多数时间都在等线程”。
本次抓到了同一转换路径中的内存准备开销，但原先那 157 ms 没有原生调用栈，本次
也未复现，仍不能断言它具体是哪次内存操作造成的。

## 3. 数据库到底等在哪里

本次把保存线程单独登记并采样，确认同类提交等待在以下链路：

```text
SQLite 提交
  → fdatasync（要求系统完成数据写入）
  → ext4_sync_file（文件系统同步）
  → 等待数据页写回 / 文件系统日志完成 / 虚拟磁盘刷新完成
```

这一步已经在保存线程内，不是分析端提交队列的等待，也不是把图像识别计算算到了
数据库头上。保持了原有 WAL / FULL 和 256 页自动检查点设置。

例如关闭程序后的 B 第 3347 源帧提交耗时 **32.104 ms**，自身 CPU **0.891 ms**。
三个内核样本先后显示 `folio_wait_writeback` 和 `jbd2_log_wait_commit`，即等待
数据页写回和文件系统日志完成。关闭前 B 第 482 源帧提交的 20.118 ms 中，还采到
`submit_bio_wait → blkdev_issue_flush`，直接等待虚拟磁盘刷新请求结束。

另外一次 86.816 ms 提交情况不同：CPU 达 78.002 ms，调用栈显示 SQLite 自动
检查点正在将日志页写回数据库，内核同时分配、清零内存页。不能把这 86 ms 全算成
一次磁盘等待，也不能用它解释 CPU 只有 0.252 ms 的历史 1.76 秒事件。

证据：[evidence_summary.json](evidence_summary.json) 的 `worst_native_samples`、
[commit_slow_stack.txt](commit_slow_stack.txt)。汇总时只将采样区间完整落在提交
区间内的样本计入，避免把保存线程闲置时的队列等待误算成提交等待。

### 对原先 1.76 秒的判断边界

原始日志足以定位到提交阶段，并显示主要在等待；本次进一步确认了正在发生的同类
文件系统/刷盘等待。但没有抓到持续 1.76 秒的原生事件，因此不能指定历史异常究竟
是某次宿主存储阻塞、虚拟磁盘停顿，还是保存线程/虚拟机被暂停。

WSL 的 Ubuntu 数据盘位于 **F:\\WSL\\Ubuntu**，Windows 页文件位于 **C:**，
二者在不同的 SSD 上。不能把 Windows 读页频繁直接解释为 F 盘损坏或两者争用同一盘。
现有历史系统日志和 Linux 日志没有找到对应的明确磁盘错误；这不等于排除了存储问题。

继续区分 Windows 存储层、虚拟磁盘和物理 SSD，需要在长停顿再现时同步采集
Windows 系统事件跟踪。当前 Windows 账户不是管理员，本次没有提升权限或启动
该类记录。因此，**这次没有完成历史 1.76 秒停顿的宿主机根因确认**。

## 4. 宿主机内存证据与限制

Windows 总内存约 16 GB。关闭应用前配套采样的可用内存曾低至 15 MB，关闭后
采样范围为 1644–2645 MB；宿主机从磁盘读入内存页的近似速率中位数由 14.62
降为 3.77 MiB/s。这是整个 Windows 的计数，不能全部归给本项目或 WSL。

WSL 自己仍可能报告有可用内存，同时 Windows 已经很紧张；只看 Linux 的交换区
读写不能排除宿主机内存压力。Windows 页文件占用约 8 GB 只是占用量，不是实时
读写速度，速率另由累计计数的差值计算。

宿主机计数使用各次查询的 UTC 开始/结束时刻对应；没有直接相减 Windows/WSL
各自的程序计时器。查询本身约数百毫秒到一秒多，只适合观察秒级趋势，不用于
声称某个几毫秒事件与 Windows 计数精确同步。

## 5. 实际改动与验证

- 可选诊断增加保存线程自己的 CPU/内核等待记录；默认不开启。
- 将灰度计算与旧图像内存释放分开计时，识别与追踪规则保持原样。
- 增加只读线程观察器，保留调用栈、线程编号、刷盘时间与系统计数。
- 检查了 11 次离线运行：送入 25080 帧，分析并提交 24641 帧，提交的 24641 帧
  全部保存，数据库快速完整性检查均通过。其余帧是分析链路跳帧，不能声称没有丢帧。
- 单元测试 **75 项通过**，包括诊断开关前后的轮廓/事件/数据库内容一致性，以及
  诊断文件关闭失败时仍完成数据库关闭和错误通知。
- 新观察器、诊断模块、保存线程、视频源及本次测试的静态检查通过。对涉及的全部
  老模块检查仍有既存风格告警，没有为此改写无关逻辑。

初次 `deep_B` 是较重的广范围采样，记录过 1 个丢失块和 61 个乱序事件，不能拿它
作为速度验收；其中已采到的调用栈只用于说明发生过哪些操作。前后对照使用仅针对
源/保存线程的较轻采样，其日志未报告丢失。所有详细诊断都有额外开销，当前数据
不代表正式运行已达到新的性能承诺。

本次没有连接或改变 AFG、PZT、相机；没有改变数据库可靠性参数、Windows 驱动、
服务或执行策略；没有提交或推送 Git。
