# 启动预热：实现与对照结果

日期：2026-10-30。

**结论：启动预热已接入，前几帧的转换停顿明显减少，但仅靠这一步还没有彻底解决停顿。**
12 次预热启动中，前 5 帧最长转换为 14.974 ms；同批不预热对照为 78.715 ms。
预热组第 13 帧仍出现一次 76.591 ms 的转换，因此不能宣布后续帧也稳定。
本轮只使用已保存的实验 B 录像，不连接相机，不发送 AFG/PZT 命令。

## 本次具体做了什么

在 `microbubble_tracking/paced_source.py` 的实际送帧进程中：

1. 解码第一张真实画面，获取尺寸、格式和原始视频时间。
2. 用这同一张画面执行原有的彩色转换、灰度转换，默认重复 8 次。
   第一遍真实转换申请并写入所需内存；后续几遍让转换函数和内存分配器完成初始化。
3. 释放临时彩色图、灰度图，保留转换器的初始化结果；不清空内存分配器。
4. 回到原有流程，从原来的第 0 帧正式送出。只有准备完成，回放时钟才启动。

预热不推进视频，不生成追踪记录，不占用正式帧号，不向共享单帧槽放入测试图像。
正式的 `to_ndarray(format="bgr24")`、`cvtColor`、共享单帧槽、原帧时间和保存方式均保留。
没有借此次预热引入新的正式缓冲区或更换图像传递路线。

预热使用当前真实输入的 1280 × 1024、`yuv420p` 画面；彩色输出约 3.75 MiB，
灰度输出约 1.25 MiB。预热记录单独保存在 `source_warmup.json`，其中有进程编号、
尺寸、格式、逐次耗时、次数和状态。失败或取消时保存原因，不开始正式送帧。

`paced_replay.py` 默认启用 8 次预热；对照参数为 `--conversion-warmup-iterations 0`。
允许范围为 0–32。8 次是本轮实际验证的设置，不声称它是所有设备上的最优次数。

## 如何比较

- 同一份 `data/raw/expB.mp4`，1280 × 1024，约 60 fps。
- 原始文件 SHA-256：`6e2e272187aaa5e03bd9e058ab1afaf11e6e73e6e0800e23c8effe815f0218d1`。
- 12 对独立启动，共 24 次，每次按原始视频时刻回放前 60 帧。
- 每对包含预热 0 次与 8 次；两种先后顺序交替，减小先运行哪一组的影响。
- 分析 24 线程，解码 1 线程，彩色转换 1 线程；送帧端灰度转换保持 1 线程。
- 原识别参数、参考背景、异步保存、等待方式一致。
- 启用原有细分计时和线程计数；没有同时运行 WPR、原生栈采样或其他基准任务。
- 环境：WSL2 / Linux 6.18.54.1，Python 3.12.3，PyAV 19.0.1，
  OpenCV 4.10.0，NumPy 2.2.6。

预热本身独立计时，不计入正式转换，也不把额外的 8 次当成正式帧。
下表测量的是之前出现停顿的 **解码图像转彩色图** 这一段，不是全部识别耗时。
完整命令在 `commands.json`，每次环境、代码指纹在各目录的 `pacing_settings.json`。

## 启动阶段结果

每组 12 次启动，各取前 5 帧，共 60 个正式转换样本。

| 指标 | 不预热 | 预热 8 次 |
| --- | ---: | ---: |
| 中位耗时 | 1.523 ms | 1.072 ms |
| P99 耗时 | 45.936 ms | 11.841 ms |
| 最长耗时 | 78.715 ms | 14.974 ms |
| 超过 10 ms | 10 / 60 | 1 / 60 |
| 超过 20 ms | 5 / 60 | 0 / 60 |
| 每次启动前 5 帧的轻微缺页次数，中位数 | 4781 | 1890 |

这里的 P99 是这 60 个样本的统计值，不能当作未来任何情况下的保证。
轻微缺页表示程序访问的内存页还需要系统准备，**不等于读取硬盘或 Windows 页文件**。
预热把一部分准备工作移到了正式开始之前，但正式转换期间仍有新的内存页准备。

额外预热耗时中位数 **12.440 ms**，本批最长 **22.064 ms**，发生在正式计时之前。
这批不预热最长值是 78.715 ms；它与上轮的 29.6 ms 来自不同运行，不能把两个数字
直接当成同一次停顿的前后变化。

## 后续帧仍有哪些问题

把每次前 60 帧全部统计，每组 720 次正式转换：

| 指标 | 不预热 | 预热 8 次 |
| --- | ---: | ---: |
| 中位耗时 | 1.447 ms | 1.107 ms |
| P99 耗时 | 20.406 ms | 3.523 ms |
| 最长耗时 | 78.715 ms | 76.591 ms |
| 超过 10 ms | 14 / 720 | 3 / 720 |

预热组 3 次超过 10 ms 的转换全部保留：

- `pair_04_warm`：视频帧号 3，即第 4 帧，14.974 ms。
- `pair_04_warm`：视频帧号 12，即第 13 帧，76.591 ms。
- `pair_03_warm`：视频帧号 39，即第 40 帧，34.291 ms。

76.591 ms 这次记录了约 76.373 ms 的送帧线程 CPU 时间和 640 次轻微缺页。
实际经过的时间与该线程消耗的 CPU 时间接近，不能把它简单解释成“线程没轮到运行”。
它也说明预热后正式转换仍会触发内存准备。不过，本轮没有 Windows 内核记录或逐次
原生调用栈，不能据这些计数进一步断言每一毫秒花在哪里，也不能断言它是页文件读取。

保留原转换接口意味着后续调用仍申请输出内存。预热释放的空间不保证每次都被复用，
系统运行状态也会变化。这是本轮尚不能承诺彻底消除停顿的具体限制。
未继续修改正式内存复用或图像传递方式，以保持本轮只检查启动预热的范围。

## 完整录像和数据核对

另用默认 8 次预热回放完整的 1320 帧，约 22 秒，目录为 `full_warm`：

- 正式送出 1320 帧，保持原视频帧号、源帧号及原始时间记录。
- 分析完成 1319 帧；等待区的 1 帧被新画面替换，并已记录。没有过期帧。
- 提交保存 1319 帧，实际保存 1319 帧，收尾后待保存为 0。
- 转换耗时中位数 1.436 ms，P99 2.184 ms，最大 5.140 ms。
- 所有送入画面的去向可核对，数据库完整性检查通过。

这一段完整回放没有再观察到超过 10 ms 的转换，但不能抹去前述短回放中的失败样本。
这里的替换是实时分析只保留最新画面的既有行为，不是原视频文件丢帧；本轮没有重新录像，
不能据此声称已验证真实相机录像不丢帧。

24 次短回放也均完成保存核对：不预热组送出 720 帧、处理 701 帧、替换 16 帧、
过期 3 帧；预热组送出 720 帧、处理 702 帧、替换 18 帧、过期 0 帧。
因此**不能把转换耗时改善说成整套分析已明显提速或不再跳帧**。
25 次运行的保存队列最高均不超过 2 帧，无已提交记录丢失。

另外，使用两个独立解码流逐帧比较完整实验 B，只有其中一路先对首帧预热：
1320 帧的彩色像素、灰度像素、视频时间逐项完全一致。
逐帧文件指纹在 `pixel_identity.csv`，结果与输入来源在 `pixel_identity.json`。
不同实时运行可能因跳帧时机不同产生不同追踪记录，因此没有声称两次实时追踪结果完全相同。
