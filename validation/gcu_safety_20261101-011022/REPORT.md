# GCU 暂停对照的前置检查

日期：2026-11-01，Europe/Zurich。

**本轮没有暂停服务，也没有运行暂停前后的 A/B 解码对照。** 前置检查发现 CPU 温度通道持续偏高；用户暂停了不需要的高负载任务后，复查仍为 93–95°C，因此没有进入可能影响散热管理的暂停步骤。当前不能得出“暂停后停顿减少且散热正常”的结论。

## 已查明的控制台设置

当前安装的界面包为 `ControlCenter3 5.17.51.19`，后台程序为 `GCUService 1.0.2.70`。
检查的是本机官方安装包的界面资源、保存的设置和后台程序指令；没有操作界面开关、编辑设置或调用功耗设置命令。

- 安装包包含“开启 Dynamic Boost”和自动风扇管理等界面文案。共享界面资源的存在，不保证这些选项在本机的每个模式下都显示。
- 没有找到可以确认能**单独关闭 CPU/GPU 联合运行定时检查**的用户开关。不能把 Dynamic Boost 或固定性能模式直接当作等价开关。
- 程序启动时，固件支持检查返回指定值后就启动该 1.5 秒定时器；在已检查的启动和回调代码里，没有看见受界面选项控制的停止判断。
- 配置文件中的 GPU 自动省电字段 `Auto` / `AutoEnable` 为 false；这也不能证明上述定时器已关闭。上一轮的通知记录已经说明两者不能直接等同。
- `GCUBridge` 服务正在运行，`CanStop=true`，但 `CanPauseAndContinue=false`。因此普通 Windows 服务“暂停”命令不可用。停止再启动服务、临时冻结后台进程是不同操作，均未执行；也不能把停止服务冒称为无设置变化的暂停。

证据：[安装包信息](appx_packages.json)、[设置核对](settings_audit.json)、[管理员只读快照](admin_preflight/snapshot.json)、[上轮定时器和启动路径](../acpi_trigger_20261101-004740/gcu_combine_methods.json)。

也检查了[机械革命官方支持页面](https://www.mechrevo.com/cn/downloads)，没有获得能确认该独立开关的本机说明。未采用第三方下载站的程序或修改建议。

## 温度和风扇怎样读取

Windows 的 `Win32_Fan` 只返回了 `OK`，没有转速；NVIDIA 的通用风扇查询也返回 N/A。这些不能充当风扇持续正常的证据。

现已新增本机专用的只读探针 [gcu_thermal_probe.ps1](../../tools/gcu_thermal_probe.ps1)：

- CPU 温度：读固件使用的 `0x043e` 温度字节，取低 7 位。这是本机 `ECTZ._TMP` 使用的温度通道，不冒充逐核心最高温度测量。
- CPU 风扇：沿用安装程序 `GetEcCpuFanRpm` 的地址和字节顺序，读取 `0x0464` / `0x0465`。
- GPU 风扇：沿用 `GetEcGpuFanRpm`，读取 `0x046c` / `0x046b`。
- GPU 温度：直接通过 NVIDIA NVML 读取。
- 这些读取不经过 GCUService 保存的缓存；**暂停后的持续可用性仍需实际对照验证**，本轮没有声称已经验证。

固件读取使用已检查过的 `WMIReadECRAM` 协议，命令前缀为 `0x010000000000`，只允许上述五个地址；没有发送 `0x0500` 联合运行设置，也没有调用风扇、频率、电压或功耗写入方法。脚本校验本机型号和已检查的 GCUService 文件 SHA-256，版本不匹配就拒绝读取。

来源：[厂商读取函数](sensor_methods.json)、[风扇地址与字节顺序](fan_rpm_read.json)、[CPU 温度来源](live_sensor_paths.json)、[本机固件 ECTZ](../gpu_host_cause_20261031-235434/firmware/DSDT.dsl)。

最初的传感器探测在遇到双字节返回值时停止了：脚本起初只接受单字节数值。对照厂商的低字节转换后修正，保留了完整返回值，并成功读取后续 20 组温度/风扇数据。首次失败保留在 `thermal_probe`，没有把失败样本算作有效测量。

旧的通用 WMI 温度接口与性能计数器曾分别返回约 62°C 和 94°C，存在不一致，因此没有使用较低的缓存读数来批准暂停。直接读取固件通道后，连续读数仍在高位。没有为了测试绕过这一限制。

## 为什么未进入暂停对照

为本次短时诊断设置的保守开始条件：连续 10 次完整读数，CPU 低于 80°C、GPU 低于 70°C，两只风扇均有有效的运行读数。它们是诊断准入条件，不是厂商标定的硬件极限。

当前 CPU 超出了开始条件。用户本轮回复授权的是关闭不需要的负载后复查温度；没有将其解释为暂停服务授权。
因此没有申请或实施实际暂停，也没有在高温状态下增加 A/B 解码负载。

后续若温度回落，仍需先准备并验证以下措施，再提供具体方案请求暂停授权：

1. 明确操作目标是后台进程的暂时冻结还是服务停止/重启，不能混用。
2. 独立的恢复程序，设置最长暂停时间；监测异常、数据不再更新、测试取消或主程序退出时立即恢复。
3. 在正常运行、临时暂停、恢复后都使用相同的传感器读取频率。当前读取约占 0.55–0.62 秒，必须把监测本身的影响纳入对照，不能直接与上轮无监测数字比较。
4. 运行相同 A/B 输入，记录原始 `0xC5` 数量、解码 P99 和最大值，同时核对温度、风扇和恢复状态。监测也会发起 WMI 读取，不能把它的请求误认成 GCUService 的管理请求。

本轮没有部署尚未验证的自动暂停/恢复程序。没有卸载服务、改固件、屏蔽通知或改电源模式。
