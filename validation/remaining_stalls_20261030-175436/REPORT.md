# 剩余停顿来源排查

已确认 AGENTS 文件，我将遵守要求进行开发。

本轮使用原始 A、B 视频离线回放，补充函数分段计时、分析线程的系统调用和内存记录，以及一次 Windows 系统记录。没有连接相机或操作 PZT，没有更改正式算法、数据库可靠性设置或 Python 自动清理规则。

## 已确认的具体来源

### 1. 首帧仍会临时读取 OpenCV 所需的文件页面

`host_A` 的首帧总耗时 **37.875 ms**，随后的视频第 1 帧被最新帧替换规则跳过。这里的帧号从 0 开始；数据库中的来源帧号分别为 274、275。

其中“生成候选区域”用时 **17.242 ms**，线程实际执行约 **2.471 ms**。这一步包含阈值判断和 OpenCV 闭运算，不能只把时间归给阈值比较。

本次已找到剩余时间的去向：

- 分析线程在 `227280.518104205` 秒停止执行，在 `227280.532893116` 秒恢复，间隔 **14.789 ms**。
- 调用记录落在 OpenCV 库内的文件缺页处理；等待栈为 `filemap_fault → folio_wait_bit_common`。含义是：需要的文件页面尚未准备好，程序等它读入。
- 同期 Linux 调度等待计数没有增加。因此这段长等待并非分析线程在 Linux 内排队等 CPU。
- 对齐后的 Windows 记录显示，WSL 的 `F:\WSL\Ubuntu\ext4.vhdx` 数据盘文件在此时有读请求完成，其中一笔读取耗时 **13.530 ms**。这支持“等待 WSL 文件读取”的判断。多个读取会重叠，不能把它们相加，也不能在缺少块地址映射时声称某一笔请求完全等于该线程的全部等待。

另一组 `native_A` 的首帧独立出现同类现象：候选区域阶段发生一次需要文件读取的缺页，线程暂停 **2.944 ms**；跟踪阶段另外出现 7 次文件缺页。可见正式程序虽然已提前写入区域编号图，但仍未把首次调用所需的所有函数页面、计算空间准备完毕。

这次证据指向 **WSL 数据盘的文件页面读取**，不能把它写成此前出现过的“Windows 页文件读取”。二者是不同情况。

证据：`host_A/consumer_stalls.csv`、`host_A_0_candidates.window.txt`、`host_watch_A.jsonl`、`host_events_A_0_candidates.txt`；独立复现见 `A_0_candidates.window.txt`、`A_0_tracking.window.txt`。

### 2. 图像处理中仍有大数组需要临时准备内存

已复用区域编号图，不等于所有整张图大小的内存都已复用。当前仍有：

- `online_tracking.py` 中灰度图转为浮点图的 `astype`；本次输入为 1024 × 1280，每张浮点图约 **5 MiB**。
- `bubble_tracker.py` 的 `GaussianBlur` 没有指定已有输出空间，仍需取得一张约 **5 MiB** 的输出图。
- 候选区域的比较、类型转换，以及部分筛选临时数组；另有首次使用的暗度、筛选和输出空间需要实际写入。

并非每次申请数组都会向操作系统要新内存：分配器经常能复用旧空间。因此大多数帧正常，偶尔才出现准备新页面的额外工作。

本次直接抓到了运行中而非仅首帧的例子：

| 回放与视频帧号 | 平滑阶段耗时 | 无需读盘的缺页次数 | 直接记录到的工作 |
| --- | ---: | ---: | --- |
| native_B，2947 | 4.954 ms | 258 | 分配匿名内存页、建立映射、清零内存页 |
| host_A，606 | 5.787 ms | 769 | 同样进入页面分配及 `clear_page_erms` 清零 |

这两段没有需要读盘的重大缺页，也没有分析线程切出记录；它们确实包含内存准备工作。不能把全部 4.954/5.787 ms 都算作内存分配，里面还包含平滑计算和少量诊断开销，但“这一步除了算图像，还临时准备了内存”已有直接证据。

证据：`B_2947_blur.window.txt`、`host_A_606_blur.window.txt` 及对应 `consumer_stalls.csv`。具体调用包含 `do_anonymous_page`、`vma_alloc_anon_folio_pmd`、`clear_page_erms`。

### 3. 保存端仍可能等待磁盘确认，但这次没有拖住分析端

`host_B` 在视频帧 4859 对应的数据库提交中出现 **188.027 ms** 等待，保存线程自身仅消耗约 **0.240 ms** CPU 时间。

连续 18 个系统采样都显示它停在：

`fdatasync → ext4_sync_file → blkdev_issue_flush → submit_bio_wait`

也就是“要求磁盘确认数据写入，然后等待完成”。这段保存线程的 Linux 调度等待计数没有增长。证据足以确定它等的是磁盘刷新，不是排队等待保存线程开始工作，也不是 Python 自动清理。它不能进一步证明硬盘固件、宿主系统存储层分别占了多少时间。

与此同时，分析端完整处理了视频帧 **4860–4870，共 11 帧**。等待保存的记录最高达到 12 份，低于容量 32；随后全部保存完成。该组 7920 帧没有跳帧。因此这次 188 ms 是保存线程中的停顿，不能直接当作分析卡顿或跳帧原因。

数据库仍是 SQLite WAL、FULL 保存确认；未通过降低数据可靠性换取速度。

证据：`slow_save.json`、`host_B/writer_stalls.csv`、`host_watch_B.jsonl`、`host_B/writer_report.json`、`host_B/database_settings.json`。

## 另外一些毫秒花在实际计算和数组操作上

并非每个比平时慢的步骤都在等待磁盘或内存。此次也定位到以下具体工作：

| 回放与视频帧号 | 阶段与耗时 | 采样时执行的内容 |
| --- | --- | --- |
| host_B，5505 | 平滑，4.465 ms | OpenCV 平滑内部代码，以及复制数据的 `memcpy` |
| host_B，3129 | 跟踪，4.493 ms | NumPy 数组取值、调用及迭代器释放 |
| host_B，7883 | 深色核心筛选，3.628 ms | 浮点数阈值比较、字节数组比较、布尔交集 |

这些窗口没有 Linux 主线程重大缺页或切出记录。Windows 中可见少量 WSL 线程争用 CPU 的事件，但没有建立宿主线程与分析线程的一一对应，不能用这些事件强行解释全部时间。普通对象释放也不等于 Python 的周期性自动清理。

对应 `.window.txt` 文件保留了原始调用采样。本次能明确“当时在执行哪些操作”；没有记录到可用于精确区分 CPU 缓存、内存带宽、频率变化的硬件计数，不能再断言这些计算波动由某个后台程序造成。

## 隔离对照：提前准备是否有帮助

使用现有 `first_frame_diagnosis`，交替运行 3 组原设置和 3 组额外准备，每组使用 A 视频前 60 帧。

“原设置”已包含正式的区域编号图预热及开始前、结束后的主动清理，不是完全无预热。“额外准备”只在诊断中先执行一次现有分割及独立临时追踪器，正式背景、帧号和编号保持原值；没有把这项对照写入正式程序。

| 组别 | 原设置首帧 | 额外准备后首帧 |
| --- | ---: | ---: |
| 1 | 40.226 ms | 9.822 ms |
| 2 | 16.655 ms | 15.844 ms |
| 3 | 16.092 ms | 10.401 ms |
| 中位数 | **16.655 ms** | **10.401 ms** |

原设置首帧的无需读盘缺页数为 3107、2617、2595；额外准备后为 331、344、330。需要读盘的缺页只在原设置第一组出现 8 次。六组的正式轮廓、编号、事件、帧时间及开始/结束背景逐项一致。

额外准备本身需要约 12.1–13.7 ms，是把准备工作移到正式送帧之前，而非让工作消失。三组样本也不足以保证所有启动都不再卡顿；第二组仍有 15.844 ms 首帧。

另用同一真实画面，交替比较平滑函数每次取得输出空间与复用已写入空间，各 3 组、每组 500 次。输出逐像素一致。两种方法日常中位数都约 1.15–1.20 ms，复用并没有稳定提高日常计算速度；初次分配组缺页较多，后续分配组也被底层分配器复用了。不能把这个独立函数对照夸大为完整分析已经加速。

证据：`control_commands.json`、`first_cold_*`、`first_analysis_*`、`blur_buffer_check.json`、`blur_buffer_samples.csv`。

## 时间对应与证据边界

- Windows 与 WSL 的计时通过多次请求/回复建立对应，再插值匹配，不直接相减。往返时间中位数约 0.788 ms。
- 首帧关键窗口附近插值残差最大绝对值约 0.429 ms；整段残差最大约 6.866 ms，不能声称所有窗口都达到亚毫秒精度。这里只把 Windows 文件读取作为跨系统支持证据，14.789 ms 线程等待来自同一 WSL 时钟下的直接记录。
- Windows 记录自动停止成功，持续 162.513 s，没有丢失事件或缓冲；见 `host_capture/finished.json`、`trace_stats.txt`。
- `perf script --time` 对这份记录仍会输出窗口外的线程切换事件。因此报告使用再次按线程编号和时间筛选的 `.window.txt`，不以完整 `.txt` 中无关事件归因。
- 上轮的 10 个跳帧位置列于 `historical_gaps.csv`。上轮原始事件没有本次的系统调用、文件读取和调用栈记录，不能事后将它们逐个指定为上述某一原因。本轮确认的是当前代码中新重现的具体机制，而不是为旧事件补造证据。
