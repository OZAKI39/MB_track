# `0xC5` 触发来源检查

日期：2026-11-01，Europe/Zurich。只调查；没有连接相机或 PZT，没有修改正式实验程序、电源方案、服务、驱动或固件。

## 结论

**本轮抓到的通知，来源已定位到“机械革命电竞控制台”的后台程序 `GCUService.exe`。**
两次系统记录共捕获 58 次 `0xC5`，全部都能对应到该程序发起的 `AcpiTest_MULong::GetSetULong` 调用，随后固件执行 `\_SB.AMW0.WMBC`，Windows 收到通知并处理显卡独占操作。

这不再只是“某个后台程序可能有影响”：日志给出了调用者的进程编号，文件路径和签名也已核对。
但日志没有携带每次调用的输入参数，**尚不能把全部 58 次通知逐个认定为控制台内部同一个条件分支**。

独立对照进一步证明：**我们的 GPU 解码任务不是触发通知的必要条件。** 两段不运行测试视频的 22 秒窗口，仍分别出现 10 次和 6 次通知。

## 谁发起，谁处理

本机文件：`C:\Program Files\OEM\机械革命电竞控制台\UniwillService\MyControlCenter\GCUService.exe`。
版本 `1.0.2.70`，签名有效，签名者 `Uniwill Technology Inc.`。详见 [文件身份](gcu_identity.json)。

运行记录中的调用关系：

```text
GCUBridge.exe (PID 6704)
  └─ GCUService.exe (PID 10940): GetSetULong
       → WMI provider (WmiPrvSE.exe, PID 9320)
       → firmware: \_SB.AMW0.WMBC
       → ACPI notification 0xC5
       → Windows graphics management holds the adapter exclusively
       → GPU decode waits for that adapter
```

- WMI 事件本身由 Windows 服务进程写出；真正请求方要看 `ClientProcessId`，不能把事件的进程号误当来源。[微软说明](https://learn.microsoft.com/en-us/troubleshoot/windows-server/system-management-components/identify-cause-of-wmi-shutdown)
- 本机记录显示 WMI provider 为 `wmiprov.dll`。WMI 到固件 `WMxx` 方法的映射由 Windows 的 `Wmiacpi.sys` 机制负责；这部分的驱动职责来自微软文档，不冒充本轮逐层抓到的调用栈。[微软 WMI/ACPI 规范](https://github.com/microsoft/Windows-driver-samples/blob/main/wmi/wmiacpi/wmi-acpi.htm)
- 上一轮已经核实通知进入 `dxgkrnl!DpiAcpiEventCallback` / `DpiAcpiHandleAcpiEvent`，独占同一个显卡适配器后，解码线程在锁上等待。本轮再次用相同 Windows 时钟核对了这一后半段。[此前的调用栈证据](../gpu_host_cause_20261031-235434/REPORT.md)

## 程序为什么会发出这类设置

只读检查了安装在本机的 .NET 文件指令，未加载、执行或修改被检查的软件。程序二进制的 SHA-256 记录在下面的检查结果里。

发现一个明确的管理入口：

1. `InitCPUGPUConbineONOFFTimers` 创建 **1500 ms** 定时器。
2. `cpugpuCombineRunTimer_Elapsed` 在交流供电状态下读取 CPU 使用率；还有防止检查重叠的保护。
3. 使用率高于 **95%** 时累计计数，达到 3 后，可能发送 `WMICPUGPUCombineRunON`。
4. 使用率低于 **10%** 时降低计数，到 -1 后，可能发送 `WMICPUGPUCombineRunOFF`。
5. 使用率处于 **10%–95%（含边界）** 时，计数和“上次返回值”都清零。因此，之后再次进入低使用率状态时，代码可以再次发送 OFF，而不一定是 GPU 刚刚开始工作。

这里的 ON/OFF 是控制台的“CPU/GPU 联合运行”管理设置，**不是实验 PZT 开关，也不是直接关闭显卡**。

两种方法向 `GetSetULong` 发送的常量分别是 `0x0000050000000002` 和 `0x0000050000000001`。
本机固件中存在对应的 `WMBC → OEMG → CTAF` 路径：修改 `NPCF` 管理值，并向显卡设备 `PEG1.PEGP` 发出 `0xC5`。
这是具体的程序入口和固件发出位置；没有直接调用这些方法，也没有读写硬件寄存器。

依据：

- [定时器、判断分支及 WMI 指令](gcu_combine_methods.json)
- [CPU 采样函数](gcu_cpu_sampling.json)：从性能计数器读取值、限制到 100 并取整。
- [日志开关及辅助函数](gcu_cpu_log_methods.json)：该程序内部日志默认关闭；没有为本次诊断开启它。
- [此前只读取得的本机固件](../gpu_host_cause_20261031-235434/firmware/DSDT.dsl)：`WMBC` 约第 133612 行，`OEMG` 的 `0x0500` 分支约第 133708 行，`CTAF` 约第 132605 行。

本轮管理调用之间的间隔多为约 3、4.5、6 秒等，符合 1.5 秒定时检查的整数倍。但**时间规律与静态代码吻合，仍不等于已经记录到每次 CPU 读数、返回值及输入参数**。没有据此宣称所有通知都是多余的，也没有把它认定为 NVIDIA 驱动缺陷。

## 正常条件对照

顺序为：不增加解码任务 → 单路 A → 双路 A+B → 双路 B+A → 单路 B → 不增加解码任务。
每个视频按 60 FPS 完整运行 1320 帧；双路分别使用独立进程。每路均采用原来的 8 帧预热。
不增加解码任务表示我们没有运行测试解码，电脑原有桌面和后台程序仍在；不表示整个 GPU 完全空闲。

电源方案保持 Balanced，没有插拔电源或更改控制台设置；测量期间不轮询 NVML，以免显卡查询本身改变运行状态。
本轮没有人为提高 CPU 负载，也没有做“停止控制台”的对照。
诊断窗口中仍有日常后台活动；期间读取过少量只读配置，并安装了后续静态检查所需的小型 Python 工具。因此这些短测用于识别触发关系，不是完全隔离环境下的性能基准。

六个阶段内共 44 次通知；最后一个阶段结束后、系统记录停止前另有 2 次，均保留，不强行分配到阶段内。这次正式对照总共 46 次，前面的定位采集另有 12 次，合计 58 次；WMI 请求为 23 + 6 = 29 次，本次每个请求旁都出现两次 `WMBC` 和两次通知。尚未解释这次映射为何重复执行两次。

## 已排除与尚未确认

**本轮证据已排除：**

- 通知必须由我们的解码、WSL 通信或微泡算法触发：不运行测试视频时也出现，且调用者是控制台。
- GPU 解码负载越高，通知必然越多：短测未呈现这种单调关系；单路 B 只有两次通知，却出现最大的单帧等待。
- 本轮通知直接由 Intel 调节服务发起：捕获到的这些 WMI 请求，客户端均为 GCUService。没有把 Intel 服务间接影响系统状态的可能性也一并排除。
- 所有慢帧都是解码计算本身慢：上面这一帧有明确的 33.22 ms 等锁证据，但不能把其他未逐一核对的慢帧全归为同一原因。

**仍未确认：**

- 每次通知究竟对应控制台的 ON、OFF 还是另一项指令；ETW 没有包含调用参数和该程序当时读到的 CPU 数值。
- 两次固件方法执行为何对应同一次 WMI 调用；本轮看到事实，但没有追查映射驱动内部的参数处理。
- 为什么某次独占操作更长；这取决于当时需要暂停、恢复的显卡工作，不能据此直接认定驱动有缺陷。
- 其他条件下是否会经由固件 `_Q83/_Q84` 等独立入口触发。本次记录中没有这些方法，不能永久排除固件中的其他入口。
- 哪个受支持的控制台选项能够安全避免重复设置。本轮没有停服务或改设置，不能承诺一个尚未测试的开关有效。

**目前没有经过验证的安全消除办法。** 可以把本报告提供给设备厂商，重点核查控制台中 CPU 使用率跨越阈值后重复下发设置的逻辑。正式实验继续保留已经验证的 CPU 解码；仅迁移到 Windows GPU 解码已证明不能绕过显卡独占等待。不建议依据当前证据直接停掉整个控制台服务。
