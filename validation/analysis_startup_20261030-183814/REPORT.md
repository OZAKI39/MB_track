# 分析端启动预热：正式接入与验证

已确认 AGENTS 文件，我将遵守要求进行开发。

本轮已把资源准备接入正式逐帧分析模块。修改前、修改后各进行了 20 次独立进程启动，
每组包括 A、B 各 10 次，每次处理原始录像前 60 帧；随后完成 A、B 整段的原速回放
和完整结果对照。修改后 20 次启动的最慢首帧为 **14.708 ms**，本次均低于 60 fps
对应的约 16.667 ms。全部轮廓、编号、事件、帧时间和初始/最终背景核对一致。

这是离线软件验证，没有连接相机、AFG 或 PZT，也没有改变仪器和 Windows 配置。

## 正式流程改了什么

`OnlineProcessor.start(sample_frame)` 现在由实际执行图像分析的同一进程、同一线程调用：

1. 真正写入暗度图、区域编号图、筛选图、编号转换索引和输出编号图的全部空间，
   并刷新对应的背景计算缓存。构造时已有的编号图准备也保留。
2. 调用现有平滑、区域识别和追踪函数试跑 3 次。先用临时画面访问轮廓和形状路径，
   再使用已经取得的样例帧。没有提供样例时，使用由背景生成的临时画面。
3. 追踪只操作临时追踪器。正式背景不更新，正式追踪器不处理试跑帧，保存队列不接收
   试跑结果；完成后清空工作图，并检查背景、编号和帧状态保持初始值。
4. 丢开临时对象，执行原有的开始前完整清理。运行中的自动清理继续开启，门槛不变。
5. 写出准备就绪记录，返回后才允许开始正式送帧。

`paced_replay.py` 已传入原视频的第一张灰度画面，并保持以下顺序：

```text
创建分析模块 → 送帧端准备后等待 → 分析端预热和清理
→ 分析端报告准备完成 → 设置正式时间起点 → 发出开始信号 → 正式发送第 0 帧
```

试跑不会修改传入画面，也不会消耗它的正式帧号。开始时正式目标编号仍为 1。
重复调用 `start()` 不重复预热。换进程或线程调用分析会明确报错，避免在一个进程预热，
却把另一个进程当作已经准备好。预热失败或取消时，不设置起点、不发开始信号，
按原有异常收尾流程关闭保存线程并留下原因。

实际修改的模块：

- `microbubble_tracking/online_tracking.py`：正式预热、清空暂用结果、状态核对与准备就绪记录。
- `microbubble_tracking/paced_replay.py`：在开始计时之前调用分析端预热，并传入首帧样例。
- `microbubble_tracking/first_frame_diagnosis.py`：诊断入口沿用正式启动流程并记录预热结果。
- `tests/test_analysis_preparation.py`：增加结果隔离、不同输入格式、调用线程及失败/取消保护测试。
- `ONLINE_TRACKING.md`、工作区 `README.md`：更新实际流程与使用说明。

没有修改 `bubble_tracker.py`、`online_store.py`、`async_store.py` 的算法和保存规则。
没有增加关闭正式预热的日常开关，也没有再次开启逐帧线程扫描。

## 20 次独立启动的实测

两组均采用 Python 3.12.3、OpenCV 4.10.0、NumPy 2.2.6；分析运行在 WSL。
每次都是新 Python 进程，OpenCV 线程数均为 24，采用相同视频、背景、保存配置和计时方法。
按 A/B 交替顺序启动，修改前的 20 次全部完成后才改正式代码。首帧耗时是 `process()`
调用的完整经过时间，包括提交记录，不把后台写盘时间叠加进来。

| 视频 | 每种版本启动次数 | 修改前首帧中位数 | 修改后首帧中位数 | 修改前最慢首帧 | 修改后最慢首帧 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 10 | 16.604 ms | 12.776 ms | **40.586 ms** | **14.708 ms** |
| B | 10 | 15.175 ms | 9.571 ms | **17.933 ms** | **12.950 ms** |

首帧超过约 16.667 ms 的次数：A 从 5/10 变为 0/10；B 从 3/10 变为 0/10。
原设置本来就包含区域编号图准备和开始前完整清理，并非完全不预热的版本。

修改后这 20 次的额外分析准备耗时 **38.999–58.202 ms**，中位数 **43.570 ms**。
这些工作发生在正式计时前，不是让资源准备的成本凭空消失。先前 3 组诊断得到的
10.40 ms 是当时小样本的中位数；本次采用更大的重复启动样本，报告新的实测值，
没有沿用旧数字冒充正式结果。

原始逐次数据见 [startup_samples.csv](startup_samples.csv)，命令和退出状态见
`before_commands.json`、`after_commands.json`，每次运行的 `timings.csv` 保留前 60 帧数据。

这项隔离测试没有最新帧替换队列，保证每次都处理相同的 60 帧，便于严格比较算法结果。
下面另用实际送帧进程和替换队列检查完整回放。

## 完整原速回放

使用现有独立送帧进程、转换预热和内存复用、最新帧队列、异步数据库保存；没有开启
详细停顿探针。每段原始视频 1320 帧、约 22 秒。

| 视频 | 正式首帧耗时 | 全段处理中位数 | 全段最大处理耗时 | 处理/保存帧数 | 跳帧 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 10.655 ms | 9.180 ms | 13.707 ms | 1320 / 1320 | 0 |
| B | 10.158 ms | 8.794 ms | 12.937 ms | 1320 / 1320 | 0 |

两组均核实：准备就绪时刻早于正式计时起点，所有画面的发布时间不早于该起点；
真正第一张处理画面仍为视频第 0 帧。原有约 200 ms 的启动提前时间没有改动。
保存等待数量最高分别为 2、1，结束时均为 0，保存线程正常退出。

分析进程内存峰值分别约为 184.625 MiB、184.352 MiB。本轮仅覆盖完整单段和重复启动，
不据此声称已经完成新的数小时稳定性测试。

另有 `science_A`、`science_B` 两次不按原速等待的完整回放，用于检查普通逐帧入口
（没有传入预热样例，使用临时画面）的结果。其启动准备分别为 46.558、71.347 ms，
同样位于正式处理之前。这两组不用于原速性能统计。

## 软件检查与限制

相关测试 **191 项通过**，详见 `tests.log`。涵盖同步/异步保存、只读输入画面、灰度/BGR/
浮点输入、无样例启动、正式帧号缺口、结果一致性、预热失败、取消、重复启动及线程约束。
第一次检查有 2 项旧测试失败：旧断言把最后一次清空编号图的时刻当成构造时首次写入时刻；
现在预热还会再次清空工作图。测试已改为记录首次写入时刻，仍检查原有构造保证，
并增加正式预热的独立验证，之后全部通过。

这些是新进程启动测试，不是每次重启电脑，也没有人为清空系统文件缓存。此次观察到的
最慢值不是永久上界；系统以后仍可能回收内存页面或暂时不给分析进程执行时间。
预热也没有把所有逐帧临时数组改为持久缓冲。本轮完成的是把首次必要资源准备前移，
不能宣称已经消除所有运行中停顿或完成真实相机接入。

复核命令（项目根目录）：

```bash
.venv/bin/python -m pytest customer_workspace/microbubble_tracking/tests -q
.venv/bin/python customer_workspace/validation/analysis_startup_20261030-183814/audit.py
```

后续仍使用原有回放命令即可，新预热默认生效。直接使用接口时，应在实际分析线程中
显式调用 `processor.start(sample_frame)`，等待返回后再允许输入源正式送帧；没有样例可调用
`processor.start()`。不显式调用而直接 `process()` 仍兼容，但那次调用会包含预热时间，
不适合正式实时送帧。
