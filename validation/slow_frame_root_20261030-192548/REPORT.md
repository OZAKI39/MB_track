# 偶发慢帧：本轮检查结论

本轮已找到并通过临时暂停对照验证了一个具体干扰来源：**Windows 中的 VS Code 页面显示进程会短时大量占用计算资源，使 WSL 中同样的微泡计算变慢。最小化窗口并没有停止这个后台活动。**

这解释了本次复现的一类慢帧，不等于能够追溯此前每一次没有底层记录的慢帧，也不等于所有后台程序同时工作时都能保证每帧不超时。没有改动微泡识别规则、追踪规则、正式线程设置或仪器程序。

## 如何确认

1. 按原速度回放 A、B 视频，记录分析各步骤的耗时、线程实际计算用时、缺页、线程切换、Python 自动清理及保存队列，同时记录 Windows 的进程运行情况。
2. 先比较 OpenCV 24 线程和 1 线程。单线程仍出现慢帧，而且区域识别更慢，不能靠改成 1 线程解决。
3. 用户最小化所有 VS Code 窗口后再测。A 的 2640 帧未超时，但 B 的第 326、327 帧仍分别耗时 17.898、18.808 ms。Windows 记录显示，**Code.exe 的页面进程 PID 27244 在相应短时窗口分别消耗约 139.8、149.5 ms 的合计 CPU 时间**。这是多核相加的时间，约等于同时使用 8 个核心；不是把一帧持续时间算成 149.5 ms。
4. 经用户明确批准，临时暂停已验证为 `Code.exe --type=renderer` 的两个进程（27244、14412），其余分析、送帧、保存和系统诊断继续运行。暂停约 72.6 秒后，两个进程均成功恢复，恢复返回值均为 0。
5. 暂停期间重放完全相同的 A、B 内容。B 的同两帧降为 **8.888、9.521 ms**。对应 Windows 窗口中，被暂停页面进程的运行活动消失；保留的少量 Code.exe 活动来自未暂停的其他进程，例如界面图形进程。

前后都是带诊断的离线测试，OpenCV 24 线程、颜色转换 1 线程、背景、预热、内存复用、保存方式相同。下面比较的是完整运行结果，不挑选最快的几帧：

| 条件 | 视频 | 帧数 | 中位耗时 ms | P99 ms | 最慢 ms | 超过 16.67 ms | 跳帧 |
|---|---|---:|---:|---:|---:|---:|---:|
| 仅最小化窗口 | A，重复 2 遍 | 2640 | 9.445 | 12.291 | 16.050 | 0 | 0 |
| 暂停页面进程 | A，重复 2 遍 | 2640 | 9.366 | 11.844 | 13.762 | 0 | 0 |
| 仅最小化窗口 | B，1 遍 | 1320 | 9.307 | 12.479 | 18.808 | 2 | 0 |
| 暂停页面进程 | B，1 遍 | 1320 | 9.010 | 11.117 | 13.027 | 0 | 0 |

P99 表示 99% 的帧没有超过这个耗时。改善主要体现在突然变慢的尾部，而不是日常中位速度大幅提升。暂停不是正式运行策略；本轮只用它隔离原因，程序没有加入自动暂停其他应用的功能。

## 慢的时候程序具体在做什么

B 第 327 帧的 18.8 ms 中，平滑约 3.05 ms、相对暗度约 4.10 ms、区域筛选约 2.40 ms、追踪约 2.35 ms。底层记录采样到 OpenCV 图像计算、NumPy 除法/减法/阈值比较、数组读写和复制。

这几步是一起变慢的；同一原始画面在暂停干扰进程后恢复到约 9.5 ms，科学结果完全一致。因此，这一类波动不能解释成该帧突然多了需要识别的微泡，也不是保存队列把分析堵住。

在这两个关键慢帧窗口中：

- Linux 没有记录到缺页，主线程未发生强制切换；少量主动切换不足以解释主要增量。
- Windows 没有记录到硬盘回读或压缩内存恢复事件。
- 本轮正式运行区间内 Python 自动清理最长不到 0.1 ms，解释不了这些十几毫秒的波动。
- 保存线程正常工作，已提交的帧全部保存。

Linux 中“线程 CPU 时间接近实际经过时间”不能单独排除宿主系统影响。本轮使用了 Windows 记录和实际移除干扰的对照，没有据此断言是 CPU 降频、缓存失效、内存带宽或某个硬件故障。**干扰进程已定位；它通过哪一种硬件资源逐毫秒影响计算，本轮没有硬件计数器证据，不进一步冒充确定。**

## 另一个已查明的跳帧原因

`native_host24` 是一组带系统跟踪、重复 3 遍 A 视频的诊断回放，共送入 3960 帧、处理和保存 3959 帧，缺视频内编号 1321。

原因链条有完整时间记录：

- 循环开始的第 1320 帧包含重新打开视频和首次解码，耗时 **38.415 ms**。
- 该帧比计划晚发送 **22.382 ms**。
- 第 1321 帧随后很快到达；分析第 1320 帧本身只用了 **10.519 ms**。
- 第 1322 帧到达时，第 1321 帧仍在“只留最新帧”的交接位置，因此被替换并明确记录。

这是离线循环回放的重新打开视频/解码及追赶计划导致的缺口，不能归为数据库丢失，也不能冒充真实相机录像丢帧。本轮没有扩大范围修改循环回放策略。静止窗口和暂停进程的两组正式对照均无此缺口。

`native_host24` 的第 2503 帧还有一次 20.547 ms 慢帧，当时 vmmemWSL 的整体 CPU 活动异常增加；该时段与本助手额外启动 Python 查询 OpenCV 配置重叠。缺少所有 Linux 进程的逐线程跟踪，不能直接断言具体贡献，故**不拿这一帧证明 VS Code 的影响**。后续静止/暂停对照没有在回放期间启动此类配置查询。

## 数据和代码检查

本轮共送入 **23760 帧**，处理 **23759 帧**；这 23759 帧全部保存成功，唯一缺口如上。所有数据库完整性与外键检查通过，结束后没有未提交记录或保存积压。

`verification.json` 保存以下逐表、逐记录核对结果，全部通过：

- 单线程与 24 线程完整 3960 帧的轮廓、编号、事件等科学记录相同。
- 静止界面的 A 前 2640 帧，与同设置的原始重复回放一致。
- 静止界面的 B 与此前五遍复测中的 B 科学结果一致。
- 暂停前后 A、B 的所有科学数据表完全一致；只排除处理耗时字段，没有排除轮廓、编号、事件或输入时间。

代码只调整普通 `StallProbe` 的诊断行为：不再逐帧扫描线程目录，详细诊断仍保留该选项。正常运行原本就不开启该探针。同步补充了说明和针对性测试，16 项测试通过。`code_changes.json` 确认生产计算模块的哈希未改变，仅 `stall_probe.py` 改变。

没有连接真实相机、AFG 或 PZT，没有修改 Windows/WSL 内存配置、驱动、服务、Python 自动清理参数或正式线程数。临时 Windows 记录均已正常停止，页面进程均已恢复。暂停脚本只为本次已批准的隔离测试准备，未来不要未经确认直接执行。

## 时间对应与证据边界

Windows 和 WSL 的计时器没有直接相减。通过持续请求/回复记录把两侧时间对应起来，再匹配短时事件。三次系统记录无丢失事件；往返时间中位数约 0.75–0.77 ms。局部插值存在误差，整体留一校验绝对残差 P99 约 0.99–1.67 ms，少数更大。因此 Windows 窗口中的合计 CPU 时间应理解为近似关联量，不是物理级精确同步，也不能把某个 Windows 线程的等待逐一冒充为 Linux 分析线程等待。

主要证据：

- `verification.json`：每次帧数、保存、耗时、跳帧与科学结果校验。
- `host_comparison.json`、`quiet/host_comparison.json`、`paused/host_comparison.json`：Windows 短时 CPU 活动对比。
- 各运行的 `consumer_stalls.csv`、`source_stalls.csv`、`.gc.csv`：分项原始记录。
- `quiet/clock_mapping.json`、`paused/clock_mapping.json` 与 `clock_uncertainty.json`：对应方法、命令和误差检查。
- `paused/pause_finished.json`：确切暂停/恢复时刻和成功状态。
- 三次 `host_capture/host.etl` 与 `trace_stats.txt`：保留系统原始证据，均无丢失事件。
- `commands.json`、`host_commands.json` 及各阶段同名文件：实际运行命令。

首次 native A/B 记录使用的系统 perf 缺少用户栈符号解析，相关用户函数证据不从那两份记录作结论；后续 Windows 关联和静止/暂停对照使用项目已有的支持栈解析的 perf 工具。用户函数定位和暂停结论以这些后续记录为准。

## 对实际实验的含义

已验证的可规避因素是：正式采集和分析时，尽量避免 VS Code 中持续更新的大型聊天/结果页面与分析争用资源；最小化并不保证这些进程停止工作。独立终端运行实验、减少无关后台工作比改识别规则更符合这次证据。

本轮的暂停实验只有一组、总计 66 秒录像，不能据此保证任何系统负载下的每一帧都不会超时，也没有证明此前未留底层记录的所有慢帧都来自同一进程。原始视频和科学算法没有因此改动。
