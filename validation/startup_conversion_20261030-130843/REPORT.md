# 启动第 3 帧转换停顿的进一步追查

## 结论与证据边界

**同类启动停顿的具体热点已经查到：把视频帧转换成 BGR 彩色图像时，首次写入新的
输出内存，触发 Linux 分配并清零内存页。现有复用没有覆盖这块输出空间。**

本轮补测的第 3 帧有一次 10.198 ms 停顿：区间内 11 个原生 CPU 样本中，10 个
直接落在 `clear_page_erms`，剩余一个落在 NumPy 数组维度信息的准备上。
校准后的同一窗口及前后约 150 ms 内，没有记录到 WSL 的 Windows 硬缺页事件。
因此这一次补测的主要采样位置是新内存页准备，不能解释为页文件读取。

**原来 29.583 ms 的那一次，没有同步采集 Linux 调用栈和跨系统时钟校准，仍不能
把其中每一段时间精确归属，或确认其中完全没有 Windows 回页影响。** 原记录与
本轮补测、代码路径强烈支持上述内存准备机制，但 10.198 ms 不是原事件的精确重现。
本报告不把新补测的证据冒充原事件的完整现场。

## 原来 29.583 ms 的直接记录

来自 `memory_pressure_20261030-123155/background_off/run_2/replay/source_stalls.csv`：

| 项目 | 原始值 |

| 阶段 | `convert_bgr` |
| 起止计时 | 209192.853716856–209192.883299386 s |
| 总耗时 | 29.582530 ms |
| 线程 CPU 计时 | 29.987613 ms |
| 线程用户态 / 内核态计时 | 4.723 / 24.821 ms |
| Linux 新映射等软缺页 | 960 次 |
| Linux 磁盘缺页 | 0 次 |
| Linux 主动 / 被动线程切换 | 0 / 0 |

用户态、内核态和线程 CPU 来自不同计数接口、不同读取时刻，粒度也不同，不能要求
它们精确相加等于总耗时。它们表明这段耗时大部分记在内核，但原记录没有函数级证据。
Linux 的零磁盘缺页也不能单独排除 Windows 在虚拟机外部进行回页。

原来的 Windows ETL 还在。本轮导出了附近 75–80 s 的窗口，发现 64 条 WSL 硬缺页
记录；但这只是按墙钟大致定位的附近区间，不能与那 29.583 ms 精确配对。
对应记录见 [original_wsl_faults_75_80s.csv](original_wsl_faults_75_80s.csv)。
没有把附近所有读页时间加起来算给这张图，也没有直接相减 Windows 与 WSL 的计时器。

## 从实际代码找到的原因链路

本机 PyAV 为 19.0.1，实际安装代码及文件指纹记录在 `library_source_hashes.json`。

1. [`paced_source.py`](../../microbubble_tracking/paced_source.py) 中，每帧调用
   `frame.to_ndarray(format="bgr24", threads=1)`。
2. PyAV 的 `VideoFrame.to_ndarray()` 先执行 `reformat()`。线程内会复用转换器对象，
   **但复用的是转换设置，不是下一张输出图像的像素空间**。
3. `VideoReformatter._reformat()` 每次创建新的输出 `VideoFrame`，调用 `_init()`，
   由 `av_frame_get_buffer()` 申请输出缓冲区，再进入 `sws_scale_frame()` 转换。
4. 本轮原生样本明确显示：转换代码首次写入部分新内存时，进入
   `do_anonymous_page → 分配内存页 → clear_page_erms`。系统正在为这些新页准备并清零。
5. 原录像为 1280 × 1024，BGR 每像素 3 字节，输出大小正好是
   **3932160 字节，即 3.75 MiB、960 个 4 KiB 内存页**，与第 3 帧的缺页量一致。

为什么已有预热仍留有这个问题：

- [`paced_replay.py`](../../microbubble_tracking/paced_replay.py) 先在主进程读取首帧、
  准备背景，之后用 `spawn` 启动一个新的送帧进程。主进程准备过的这类工作空间
  不会因此成为新进程已经准备好的 BGR 输出缓冲区。
- 送帧进程只把第一次转换放在 `ready` / `start` 握手之前；后续帧仍会申请输出空间。
- 识别模块复用的暗度计算数组、区域标号数组属于另一部分，不能替代这块 BGR 空间。
- 运行中内存分配器可能复用已准备过的页，也可能再次使用新页；因此问题更容易在
  启动出现，但不能承诺永远只影响前三帧。

## 8 次带原生调用栈的启动补测

使用完全相同的 Exp. B 原录像、参考背景、算法及保存方式。每次新启动现有回放
程序，送入前 60 帧；转换 1 线程、分析 24 线程。PZT 记录只读，不连接设备。
Linux perf 从进程启动前开始记录，频率为 999 Hz。它会增加诊断开销，因此以下
耗时用于定位，不用于宣布新的正式运行速度或优化幅度。

第 7 次关键证据：

- [原生调用栈](run_07_slow_native.txt)：11 个区间内样本，10 个位于内存页清零，
  最后一个为 NumPy 的维度信息准备。采样比例不是逐函数精确耗时账单。
- [时钟对应](clock_mapping.json)：实际转换对应 ETW 约 30.210785–30.221000 s。
  前后两次请求的往返时间约 1.34 / 1.19 ms；附近插值检查误差最大约 0.12 ms。
  全记录插值检查最大误差约 3.56 ms，这些都是实测检查，不是物理同步保证。
- [Windows 窗口明细](run7_wsl_faults.csv)：以该区间前后各约 150 ms 导出后，没有
  `vmmemWSL` 硬缺页记录。原始 ETL 本身报告零丢失缓冲区、零丢失事件。
  这排除了该窗口中**被记录的页文件回读**作为主要解释，但不能排除未记录的
  Windows 内部内存准备或宿主机调度影响。
- 第 1、2 次较短的启动转换，也在原生样本中看到相同的新内存页处理路径。

## 完成与未完成

- 8 次启动均正常完成，共送入 480 帧、分析并保存 476 帧；4 帧分析跳过有记录。
  所有已提交记录都已保存，8 份数据库快速完整性检查均通过。
- 输入文件和分析代码指纹与原来 29.583 ms 那轮一致，见
  [verification.json](verification.json)。没有修改识别算法、正式送帧或保存流程。
- 新增的是本目录的诊断采集脚本、两端时间校准和分析记录；Windows 采集已停止，
  未修改 WSL 配额、页文件、交换空间、驱动、服务或仪器设置。
- 原生导出提示有 1 条乱序事件，保留该提示；没有将采样未看到的路径断言为绝不存在。
- 最初一次旧 ETL 导出未等待子进程完成，随后重试；第一次窗口参数误按秒填写，
  得到只有表头的结果。之后改用微秒范围重新导出。前两份空导出没有用于结论，
  日志保留，原始 ETL 未修改。

下一步若处理这个问题，应针对**真正的送帧进程中的 BGR 输出空间**做提前准备和复用，
并验证输出像素一致。仅在主进程提前读一张图，或仅复用后面的识别数组，不足以保证
后续 BGR 转换不再首次准备内存。此轮是诊断，没有提前实施这项改动。

对原来 29.583 ms 的严格逐项分解仍受限于当时未采集的现场，事后无法补回；本轮已将
可复现的具体内存处理路径与其在现有代码中的触发原因分开确认。
