# 停顿原因排查

本次增加了可选诊断，没有改变识别阈值、追踪规则、正式线程默认值或保存可靠性设置。
使用现有 A/B 原视频，在 WSL 中离线回放；没有连接相机、AFG 或 PZT。
结论：停顿有多个来源。首帧首次使用内存的额外成本、部分线程等待和调度停顿有明确证据；
颜色转换的极端异常和一次长时间数据库提交已定位到函数，但底层原因尚未全部查清。

## 1. 首帧：预分配数组不等于内存已经准备好

正式分割使用 `np.empty` 创建工作区。这一步可以只预留地址；第一次真正写入时，
操作系统仍要把内存页交给程序。这里发生的是“软缺页”，不是从硬盘读丢失的图像。

在独立进程内，用同一张 A 首帧、同一个背景和原分割函数各做三次对照：

| 条件 | 第一次分割平均耗时 | 三次耗时 |
| --- | ---: | --- |
| 当前方式 | 13.750 ms | 12.626、13.924、14.702 ms |
| 事先写入两个暂用数组 | 10.465 ms | 11.043、10.181、10.172 ms |

只提前写入暗度数组和区域标号数组，没有修改背景、输入或阈值。第一次区域标号
从约 3.3–3.9 ms 降到约 0.8–1.2 ms。六次的标签和轮廓指纹相同；
每次继续对同一画面调用 12 次，结果也不变。

这确认了首帧慢的一个具体来源，但不能解释所有启动耗时。这是分割小实验，
不含视频送帧、完整追踪和保存，不能把 10.465 ms 当作正式整帧耗时。
证据：`kernel_24_cold_*`、`kernel_24_touch_*`、`evidence.json`。

## 2. 视频颜色转换：确实出现等待，但单线程不能解决全部异常

原送帧日志把读取、解码、转彩色和转灰度合成一个时间。现在分别计时。
确认解码线程数为 1，并不限制 `frame.to_ndarray(format="bgr24")` 的转换线程数。
已安装的 PyAV 19.0.1 在 `VideoReformatter.reformat` 中默认使用自动转换线程数；
`stream.thread_count = 1` 和 `cv2.setNumThreads(1)` 都不能替它完成这个设置。

无并行单元测试的 A 回放中，第 1001 帧颜色转换用了 **26.242 ms**：
主线程只用了 **0.488 ms CPU**，同进程合计 **29.155 ms CPU**，有一次主动等待。
这与主线程等待转换工作线程完成一致，慢点在转换步骤，而不是按时刻表等待或微泡轮廓计算。

不过，只限制颜色转换为 1 个线程后，B 第 89 帧仍出现 **157.147 ms** 的异常。
该次主线程 CPU 为 158.402 ms，未记录到线程切换或需要磁盘读取的缺页，
该时间段系统也没有新增交换分区读写、直接内存回收或内存压缩整理。
因此不能把全部异常归因于多线程等待、交换分区或磁盘读取。

后续把原生转换和数组获取拆开，并做 CPU 采样，但没有再次复现这次 157 ms 异常。
它已定位到 PyAV/FFmpeg 的转换调用，尚未确定其中是哪一条底层路径耗时。
CPU 采样环境也没有完整的原生调用栈展开支持；该采样不能证明此异常已被解决。

两种线程设置分别处理 A/B 全部 **2640 帧**，逐帧 BGR/灰度字节指纹及 PTS 完全一致。
测试选项保留，正式默认值未改。不能依据某一次最大值下降就宣布方案稳定。
证据：`probe_A_24_cauto_2/source_stalls.csv`、`probe_B_24_c1_1/source_stalls.csv`、
`conversion_A_*`、`conversion_B_*`、`conversion_cpu_report.txt`。

## 3. 操作系统调度：有一部分时间确实没有执行这段代码

`probe_A_1_cauto_1` 的源视频第 994 帧，读取/解码经过 **13.175 ms**，
主线程 CPU 只有 **5.173 ms**，记录到一次被系统强制切走，主动等待和缺页均为零。
它说明约 8 ms 的差额与线程未获得执行机会有关，不能算作算法多做了 8 ms 计算。
目前没有证据指定是哪一个其他程序或 Windows/WSL 宿主活动造成抢占。

分析程序全部改成单线程也没有改善整体：本次中位数 12.208 ms、P99 20.741 ms，
而 24 线程的两次干净 A 对照中位数约 9.9 ms、P99 约 14.1–14.5 ms。
不同回放跳过的帧略有不同，这里只用于否定“单线程必然更快”，不是严格优化收益验收。

## 4. 保存：一次长时间提交使队列确实满了

`probe_A_24_c1_1` 在提交第 1493–1496 源帧这一批记录时，
数据库提交等待 **1760.428 ms**，保存线程 CPU 仅 **0.252 ms**。
提交发生在独立保存线程，分析仍继续，待保存记录最终达到 32 条上限；
第 1525 源帧提交被明确拒绝，程序保存错误并停止。

此前已接收的 **1247 帧全部保存**，最终队列清空，无已接收但未保存记录。
这次是失败运行，不能计作一次完整通过。

另做低干扰的系统调用跟踪（strace 的 seccomp 过滤），确认正常保存路径实际进入
`fdatasync` 等待系统完成写入，所测最慢一次为 24.682 ms。
没有用这次 24.682 ms 冒充重现了前面的 1760.428 ms；前一次长等待尚不能进一步
分清是文件系统、虚拟磁盘、宿主存储还是保存线程被调度延迟。
保留 WAL/FULL 和原队列限制，没有以放松可靠性或扩大队列掩盖问题。

第一次不带 seccomp 过滤的 strace 跟踪明显干扰运行，并触发保存等待超时；
它仅作为失败诊断保留，不用于速度结论。证据：`storage_trace`、`storage_filtered`、
`storage_filtered_syscalls.log` 及失败运行的 `writer_report.json` / `writer_timing.csv`。

## 5. 自动内存清理：存在，但目前不能判作正式流程的主要原因

详细探针中，两次 Python 完整清理分别花了 14.658 ms 和 11.638 ms，
与追踪/提交阶段的长耗时精确重合。但是探针每帧新增诊断对象，本身可能提前触发清理。

为排除这一影响，又完整回放 B：只记录清理事件，不增加逐步骤诊断行。
正式处理时间内只有三次小清理，最大 **0.036 ms**。
另一次只在该诊断进程关闭自动清理，中位数/P99 为 9.954/14.493 ms，
没有比开启时的 9.797/13.421 ms 更好，两次都分析保存 1319/1320 帧。
所以没有修改正式清理设置，也不把详细探针中的清理次数当作正式程序的证据。

## 验证、范围和保留的疑点

- 现有及新增检查共 **73 项通过**。最初在子项目目录运行测试出现包导入失败，
  改用项目根目录的正式测试入口后通过；没有通过修改导入路径规避它。
- 一次完整 A 回放的 1320 帧、22041 条区域观测、编号、事件、轮廓字节、
  背景以及 PZT 对应文件，与上一轮同样完整输入的结果逐项一致。
  详见 `scientific_equality_A.json`；没有声称所有跳帧不同的回放输出也逐项相同。
- 本次多数运行仍有分析漏处理帧；没有实时相机/录像负载，不能据此承诺实机不掉帧。
- `probe_A_24_1` 启动时与单元测试有短暂重叠，保留原记录，但不用于干净性能比较。
- 上一轮 32.9 ms 的轮廓阶段停顿没有 CPU、缺页或清理记录，无法事后认定其根因。
- 157 ms 转换和 1.76 s 提交的底层异常仍未完全解释；需要在再次发生时抓取更底层证据。

后续最明确的小范围工作是把首次内存准备移到正式计时前，并继续单独检查转换和
持久化异常。不能只压缩识别算法平均耗时，就声称所有突发停顿已消除。

## 文件与复现

`run_summary.csv` 汇总每次完整/失败回放；`stage_summary.csv` 给出各步骤中位数、
P99、最大值及其帧号；`evidence.json` 保留数值和对照信息。
环境：WSL2 Linux 6.18.54.1、Python 3.12.3、NumPy 2.2.6、OpenCV 4.10.0、PyAV 19.0.1，
24 个可用逻辑 CPU。每次回放的输入校验、设置和代码指纹在该运行目录内。

在 `customer_workspace/microbubble_tracking` 中运行；输出路径应换成新的、尚不存在的目录：

```bash
../../.venv/bin/python paced_replay.py \
  --video data/raw/expA.mp4 --reference results/B_offline/background.npy \
  --pzt data/pzt/expA --output-dir ../validation/new_stall_run \
  --measure-stages --diagnose-stalls --opencv-threads 24

../../.venv/bin/python stall_diagnosis.py kernel \
  --video data/raw/expA.mp4 --reference results/B_offline/background.npy \
  --threads 24 --prefault --output-dir ../validation/new_first_frame_check
```

新诊断代码、旧结果和失败记录均保留。没有运行仪器控制、提交 Git 或推送 GitHub。
