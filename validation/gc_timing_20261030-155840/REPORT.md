# Python 自动清理时机对照

已确认并遵守 AGENTS 文件。本次使用当前 A 视频做离线对照，不改识别、追踪、保存规则，不操作相机或 AFG/PZT。正常回放的默认清理方式没有改变，没有永久关闭自动清理。

## 先查清清理了什么

独立对象审计发现，分析进程启动后约有 **56,247 个**被 Python 自动清理机制跟踪的对象，其中最老一组有 **53,077 个**。数量最多的是库函数、元组、字典、列表、类型和内部引用。这些大部分仍在正常使用，不是应该删除的垃圾。

一段完整视频的独立审计实际捕获 **66 个**待回收对象，类型是 44 个内部引用、8 个元组、8 个函数、2 个 JSON 编码器、2 个方法和 2 个字典。函数来源均指向 Python 标准库的 `json/encoder.py`。这些编码函数互相引用，需要自动清理机制处理。

另做最小复现：同一份数据，用普通紧凑 JSON 编码未捕获此类对象；用 `indent=2` 的排版方式捕获 **33 个**对象，类型和函数来源与实际审计一致。项目的启动配置和结束报告使用这种排版方式。没有为减少这些少量对象而改写现有报告格式。

证据：[对象审计](object_audit/gc_report.json)、[JSON 独立复现](json_cycle_check.json)。审计临时保留待回收对象供检查，会改变清理行为，所以审计运行不参与速度比较；结束后暂存对象已释放，原设置已恢复。

## 触发位置与真正工作量要分开

普通自动清理组再次记录到一次 **9.205 ms** 的最老一组清理，执行线程自身的 CPU 时间为 **9.151 ms**，实际回收数量为 **0**。
这次发生在回放帧 2640，整帧处理为 18.638 ms；之后的长测也在帧 2640 触发了
10.577 ms 的大范围清理，整帧处理为 19.690 ms，回收数量同样为零。

触发位置是 `online_store.py` 的 `snapshot_frame()` 在复制动作事件记录时构造列表和字典。它触发了累计分配计数的检查；不能据此说这份记录出了错，或把保存快照本身当作应删除的数据。

这次长停顿并不是在释放大量废弃图像。一次大范围检查即使最终没有找到可回收对象，也可能花费毫秒级时间。最老一组清理还涉及 Python 内部对象缓存的整理，不能把整个耗时仅算成释放多少字节。

Python 的循环引用清理与普通引用计数释放是不同机制。相关接口和分代规则以本机 Python 3.12 为准，参见 [Python 3.12 gc 文档](https://docs.python.org/3.12/library/gc.html)。

## 三种短测

每组用同一 A 视频连续回放三遍，约 **66 秒、3960 帧**。线程数、转换预热、内存复用、识别参数和异步保存设置一致。三组均保持自动清理开启，只在真正发生清理时记录事件，不逐帧扫描线程或对象。

| 方式 | 实验中最长清理 | 实验中最老一组清理次数 | 整帧中位数 | 整帧 P99 | 整帧最大值 | 处理并保存 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原自动清理 | 9.205 ms | 1 | 9.230 ms | 12.395 ms | 23.117 ms | 3960 / 3960 |
| 送帧前清理一次 | 0.043 ms | 0 | 9.249 ms | 12.585 ms | 21.950 ms | 3960 / 3960 |
| 启动清理并暂缓最老一组 | 0.042 ms | 0 | 9.178 ms | 12.797 ms | 23.816 ms | 3960 / 3960 |

三组均无跳帧。启动清理组的自动清理门槛仍为原来的 `(700, 10, 10)`；暂缓组仅临时改成 `(700, 10, 1000000)`，年轻两组仍自动清理，退出时恢复原值。

启动清理组在送帧前花费 **8.318 ms** 完成一次大范围清理；实验结束并等待保存线程退出后，再花费 **10.528 ms** 做收尾。这些时间单独保留，没有伪装成“没有发生清理”。

短测没有显示提高门槛的额外收益。因此后续长测选用更简单的“送帧前清理一次”，不改变自动清理门槛。收益集中在减少实验中偶发的清理停顿，整帧平均处理水平仍约 9.2 ms，也仍然存在其他原因造成的慢帧。

命令、顺序与代码校验值：[short_plan.json](short_plan.json)。

新增 `gc_replay_check.py` 独立离线入口，以及 `paced_replay()` 的可选诊断控制对象。正常入口不创建该对象、不安装其观察回调。设置只作用于当前分析进程，包含它的保存线程，不改变独立送帧进程。

完整自动检查 **152 项通过**。新增检查覆盖三种模式下的正常结束、Python 异常、取消；异常发生时已提交的 6 帧仍全部保存，保存线程退出，原清理门槛、开关和其他观察回调保持正确。还测试了收尾清理函数本身报错或被中断时仍恢复设置，以及重复关闭不覆盖报告。

另运行一次真实回放的中途取消检查：先临时把最老一组的门槛提高到 1000000，约 2 秒
后取消；已提交的 **120 帧全部写盘**，运行明确标记为 `cancelled`，门槛恢复为
`(700, 10, 10)`，自动清理保持开启，未遗留保存线程或未保存记录。

异常处理测试指可以执行 Python 收尾代码的异常或取消，不保证强制杀进程、系统崩溃或断电时也能执行收尾。未把尚在保存队列中的数据描述为已经写盘。

新文件 Ruff 检查、涉及模块的关键错误检查及 `git diff --check` 通过。所有参数仅用于离线对照，使用方法见 `microbubble_tracking/ONLINE_TRACKING.md` 的“自动清理时机”。

## 本轮结论

当前证据支持优先采用 **初始化完成后、正式送帧前清理一次，运行时保留原自动清理，
保存结束后再做收尾清理**。提高最老一组的门槛没有显示额外必要性，且只做了 66 秒候选
对照，未作为长时间推荐方案。

目前提供的是可重复执行的独立离线验证入口，正常实验代码的默认清理设置没有改动。
没有验证真实相机、录像及 AFG 同时运行的负载，也没有声称已经解决全部偶发停顿。
