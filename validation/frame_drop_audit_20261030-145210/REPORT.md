# A 视频 20 帧跳帧逐项审计

审计对象：`stall_retest_20261030-143551/expA/replay`。只读取这一次原始记录，没有用重新运行的结果替代现场，也没有修改正式送帧、识别或保存代码。

**直接原因已逐条确认：新帧正常到达时，旧的待处理帧尚未被分析端取走，单帧等待区按既定规则将它替换。20 次之前正在分析的那一帧均耗时超过 16.67 ms，其中一次明确由 Python 自动清理无用对象占用了 21.06 ms。其余事件定位到具体分析步骤和交接区间，但部分步骤为何在系统内部变慢，没有当时的底层记录，不能进一步猜测。**

## 如何保证不是猜测

1. `frame_outcomes.csv` 的 20 个 replaced 编号，与 `source_timing.csv` 中新帧实际记下的 `replaced_video_frame` 完全一致。
2. 这 20 个编号在消费者记录和数据库中均不存在；其余 3940 个编号在消费者、保存记录和数据库中逐项一致，数据库完整性检查为 ok。
3. 本次生产者和消费者均在同一 WSL 主机，使用同一个 perf_counter 时间基准；没有减去历史 Windows 时间。
4. 读取了执行时源码指纹，确认 `LatestFrame.put/take` 及诊断时间戳的含义与本次代码一致。
5. 覆盖决定没有单独打时间戳。它实际发生在发送端取得锁后、`slot_lock` 标记完成至新帧 `published_s` 之间。因此使用一个上下界区间，不把发布时间直接当成精确覆盖时刻。
6. 读取前后核对原始日志文件指纹，未改写原日志。详见 `verification.json`。

## 能明确指出的原因

### 1. 启动第一帧拖慢，随后两帧受到影响

- 回放帧 0 分析花费 **45.09 ms**，其中区域识别 35.52 ms。
- 候选区域阶段耗时 18.39 ms，分析线程 CPU 时间 3.43 ms，期间记录了 1 次 Linux 读盘型缺页；追踪阶段另有 7 次。能够确认首帧存在内存页面加载活动，但没有函数栈和文件地址，不能说这些读取具体来自哪个文件，也不能把全部时间都归为页文件读取。
- 帧 1 在实验计时 16.885 ms 发布，帧 2 在 33.891 ms 发布并覆盖它；帧 0 到 **48.485 ms** 才完成。
- 接下来帧 2 本身在等待区已经等了 15.80 ms，再分析 17.04 ms。帧 3 因这段延迟的延续，又在帧 4 到来时被覆盖。覆盖区间跨过帧 2 的分析结束边界，不能细分成“纯计算”或“纯交接”。

这证明，前述“图像转换预热已经完成”并不等于首帧完整识别也已完成预热。本轮没有进一步改动预热范围。

### 2. 第 2 遍原视频 3.150 秒：明确的 Python 内存清理停顿

回放帧 1508（原帧 188）分析共 33.16 ms：

- 整理并提交待存记录的计时为 **21.20 ms**。
- `consumer_stalls.gc.csv` 同时记录同一个分析线程（680408）的第 2 代对象清理，起止为 `215015.377414535–215015.398470633`，持续 **21.056 ms**。
- 这段清理完整落在 submit 阶段内；其前后的实际帧号和记录时间一致。
- 帧 1509 的发布时间为 `215015.381760007`，后续帧 1510 到来时，它尚未被取走。

因此，这一次多出的约 21 ms 有直接事件证据：**Python 在分析线程里集中清理无用对象，暂时没有继续处理下一帧**。这里的“整理并提交记录”发生在分析端，不能把它误称为保存线程等硬盘。数据库真正提交耗时另记在 writer 文件中。

### 3. 其余 17 次：分析耗时连续超过画面间隔，部分还被帧间交接推过了取图时限

这些事件之前的分析调用为约 17.61–32.19 ms，均大于一张新画面约 16.67 ms 的到达间隔。很多前一帧在开始分析前就已等待了 10–16 ms，所以不需要出现 100 ms 的大停顿，也会来不及取下一帧。

## 本次证据不支持归因于什么

- 20 次旧帧发布到替换帧发布之间为 **16.235–17.006 ms**，保持正常的约 60 fps 节奏，没有观察到这 20 个替换窗口中送帧突然密集挤在一起。
- 对应发送端 `slot_lock` 小段为 **0.030–0.126 ms**，没有长时间卡在这一段；它也包含标记读取等小段开销，不能冒充纯锁等待。
- 保存模式为异步，队列峰值仅 2 条，容量 32 条，未满。主线程在这些帧里的提交等待计时为 0，实际磁盘提交在保存线程进行。除已证实的内存清理外，20 个前帧的待存记录整理耗时均很短。
- 所有已分析帧均完整保存，没有数据库拒收或漏写。保存线程可能与分析共享系统资源，但没有证据把这些替换认定为“主线程等待数据库落盘”。
- 没有本次 WPR 或原生调用栈，不能继续把普通计数解释成“某个 Windows 应用造成了全部跳帧”。
