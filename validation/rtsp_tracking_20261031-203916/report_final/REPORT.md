# 模拟 RTSP 接入 Windows→WSL 正式链路

本轮已经接通并完成 A、B 各一段约 22 秒测试。录像与解码完整，已分析的结果全部保存，
每个帧数差异都能对应到具体记录。**两组各跳过 2 帧分析，因此尚未达到每帧都分析的 60 FPS 目标。**

没有连接真实相机或 PZT；识别、追踪、解码、内存复用、清理和数据库保存代码保持原样。
输入视频、背景、正式相机配置与 AFG 配置均保持原文件哈希，详见
[`unchanged_inputs_and_algorithms.json`](../unchanged_inputs_and_algorithms.json)。

## 1. 本次实际路线与修改

```text
Windows：F:\MB_camera_sim 中的 A/B 副本，以原速度循环发布 H.264
       ↓ 本机 RTSP / UDP
Windows：现有 parallel_camera.py，GStreamer 接收并分成两路
       ├─ 压缩录像 → 原 FFmpeg → WSL 目录 recording/video.mp4
       └─ H.264 压缩帧与时间、编号 → 原有进程管道
                                         ↓
WSL：现有 parallel_camera_bridge.py 解码与灰度转换
       ↓ 最新图像共享空间
WSL：原 OnlineProcessor 识别、追踪 → 原独立保存线程 → tracking.sqlite
```

本次没有使用 `--offline-video`，实际发起了 RTSP `OPTIONS / DESCRIBE / SETUP / PLAY / TEARDOWN`，
每组各一次 PLAY，所有控制响应均为真实的 `RTSP/1.0 200 OK`。
模拟服务器运行日志在 [`simulator/`](../simulator/)，Windows 录像写入原 WSL 路径
`\\wsl.localhost\Ubuntu\home\lzy\projects\new_microbubble_experiment\customer_workspace\validation\rtsp_tracking_20261031-203916\`。

原 Chronos 中继每次控制请求重新建立连接；MediaMTX 需要持续控制会话及完整视频路径。
本次只给 `RecordingRtspControl` 增加显式 `rtsp_url` 的持续连接支持，并让接收入口传入该地址。
未指定 `rtsp_url` 时仍走原来的 Chronos 方式，录像与识别规则没有改动。

两份独立测试配置是 `customer_workspace/configs/rtsp_sim_A.json`、`rtsp_sim_B.json`：

| 项目 | A | B |
| --- | --- | --- |
| 模拟地址 | `rtsp://127.0.0.1:8554/expA` | `rtsp://127.0.0.1:8554/expB` |
| Windows 接收端口 | UDP 5500–5501 | UDP 5500–5501，依次运行 |
| 背景 | 已验证的 `camera_tracking_20261031_final/background_A.npy` | 同目录 `background_B.npy` |
| 分析参数 | 原设置，OpenCV 24 线程，详细诊断关闭 | 同左 |

Windows 只传压缩帧给 WSL，不在本轮新增完整图像跨系统传输。

## 3. 具体跳帧及原因

帧号从 0 开始；下表“录像帧号”对应本次保存的视频，“接收编号”对应 Windows 接收记录。

| 测试 | 录像帧号 | 接收编号 | 录像时间 | 上一帧分析用时 | 本帧到下一帧的发布间隔 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 426 | 518 | 7.100 s | 22.992 ms | 7.449 ms |
| A | 1076 | 1168 | 17.933 s | 14.155 ms | 7.718 ms |
| B | 398 | 490 | 6.633 s | 12.449 ms | 6.176 ms |
| B | 498 | 590 | 8.300 s | 16.177 ms | 9.545 ms |

这四次都是：上一帧尚在分析，下一张和再下一张画面先后准备好了；现有“只保留
最新画面”规则把中间一张替换掉。下一张更新画面发布后，上一帧分析还分别继续了
0.859、0.510、4.506、1.163 ms。所有差值都使用 WSL 自己的时钟，没有混减 Windows 时钟。
逐帧去向和替换计数恰好相符，所以这四张画面都能明确归为分析等待处的替换。

这说明平均分析用时小于 16.67 ms，也不保证每帧都会处理：实际解码完成、发布的
间隔会有波动。本轮不修改等待队列或识别算法，也没有为了通过验收补做丢掉的帧。
完整明细见 [`gap_details.csv`](gap_details.csv)。

| 软件延迟上界最大值 | 55.195 ms | 63.996 ms |

P95 表示 95% 的记录不超过该数值。“软件延迟上界”把 Windows 端的等待时间、WSL
取帧往返时间以及 WSL 收到后完成分析的时间合在一起，是现有程序的保守估计。
它不是纯通信时间，也不是从相机曝光到结果的精确延迟；本轮没有直接相减两套系统的计时器。

## 5. 画面与追踪结果一致性

- 保存视频的 1320 帧解码像素，逐帧与原始 A/B 的循环序列一致。
- A 从原视频第 273 帧开始，本次录像第 1047 帧循环回原第 0 帧；B 从原第 1183 帧开始，
  本次第 137 帧循环回原第 0 帧。源视频对应表见 `*_source_mapping.csv`。
- 使用保存录像中的同一批实际分析帧、同一背景和原始时间记录，重新调用现有离线核对工具。
  两组各 1318 帧的轮廓、编号、速度、事件、输入时间及编号更新记录逐表相同；只排除运行耗时字段。
- 此处重跑是结束后的核对，未把这些额外计算混入实时结果或分析帧数。
- 录像重复播放产生的末尾→开头突变只是模拟素材边界，不能当作真实微泡运动、融合或动作响应。

两组的 `equivalence.json` 用保存录像重跑同一批帧；原始素材与保存录像的独立像素核对
由本报告另行完成，避免用视频和自身比较来冒充原始素材核对。

## 6. 警告、收尾与范围

两组 Windows 标准错误日志都包含 `giolibproxy.dll` 无法加载的提示。已确认文件本身
存在，且在隔离进程中直接加载也失败；暂加一个依赖搜索目录仍未解决，说明不能简单
断言是该 DLL 文件缺失。具体未满足的加载依赖尚未完全定位，本轮未修改已安装环境。
记录见 [`dll_loading_check.json`](../dll_loading_check.json) 和每组 `windows_stderr.log`。
该提示没有阻止本次本机接收、录像、解码、分析及正常收尾，不能据此声称所有其他输入环境也无影响。

模拟源、Windows 接收进程、WSL 解码进程和保存线程均已结束，未遗留本次后台进程；
Windows UDP 5500–5501 已释放。RTSP TEARDOWN 均得到 200 OK。
54 项相关测试通过，新增/修改代码的 Ruff 检查通过。

**本轮完成：** 正式链路联通、录像完整、已分析结果全部保存、所有帧数差异有记录，
并且同帧输入的科学结果与离线一致。**仍未达到：** 60 FPS 每帧都分析；另有上述 DLL
启动警告未修复。每个素材本轮只运行一次 22 秒，不把该结果扩大为长时间运行保证。
真实相机网络、现场成像和 PZT 联合运行不在本轮范围，没有进行这些实机测试。
