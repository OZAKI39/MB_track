# 第二步：转换内存复用

日期：2026-10-30。

**已实现，并通过现有两段原视频的像素核对。** 发送端把彩色、灰度转换结果直接写入
启动时准备好的固定空间；复制给共享等待区后才允许覆盖。当前路径只需一组转换空间，
无需人为增加双缓冲或三缓冲。正式帧号、时间对应和识别规则保持不变。

同一录像、两组均预热 8 次的对照中，彩色转换中位数从 **1.043 ms 降到 0.608 ms**，
P99 从 **2.181 ms 降到 0.946 ms**。复用组累计检查 6000 次正式转换，未观察到超过
10 ms 的彩色或灰度转换。但本批原路线也未重现此前数十毫秒的停顿，不能据此保证
以后绝不会停顿，或宣称所有在线分析都已稳定无跳帧。

## 内存到底由谁使用

现有 WSL 回放路径是：

```text
发送进程的固定彩色图 → 固定灰度图
                            ↓ 同步复制，在原有锁内完成
                       共享等待区
                            ↓ 同步复制，在原有锁内完成
                    追踪进程自己的图像
```

发送端只在共享等待区复制完成之后，才把这组转换空间标记为空闲。
追踪进程处理的是自己的副本，不会被下一张画面覆盖。
如果等待区中的旧帧还未被取走，新帧仍按既有“只保留最新画面”的规则替换它，并记录缺帧；
这与覆盖消费者正在读取的图像是两回事。

当前实际同时占用转换空间的只有一帧，因此发送端准备一张彩色图、一张灰度图即可。
共享等待区另有灰度存储，追踪者另持自己的副本，**不是整个系统只用一块内存**。
异步保存线程收到的是独立的轮廓、位置、编号和事件快照，不保存转换图像的视图。

本轮没有让录像程序持有这组空间。未来如果增加会异步读取图像的录像或网络分支，
必须先取得独立副本，或明确登记借用并等待所有读者完成后归还；届时再根据实际同时
持有的帧数决定数量，不能直接复制当前的“发送后即可归还”条件。

## 具体实现

- 新增 `microbubble_tracking/frame_conversion.py`：管理固定彩色/灰度空间及借用状态。
- `paced_source.py`：保留启动预热，使用固定空间转换，在 `LatestFrame.put()` 复制完成
  后归还；取消或出错时也执行收尾。
- `paced_replay.py`：默认 `--conversion-memory reuse`；`allocate` 是本轮原路线对照。
- `ONLINE_TRACKING.md`：补充运行方法、内存归属、限制和结果字段。

PyAV 当前的转换接口会新建目标图像，没有传入目标空间的参数。新路线使用它已加载的
同一套 FFmpeg，通过公开的 `sws_scale` 接口指定目标平面；没有修改 PyAV，也没有加载
另一套系统转换库。灰度仍使用 OpenCV 原有转换，只增加 `dst` 指定固定目标空间。
接口依据见 [FFmpeg libswscale 文档](https://www.ffmpeg.org/doxygen/8.0/group__libsws.html)。

图像空间由 PyAV 按 FFmpeg 要求分配，保留对齐和行跨度；NumPy 只建立视图。
没有猜测 `AVFrame` 的内部结构，没有把仍在读取的解码图像当成可覆盖输出。
同一份原始图像仍按彩色到灰度的相同像素结果进入识别。

防止误用的检查：

- 上一帧还在使用时，再次转换或关闭转换器会报错，不覆盖旧画面。
- 另一线程不能使用这组空间。
- 每次启动用真实首帧与原 PyAV 输出逐像素比较；不一致就停止。
- 图像尺寸、格式、色彩空间或范围中途改变会报错。
- 不支持的输入明确停止，不静默切回旧路线后仍称为“已经复用”。

当前验证范围是 Linux/WSL，现有 A/B 视频的 `yuv420p`、未指定色彩空间/范围输入。
使用环境为 Python 3.12.3、PyAV 19.0.1、libswscale 10.1.102、OpenCV 4.10.0。
Windows 相机端尚未部署或验证本轮改动。

## 同条件速度对照

12 对独立启动，每对都使用实验 B 的前 60 帧；两组均保留 8 次预热。
每对的运行先后顺序交替，转换线程数为 1、解码线程数为 1、分析线程数为 24。
每组 720 帧。没有同时运行 WPR、原生栈采样、其他性能基准或真实设备任务。

| 正式彩色转换 | 预热 + 每帧申请空间 | 预热 + 固定空间复用 |
| --- | ---: | ---: |
| 中位耗时 | 1.043 ms | 0.608 ms |
| P99 耗时 | 2.181 ms | 0.946 ms |
| 最长耗时 | 5.054 ms | 1.330 ms |
| 超过 10 ms | 0 / 720 | 0 / 720 |
| 轻微缺页次数合计 | 303043 | 14 |

| 正式灰度转换 | 预热 + 每帧申请空间 | 预热 + 固定空间复用 |
| --- | ---: | ---: |
| 中位耗时 | 0.696 ms | 0.554 ms |
| P99 耗时 | 1.698 ms | 1.018 ms |
| 最长耗时 | 2.522 ms | 1.934 ms |
| 轻微缺页次数合计 | 91200 | 0 |

轻微缺页表示访问内存页时系统还需要完成准备，**不能等同于读取磁盘或 Windows 页文件**。
复用结果显示这部分工作在正式转换期间已大幅减少。没有本轮 WPR 明细，不能据此
宣称 Windows 页文件读取减少了多少。

每次完整转换准备时间（含空间准备、首帧核对、预热）的中位数：
原路线 13.060 ms，复用路线 12.670 ms。这些工作都在正式计时之前。
前 5 帧彩色转换的最大值为原路线 2.237 ms、复用路线 1.330 ms。
本批没有复现旧记录中的 76.6 ms，不能直接拿那个历史数字作为本次对照的最大值。

## 完整录像及连续运行

| 检查 | A 完整录像 | B 连续重复 3 遍 |
| --- | ---: | ---: |
| 计划时长 | 约 22 s | 约 66 s |
| 正式送入 | 1320 帧 | 3960 帧 |
| 实际处理并保存 | 1319 帧 | 3959 帧 |
| 等待区被替换 | 1 帧 | 1 帧 |
| 过期帧 | 0 帧 | 0 帧 |
| 彩色转换中位数 | 0.595 ms | 0.583 ms |
| 彩色转换 P99 | 0.889 ms | 0.872 ms |
| 彩色转换最大值 | 1.556 ms | 5.897 ms |
| 灰度转换最大值 | 1.633 ms | 5.864 ms |
| 保存队列峰值 | 7 帧 | 2 帧 |

B 的重复是同一录像的负载检查，使用明确标记的虚拟回放时间，**不是三次新实验**。
每张画面仍保留原始录像轮次、原帧号、原视频时间及历史 Windows 时间。

短时对照中，原路线处理 720/720 帧，复用路线处理 719/720 帧；复用组有 1 帧被替换。
所以不能把转换加速说成整条分析链已不跳帧。所有 26 次运行的送帧去向均可核对，
已提交记录全部保存，停止时待保存数量为 0，数据库完整性检查通过。
没有因复用发生旧图像被新内容覆盖的问题；实时分析原有替换机制仍存在。

66 秒检查中，发送进程内存从约 122.2 MiB 到 131.2 MiB，最后 20 秒维持在
131.230–131.234 MiB；追踪进程从约 151.7 MiB 到 184.4 MiB。
整个进程还包含解码器、分析和记录空间，不能把这些变化全算成转换空间泄漏，
也不能说内存从启动起完全不增长。固定转换空间的地址在像素核对中全程保持一致。
66 秒范围内没有持续增大的保存积压，更长时间运行尚未验证。

## 像素、安全顺序和软件检查

完整处理 A/B 两段原视频，共 **2640 帧**，逐帧核对：

- 彩色图每个像素与原 PyAV 转换相同。
- 灰度图每个像素与原 OpenCV 转换相同。
- 原始视频时间及色彩说明未被改变。
- 彩色、灰度空间地址始终固定。

测试中专门让消费者停在上一张图像的读取阶段，同时发送端连续转换并发送后续画面。
消费者保留的旧图像和原帧号不变。还检查了未归还就覆盖、跨线程使用、输入变化、
转换失败、关闭后再用、启动像素核对失败及取消收尾。

**108 项测试通过**，其中 16 项为本次固定空间检查；修改文件通过 Ruff，
`git diff --check` 通过。没有修改检测/追踪算法，没有修改真实设备程序、驱动或系统配置。

## 使用和记录

原来的回放命令默认已经启用复用，例如在 `microbubble_tracking` 目录运行：

```bash
../../.venv/bin/python paced_replay.py \
  --video data/raw/expB.mp4 \
  --reference results/A_offline/background.npy \
  --pzt data/pzt/expB
```

做原路线对照时增加 `--conversion-memory allocate`。
`--conversion-warmup-iterations 0` 只关闭额外重复预热，复用模式必需的空间准备和
首帧核对仍然执行。

| 文件 | 内容 |
| --- | --- |
| `comparison_summary.json` | 性能统计、26 次保存核对、连续运行内存 |
| `commands.json` / `progress.json` | 实际命令、顺序、逐次结果 |
| `pair_*/source_stalls.csv` | 每帧原始计时与缺页计数 |
| `*/source_report.json` | 运行状态、固定空间大小/地址、转换库及准备时间 |
| `expA_pixels.csv` / `expB_pixels.csv` | 每帧像素指纹、视频时间与固定地址 |
| `pixel_identity.json` | 两段输入文件来源、指纹与核对结果 |
| `full_A_reuse/` / `long_B_reuse/` | 完整运行、缺帧去向和保存记录 |
| `environment_before.json` / `environment_after.json` | Windows/WSL 环境快照 |
| `tests.log` | 108 项测试输出 |

本轮仍是软件回放，不包含实时相机接收、压缩录像或 AFG 动作负载。
解码、追踪进程取自己的副本、保存和系统调度仍可能耗时；它们不属于本次固定转换空间的
覆盖范围。下一步若接入实机，应核对相机接收和录像的实际内存归属后再部署，不能假定
这次软件回放的归还条件自动适用于异步录像。
