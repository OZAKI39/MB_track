# 识别停顿与帧间交接：进一步诊断结果

本次已确认 AGENTS 文件，并按要求开发。使用原 A 视频离线回放，新增可关闭的细分计时，结合 Linux 函数采样、Windows 线程调度和内存读取记录。没有改变识别阈值、数学运算顺序、编号规则或数据库的安全写入设置。

**结果：不能把所有停顿归为一个原因。这次分别抓到了 Windows 侧等待 CPU、临时数组触发内存分配和清零、Python 集中清理对象，以及诊断记录自身的交接开销。**

这里解释的是本次重新抓到的现场。之前那次 20 帧跳帧的原记录仍然保留；不能用新运行的事件替代过去缺失的现场，逐一认定那 20 帧都具有相同底层原因。

## 1. 数组除法突然变慢：抓到了 Windows 侧的 CPU 等待

Windows 联合记录组，回放帧 **187** 的相对暗度除法耗时 **11.012 ms**。

- Linux 底层样本落在 NumPy 的 `FLOAT_divide_AVX2`，期间没有记录到 Linux 的线程切换或读盘型缺页。
- 但该步骤内的两次连续函数样本之间，出现 **7.839 ms** 的空档。只有 Linux 的“线程 CPU 时间约等于总时间”，不能排除宿主 Windows 让 WSL 暂停运行。
- Windows 的调度记录显示：`vmmemWSL` 的线程 **18300** 于本次记录开始后 **5.987532 s** 被换下，当时状态为 **Ready**，即有工作要做、等待 CPU；直到 **5.995092 s** 才继续运行，中间 **7.560 ms**。
- 换下它时接替运行的是 `System` 的线程，优先级为 8；该 WSL 线程当时优先级为 1。这是实际调度记录，本次没有修改任何进程优先级。
- 同一段约 11 ms 内，Windows 有 **124 个 CPU 样本**落在 `RtlDecompressBufferXpressHuff` 解压函数，分布在 **23 个逻辑核心**；另有 **60 次、合计 16,769,024 字节**的读取指向 EdgeWebView 的 `msedge.dll`。

**通俗解释：识别算到一半，Windows 正在忙着加载、解压浏览器组件，WSL 有工作却没有及时获得 CPU。不能把这段等待全部说成“除法本身需要 11 ms”。**

同一负载时段还有第二条独立证据：帧 185 后扫描线程列表的操作耗时 **9.080 ms**，对应 Windows 中同一 WSL 线程 **8.434 ms** 的 Ready 等待；Linux 在这段操作末尾才再次采到函数样本。说明宿主调度影响可以落在图像运算，也可以落在普通的诊断操作上。

精度边界：Windows 与 WSL 通过请求/回复校时，没有直接相减各自的计时器。校时往返时间中位数 **0.763 ms**，全程相邻校时插值残差 P99 为 **0.420 ms**；除法附近残差约为 **−0.044～0.037 ms**。这些是软件对应证据，不是硬件精确同步，也没有建立 Windows 线程与 Linux 线程的一对一映射。上述等待与采样空档及恢复时刻相吻合，支持宿主调度影响；不声称已经把全部 11 ms 逐微秒归账，也不据此猜测是哪个浏览器窗口或哪个用户操作启动了该组件。

## 2. 区域筛选突然变慢：生成新数组时重新准备内存

筛掉过小区域后，现有代码通过 `labels = remap[labels]` 生成重新编号的整幅图。这个分支只在确实需要删除小区域时执行，并非每帧都执行。

本次抓到：

| 回放帧 | 区域筛选时间 | Linux 新内存页面映射次数 | 底层现场 |
| ---: | ---: | ---: | --- |
| 3956 | 14.233 ms | 624 | NumPy 整数索引取数 → 页面分配 → 内存清零 |
| 6547 | 11.638 ms | 640 | 相同路径 |
| 4212 | 10.149 ms | 见原始记录 | 相同路径 |

函数栈中的链路是 `mapiter_get → do_user_addr_fault → do_anonymous_page → __alloc_frozen_pages_noprof → clear_page_erms`。这是重新准备内存的直接证据，不是根据总耗时猜测。

Windows 在这些对应时间段还记录到 `vmmemWSL` 回读 `pagefile.sys`。例如帧 6547 的区间内，同一 WSL 宿主线程有 3 次页文件读取，记录耗时分别为 **0.305、0.320、0.293 ms**。这证明 Windows 换页在本次仍有发生；它们不能简单相加后充当整个筛选时间，也不能把所有读取都强行对应到某一块 Linux 数组。

启动第 0 帧也有类似问题：连通区域标号阶段 **10.869 ms**，函数样本显示在分配并清零大内存页。此前做的是送帧端的图像转换预热，不能据此认为识别端的全部工作内存也已准备好。

**通俗解释：程序有时需要一张新的大“工作纸”，系统要先给它找空间、清空；有时还要从硬盘取回 Windows 管理的内存。这些准备工作让某一帧突然变慢。**

证据：[慢步骤及完整函数栈](host_correlated/analysis/slow_native_stacks.json)、[各时间窗口的 Windows 内存事件](host_correlated/analysis/host_windows.json)。

## 3. Python 集中清理对象：再次独立复现

原诊断方式组中，帧 **1322** 的记录提交步骤耗时 **10.116 ms**；同一个分析线程记录到 **9.964 ms** 的第 2 代垃圾回收，完整落在这个步骤内。

细分组、Linux 采样组、Windows 联合记录组也分别记录到 **13.136、8.950、10.144 ms** 的主分析线程垃圾回收。这个自动清理可以发生在不同操作期间，步骤名称不能代替真实原因。

**这是分析线程在整理不再使用的 Python 对象，并不是保存线程等待磁盘。** 上一轮已经确认的 21.056 ms 垃圾回收仍然成立，本轮补充了新的复现记录。

## 4. 交接的 1–2 ms 具体用在哪里

本次逐段记录了分析结束到下一帧取图完成的全过程，并核对每段起止时间首尾相接。正常等下一帧到来的时间单列为 `wait_for_frame`，没有冒充交接工作的成本。

不带底层采样的细分组，共有 **56 个不需要等待新画面的交接区间**，总耗时中位数 **1.021 ms**，最大 **1.905 ms**。

下面给出一个完整实例：回放帧 **2155 → 2156**，总共 **1.482 ms**。

| 操作 | 本例时间 |
| --- | ---: |
| 扫描本进程的线程列表，记录线程数 | 0.638 ms |
| 写细分诊断日志 | 0.351 ms |
| 复制下一帧图像 | 0.293 ms |
| 写本帧运行记录 | 0.104 ms |
| 进入取图锁 | 0.005 ms |
| 其他小操作：整理字段、标志处理等 | 0.091 ms |
| **合计** | **1.482 ms** |

**这 1–2 ms 主要是诊断与图像交接工作，不是一直卡在保存队列里。** 特别是“每帧扫描线程列表”和细分诊断日志，只在开启诊断时使用，并非正式识别算法必需。

也不能保证交接永远只有 1–2 ms：前文帧 185 的交接总长 **10.143 ms**，其中线程列表扫描遇到了 Windows 侧的调度等待。已经分别记录操作本身和宿主等待证据，没有把这个长尾隐去。

证据：[逐段交接表](analysis/handoff_intervals.csv)、`details/consumer_handoff.csv`、`host_correlated/replay/consumer_handoff.csv`。

全部为同一段 A 原录像按原播放速度重复回放，参数保持：分析 OpenCV 24 线程、图像转换 1 线程、转换预热 8 次、复用转换内存、异步保存、数据库自动检查点和 FULL 安全写入。

| 组别 | 回放帧数 | 分析并保存 | 等待区替换 | 分析中位数 / P99 / 最大值 |
| --- | ---: | ---: | ---: | --- |
| 原有诊断方式 | 3960 | 3960 | 0 | 9.306 / 14.317 / 29.969 ms |
| 新增细分计时 | 3960 | 3958 | 2 | 9.333 / 14.750 / 31.577 ms |

这些组用于定位原因，包含不同诊断开销和不同时间的后台负载，不能把跳帧数差异解释成算法优劣。共送入 **19800 帧**，**19791 帧**实际分析并保存，9 帧等待区替换都有记录，没有把它们算成已分析。

- 每组分析过的帧号与数据库逐项一致；已提交记录全部保存，结束时待保存数为 0，数据库完整性检查均为 `ok`。
- 原视频、背景参考和原帧时间表的文件指纹前后一致。
- **122 项测试通过**，包含开关细分诊断后轮廓和计算结果完全相同、交接时间闭合、长时间等待时诊断内存有界。静态检查结果见 `lint.log`。
- Windows 记录实际持续约 **138 秒**，正常停止，丢失事件和丢失缓冲均为 **0**；原始 ETL 已归档到本目录。没有修改 Windows 配置、进程优先级、仪器或相机设置。
- 初次尝试导出 Linux CPU 编号时，原采样未包含该字段，导出失败；失败日志保留，改用已有的函数和切换时间记录。当前 WSL 不支持所试的硬件 cycles/instructions/cache-misses 计数，未虚构这些指标。
- 完整 Windows 符号下载导出超过 160 秒后，停止了本次创建的导出进程；随后仅使用已缓存的内核符号成功生成 `kernel_window.txt`。这发生在采集结束后，没有混入实验时间。保留失败日志，没有结束用户的程序。

核对结果见 [verification.json](verification.json)，测试记录见 [tests.log](tests.log)。

## 6. 本轮改动及边界

新增 `--diagnose-details`，默认关闭；它把相对暗度、区域筛选和帧间交接继续拆开计时。`native_stall_watch.py` 可以明确选择分析线程作为采样对象；`stall_detail_report.py` 负责汇总并检查时间记录是否闭合。使用方法已写入 `ONLINE_TRACKING.md`。

本轮目标是查原因，没有将关闭系统功能、提高进程优先级、减少保存可靠性或改变识别规则作为“解决办法”。偶发跳帧尚未消除。下一步有依据的方向是减少识别中的临时整图数组、在正式实验关闭高频诊断扫描，并避开运行时启动占用大量 CPU/内存的后台任务；这些优化仍需要分别验证。
