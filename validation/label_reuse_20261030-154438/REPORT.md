# 区域编号图的内存复用

已确认并遵守项目 AGENTS 文件。本次只修改区域筛选和编号图的内存使用方式，未改变识别阈值、轮廓规则、追踪参数、事件判断或数据库保存方式。没有连接真实相机或操作 AFG/PZT。

## 找到的问题与实际修改

生成区域编号图的函数是 `bubble_tracker.py` 的 `segment()`。

1. 第一次标号调用 `cv2.connectedComponentsWithStats()`，本来就通过 `labels=workspace.component_labels` 写入固定空间，这部分无需再改。
2. 后面的候选掩膜原本每帧 `np.zeros()`，现在使用固定空间，每帧先清空。
3. 绘制外轮廓后的最终编号图原本每帧新建。在线处理现在提前准备好这张图，确认上一帧用完后再清空和重写。
4. 像素面积筛选发现小区域时，原来的 `labels = remap[labels]` 会再生成一张完整编号图。现在按 64 行一段，将旧编号复制到固定的小工作区，用同一张映射表写回原图。

简单地写成 `np.take(..., out=...)` 并不能避免全部大块申请：本机 NumPy 仍会把整图的 `uint16` 编号转换为 `intp` 索引，试测出现约 10 MiB 临时申请。因此显式准备 64 行的 `intp` 空间，并逐段使用。没有缩小视野、忽略小区域或修改编号顺序。

使用 `mode='clip'` 是为了避免 `take` 默认异常保护模式的额外输出缓冲。这里的标签只来自本次绘制，值一定是映射表的合法下标，因此不会实际触发越界裁剪。相关接口行为见 [NumPy take 文档](https://numpy.org/doc/stable/reference/generated/numpy.take.html)。

对于当前 1280×1024 图像，固定候选掩膜为 1.25 MiB、最终编号图为 2.5 MiB、小段索引空间为 0.625 MiB，共约 4.375 MiB。这是固定空间换取更少的重复申请，不是承诺进程总内存会减少 4.375 MiB。

## 为什么不会覆盖旧帧

当前在线接口明确由单个分析线程依次调用。每帧顺序是：

`分割并写编号图 → 追踪读取编号图 → 更新背景读取编号图 → 提交独立保存记录 → 下一帧`

追踪留下的是独立像素坐标；保存队列接收的是位置、事件、状态和已经转成独立字节的轮廓，不会接收整张编号图。因而下一帧重写这张图时，上一帧的读者已经用完它。

普通 `segment()` 仍默认返回独立编号图，下一帧不会改变旧结果。只有显式提供 `labels_out` 才写入调用方给出的空间；在线入口使用自己的私有数组，不把它放到返回值或保存队列中。

- 小区域全部被剔除、无目标、贴图像边缘、填孔、超过 255 的编号、最后一段不足 64 行、非连续或只读输出等情况均有自动检查。

## 重编号单项耗时与申请内存

从 A/B 各取 12 张真实编号图，用明确的测试映射表比较原方法与复用方法。每张交错测试 20 次，两种方法各 480 个计时样本；逐次检查结果一致。只测试重编号步骤，输入恢复和结果比较不计入耗时。

| 方法 | 中位数 | P99 | 最大值 | 测到的临时申请峰值 |
| --- | ---: | ---: | ---: | ---: |
| 原来的整图索引 | 2.099 ms | 2.704 ms | 2.910 ms | 2,689,824 字节，约 2.57 MiB |
| 分段复用空间 | 0.889 ms | 1.148 ms | 1.604 ms | 736 字节 |

临时申请由 `tracemalloc` 另行测量，未混进计时；预先存在的工作区不算临时申请。该工具测的是可跟踪的 Python/NumPy 分配，不代表整个 OpenCV、WSL 或 Windows 都不再申请内存或换页。

原始计时：[remap_timing.csv](equivalence/remap_timing.csv)。测试代码为 `microbubble_tracking/label_reuse_check.py`。

## 使用与边界

正常使用 `OnlineProcessor` 不需要改变命令，默认使用新的固定空间；详细诊断依旧默认关闭。

本次已证实减少了指定步骤的大块临时申请、单项耗时下降、前后数据不变且两次真实速度离线回放完整保存。尚未验证连接相机、同时录像时的效果，也未证明整套系统更快或所有偶发停顿消失。本次没有修改其他图像计算或后台系统设置。
