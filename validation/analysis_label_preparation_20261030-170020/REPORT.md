# 分析端区域编号图正式准备：实现与验证

2026-10-30。已把区域编号图的提前写入接入正式 `OnlineProcessor` 初始化，不需要额外启动参数。本次仅处理这块工作内存，没有提前运行整个识别或追踪算法。

## 实际修改

`online_tracking.py` 在创建背景工作区之后，立即执行：

```python
self.background.workspace.component_labels.fill(0)
```

这块 `int32` 编号图原本就已申请并会跨帧复用；本次补上真正写入整块空间的步骤。当前 1024 × 1280 画面对应 **5 MiB**，没有再创建第二张同样大小的图。

构造成功返回之前完成写入。现有 `paced_replay.py` 的顺序为：

1. 创建分析模块，完成编号图写入。
2. 创建和启动送帧进程。
3. 等送帧端完成自己的图像转换准备。
4. 确定正式起点，发出开始送帧信号。

因此不用再增加一套线程或通信流程。写入失败时，构造直接抛出异常，送帧进程不会创建或启动。

`session.json` 和数据库会话信息新增 `startup_preparation`，记录准备成功、空间大小、写入耗时及完成时间。时间来自分析主机的 `perf_counter`，只用于核查软件启动顺序，不表示相机曝光时间。

没有调用 `segment()`、`Tracker.step()` 或背景更新，没有生成测试轨迹；正式背景、首帧编号和时间、微泡起始编号保持原规则。后续仍复用同一张编号图，普通运行不启用逐帧详细诊断。自动清理设置也没有改变。

独立的 `first_frame_diagnosis.py` 已补充说明：其中 `cold` 现在表示“不额外准备”，仍包含正式入口默认执行的编号图准备，避免以后误把它叫作旧版未准备基线。

## 仍需明确的边界

这次修复的是区域编号图的首次写入。输入格式转换、平滑、其他临时空间以及系统等待仍可能带来首帧开销，所以不能保证每一帧都低于 60 fps 对应的 16.67 ms，也不能保证后续永不跳帧。

预先写过内存也不是把内存永久锁定；如果之后系统内存压力很大，仍可能再次发生页面调入等待。本次没有更改 Windows 或 WSL 内存配置，没有关闭交换空间或自动清理。

代码已进入正式逐帧处理入口。真实相机、录像、AFG/PZT 联合运行和 Windows 部署未在本次执行；此次只做用户指定的内存准备修改及离线验证。
