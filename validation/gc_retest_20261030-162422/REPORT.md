# 自动清理时机复测：2026-10-30

本次复测再次支持“正式送帧前先做一次完整清理”，用来减少处理画面期间的清理停顿。但它不能解决所有偶发停顿：本次默认组首帧处理过慢，跳过了 1 帧；这次跳帧主要不是清理造成的。

## 测试条件

- 使用当前代码，没有修改正式处理代码、识别规则或默认清理设置。相关代码及输入文件的校验值在运行前后相同。
- WSL 2，Python 3.12.3，OpenCV 4.10.0，NumPy 2.2.6；分析使用 24 个 OpenCV 线程，图像转换使用 1 个线程。
- A 原始视频按 60 帧/秒播放，重复 15 次，每组 330 秒、19,800 帧。背景文件沿用上一轮的 `results/B_offline/background.npy`，没有重新选择或训练背景。
- 两组顺序运行，均保留转换预热、内存复用、独立保存线程。详细逐帧诊断关闭，仅保留基础时间、帧号和实际发生的清理事件。
- 默认组：正常自动清理。预清理组：送帧前完整清理一次，全部结果保存结束后再清理一次；运行中仍允许正常自动清理，两组阈值均为 `(700, 10, 10)`。
- 另运行一组 2 秒后主动取消的测试，检查保存及清理设置恢复。
- 本次是离线视频回放，没有连接真实相机、运行录像分支、发送 AFG/PZT 命令，也没有更改 Windows 设置。

两组典型帧处理速度接近，预清理组的中位数和 P99 并没有变快。本次得到的改善主要是把完整清理移到送帧之前，不能据此宣称每一部分计算都加速了。

## 清理停顿发生在哪里

默认组在回放第 2640 帧、约 44 秒处发生一次完整清理：

- 清理耗时 **13.914 ms**，其中线程实际执行时间 **13.839 ms**。
- 该帧总处理耗时 **24.469 ms**，清理时间落在该帧处理区间内。
- 触发位置为 `online_store.py` 的 `snapshot_frame()`。这是整理当前帧保存记录时触发的自动清理，并不是数据库提交。
- 这次完整清理回收了 **0 个对象**。它仍需检查存活对象，因此“没有收回东西”不等于“没有花时间”。

预清理组把一次 **9.880 ms** 的完整清理放在送帧前，运行期间只有最长约 **0.041 ms** 的小清理；全部帧处理和保存结束后还有一次 **11.455 ms** 的完整清理。

逐次记录见 [gc_frame_links.csv](gc_frame_links.csv) 和各组 `gc_events.csv`。原有自动清理一直开启，退出时阈值恢复正确，没有不可回收对象或清理观察记录溢出。

## 默认组跳过的 1 帧

这里的帧号是从 0 开始的回放帧号，可由 `source_timing.csv` 查回原始视频及相机帧号。

| 事件 | 相对回放开始的时间 |
| --- | ---: |
| 第 0 帧开始分析 | 1.127 ms |
| 第 1 帧送入等待区 | 16.919 ms |
| 第 2 帧送入，替换尚未被取走的第 1 帧 | 33.554 ms |
| 第 0 帧分析结束 | 41.344 ms |
| 第 2 帧开始分析 | 41.657 ms |

第 0 帧分析用了 **40.217 ms**，其中清理仅占 **0.068 ms**。因此，这次跳帧的直接原因已明确：首帧分析尚未完成时，后续画面连续到达，只有一个位置的等待区按既定规则保留了较新的画面。它不是保存时丢失，也不能主要归因于自动清理。

首帧的核心处理耗时为 39.085 ms。本次按正常运行方式关闭了详细诊断，因此不能继续把这段耗时拆分到具体识别函数、线程调度或内存等待；没有证据将它归因于某个后台程序。预清理长测最慢一帧为第 10397 帧的 21.577 ms，同样没有清理重叠。取消测试首帧仍用时 30.822 ms，也没有清理重叠，说明启动和其他非清理停顿仍未彻底解决。

完整前后记录已保存于 [verification.json](verification.json) 的 `gap_context`。

## 保存与内存检查

默认组第 6785 帧保存时，一次数据库提交耗时 **206.279 ms**，线程实际执行仅 **0.153 ms**；主要时间没有用于该线程执行计算，但仅凭本次记录不能继续区分底层磁盘等待和系统调度。

这段等待期间，分析线程仍完成第 6786–6797 帧，共 12 帧，其中最慢分析为 **10.655 ms**。保存等待数量峰值为 13 帧，低于 32 帧容量，之后清空，没有产生额外分析跳帧或保存缺口。预清理组最长数据库提交为 **20.385 ms**，等待数量峰值为 2 帧。不能将两组这项差异归功于清理时机，因为本次没有控制底层磁盘波动。

详情见 [writer_verification.json](writer_verification.json)、[save_delay_context.json](save_delay_context.json) 和各组 `replay/writer_timing.csv`。

两组分析进程内存保持在约 191 MiB，稳定阶段变化均小于 1 MiB，没有观察到持续大量增长。保存线程全部退出，已提交的帧全部保存，数据库完整性和关联检查通过。

## 识别结果是否改变

- 预清理组的 19,800 帧，与上一轮完整默认基准的 19,800 帧逐表相同：帧记录、轮廓与位置、轨迹、事件、事件更新、轨迹更新、输入拒绝记录均一致。比较只排除本来就会变动的处理耗时字段。
- 本次默认组跳过了第 1 帧，后续追踪获得的输入已经不同。因此本次两组不能作为“相同输入、结果全等”的直接证据，也没有将其差异隐去。
- 三组数据库中的帧号均与各自实际完成分析的帧号逐项对应。

## 取消收尾

主动取消组在约 2 秒时停止：已完成的 **120 帧全部保存**，另 1 帧记录为取消后未处理，没有悄悄删除记录。保存队列清空、保存线程退出，自动清理开关与阈值恢复正确。

本次验证的是正常完成与主动取消；没有重新注入磁盘故障、进程强杀等异常。本轮未修改正式代码，因此没有重复运行上一轮的单元测试，不将上一轮测试次数算作本次结果。
