# 正式接入开始前、保存后的 Python 内存清理

2026-10-30。本轮已把两次完整清理接入正式逐帧分析模块。运行期间保留自动清理，门槛始终为 `(700, 10, 10)`。四组 330 秒回放中，自动清理最长为 **0.138 ms**，没有再观察到十几毫秒的清理停顿；但处理链仍有少量非长时间清理导致的超时，**没有达到整体零跳帧**。

## 正式程序现在怎样运行

1. 创建分析模块，完成已有的区域编号图准备；等待送帧端完成转换初始化和预热。
2. 实际分析线程调用 `OnlineProcessor.start()`，执行一次 `gc.collect(2)`。成功后再设定回放起点、发出开始送帧信号。
3. 逐帧分析时，保持自动清理开启，保留原门槛。正式模块不调用 `gc.disable()`、`gc.enable()` 或 `gc.set_threshold()`，也不安装逐帧清理探针。
4. 停止接收后，先排空已提交记录、核对保存数量、等待保存线程及数据库退出，再完整清理一次。

`start()` 重复调用不会重复清理。直接调用接口时，应在开启输入前显式调用它；`with processor:` 会自动调用。旧调用如果直接进入首次 `process()`，会补做启动清理，因此外部测到的首次调用会包含准备时间。正式定速回放已显式提前调用，避免这个问题。

开始时发现自动清理已被外部关闭，会明确报错，不擅自改变进程设置。正常结束、取消、分析异常都执行保存收尾；清理自身的异常不能覆盖原始错误。保存超时且线程还在运行时，报告未完成并跳过结束清理，不能当作成功。

每个新结果目录都有 `gc_lifecycle.json`，记录进程、线程、两次清理时间、耗时、回收数量、前后开关和门槛，以及保存结束时间。正式回放的记录确认：**启动清理完成早于送帧起点，结束清理晚于最后分析帧和保存退出**。

代码与说明：

- [online_tracking.py](../../microbubble_tracking/online_tracking.py)：生命周期及异常收尾。
- [paced_replay.py](../../microbubble_tracking/paced_replay.py)：完成双方准备后才开始送帧。

## 测试条件

Python 3.12.3，WSL2/Linux，分析 OpenCV 线程数 24、转换线程数 1。沿用原 A、B 视频、原背景及参数，保持已验证的预热、内存复用、独立保存线程和普通记录模式。所有性能回放依次运行，没有并行跑其他本任务的计算测试。

每段原视频为 1,320 帧、22 秒、60 帧/秒。长测连续重复 15 遍，共 330 秒、19,800 帧；重复接缝是压力测试安排，不能当作新的真实微泡动作。此轮没有连接相机、录像或 AFG/PZT，没有修改 Windows 或 WSL 配置。

自动清理统计窗口严格限定为 `origin_perf_s` 到最后一帧分析完成时间，排除开始前、保存后的主动清理。观察器只在清理发生时记录，不扫描逐帧线程列表。正式普通回放不创建该观察器。

- 原源帧号、视频帧号、视频时间、Windows 接收及解码时间完全一致；比较只排除本机处理耗时。
- 初始背景、最终背景、原动作表、原视频帧时间表的文件校验值一致。

这两次是完整输入的正确性验证，不是实时性能测量。A 的本轮 66 秒前后定速对照也全部科学记录一致。B 短测及两次长测之间存在不同跳帧，科学结果因此并非全量相等；它们不能用于声称相同输入下算法改变。原失败/跳帧记录没有删去或覆盖。

## 取消和异常验证

定速回放在约 2 秒主动取消，已提交的 **120 帧全部保存**，保存线程退出后才完成末次清理，状态保留为 `cancelled`。

最终 **177 项测试通过**，其中新增的 14 个参数化测试覆盖同步/异步保存、正常退出、分析错误、取消、开始或结束清理出错、等待保存时被取消、保存超时和自动清理原本关闭。测试确认不能留下修改过的清理设置，原始异常不被后续清理异常覆盖，保存线程未退出时不假称完成。

记录见 [tests_final.log](tests_final.log)；测试失败注入不等于断电保护。强制杀进程或断电无法保证 Python 收尾代码执行，磁盘故障也必须明确报告保存失败。

## 仍然存在的停顿

长测跳过的回放帧号（从 0 开始）分别为：

- A 第 1 次：44。
- B 第 1 次：5,970、5,974。
- A 第 2 次：1、6,856、6,858。
- B 第 2 次：2,843、5,426、11,785。
- 另有 B 修改后 66 秒短测：3,366。

记录显示这些时段处理赶不上新帧到达，待分析旧帧被替换。A 第 2 次的首帧处理为 32.429 ms，附近只有一次 0.047 ms 的自动清理，无法解释这段长停顿；其余缺口前后相邻帧时间范围内没有 GC 事件。B 短测的连续两帧分别用了 26.805、23.485 ms，期间没有清理。

因此，十几毫秒的清理不是这些缺口的解释。本轮保留普通记录，没有重新打开全部底层探针，不能进一步断言每次慢帧是计算、系统调度还是内存等待造成。当前任务没有扩大到修改识别规则、系统内存配置或更激进的清理策略。真实相机录像与分析同时运行是否新增丢帧，本轮没有执行，不能作通过声明。
