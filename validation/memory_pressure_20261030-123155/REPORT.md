# Windows / WSL 内存压力对照

**结论：关闭 Pylance 后，本次同条件回放的内存换页和长停顿明显减少。**
目前采用“实验期间暂停 Python 后台分析”，保留 WSL 的 8 GB 内存上限和交换空间。
没有修改识别算法，也没有增加 WSL 的内存配额。

本轮只回放已有 Exp. B 录像，未连接相机或操作 AFG/PZT。
使用相同原录像、参考背景、帧时间表与算法；每次连续回放三遍，共 3960 帧、约 66 秒。
分析线程数为 24，解码和 BGR 转换均为 1；使用已有异步保存。

### 尚存的启动停顿

29.583 ms 出现在第二次对照的回放帧号 2，也就是**启动后的第 3 帧**。
该阶段记录 960 次 Linux 软缺页、零 Linux 磁盘缺页，线程 CPU 约 29.988 ms，
其中内核时间较多。这与启动时准备新内存的情况相容，但本轮没有该时刻的原生
调用栈及两侧时间校准，不能据此精确区分 Windows 回页与 Linux 内存准备各占多少。

它完整保留在总体统计中，没有因为属于启动期而删除。现有预热诊断与分割工作区
复用保持原样；本次没有另外实施 BGR 转换缓冲区改造或额外预热，因此不能声称
已彻底解决正式前几帧的所有内存准备停顿。

本次是前后顺序对照，不是随机交错实验。Windows 其它应用、缓存和调度仍会变化，
不能把改善的全部比例都严格归因于 Pylance，更不能保证以后每次都没有长停顿。
不过已直接确认其约 3.3 GiB 占用消失，并观察到回页量和长停顿同时明显减少。

## 当前配置决定

Windows 实际可见物理内存约 15.74 GiB；`.wslconfig` 为 `memory=8GB`、`swap=8GB`。
WSL 在基线中仍有可用内存，也未新增自身交换区读写。
关闭 Pylance 后，WSL 可用内存进一步增加至约 5 GiB；Windows 可用内存最低也在
约 2 GiB。四次回放均无新增 WSL 交换区换入、换出。因此，**没有发现必须调整
WSL 内存配额的依据，本轮不进行配额修改或重启**。扩大配额不能解释为优化；
缩小配额又可能引入新的 WSL 交换。本次按用户要求先单独验证后台任务的影响。

Windows 页文件和 WSL 交换空间均保留。四次开始前保存的 `.wslconfig` 内容一致。
实验期间可以保持 `Python: Language Server = None`；需要补全和代码检查时，再由
用户恢复原来的 `Default` 或 `Pylance`。本轮未替用户恢复，以免实验期间再次占用内存。

## 保存与稳定性验证

- 四次总共送入 15840 帧，分析并提交的 15819 帧全部保存。21 帧分析跳过有记录，
  其中基线 19 帧、对照 2 帧；这是已有录像的实时回放，不是实际相机录像丢帧测试。
- 四份数据库 `quick_check` 均通过，保存线程全部正常结束，没有未保存的提交。
- 代码指纹、录像和参考背景、帧时间表、回放次数、线程设置、保存参数一致，
  详细核对见 [verification.json](verification.json) 和
  [input_consistency.json](input_consistency.json)。监测工具的取消收尾及进程识别
  小修不改变实际分析代码；原有识别、追踪和保存代码指纹均相同。
- 两段 Windows 记录期间，查询 Application 日志中的程序崩溃/无响应事件
  （1000、1002）和 System 日志中的资源耗尽事件（2004），均未发现匹配记录，
  查询本身无错误；Linux 也没有新增内存不足终止记录。
  这只能说明本次短时观察未发现这些问题，不能保证所有程序的长期稳定性。
- 完整相关测试最终为 **83 项通过**，见 [final_tests.log](final_tests.log)；
  格式检查和 `git diff --check` 通过。

本轮已完成后台分析关闭前后的同录像测试，并观察到预期改善；剩下的启动停顿仍
需保留关注。没有将历史 157 ms 事件写成已经消除，也没有声称本轮已验证实机录像。

## 新增的工具

- `memory_pressure_check.py`：复用现有回放，同时保存 Windows、WSL 内存和运行日志；
  监测失败会明确报告，不自动关闭应用或修改系统配置。
- `memory_pressure_report.py`：汇总转换中位数、P99、最大值、长停顿次数和内存；
  分开统计全系统缺页与 WSL 页文件读取。
