# 数据库保存检查与优化测试

日期：2026-10-30。仅使用已有录像回放，没有连接相机或控制 AFG/PZT。

**结论：保存步骤和等待位置已查清，并增加了可追溯的计时。分段写回候选方案减少了部分较慢保存，但没有改善最坏情况，因此没有采用为默认方案。** 当前默认仍为原来的 `auto`，保留新增记录；`deferred` 可用于继续对照。

## 1. 数据实际存在哪里、怎样保存

- 数据库为 SQLite 3.45.1，文件是每次运行目录下的 `tracking.sqlite`。
- 当前项目及本次结果目录在 WSL 本地 ext4，设备 `/dev/sdd`，不是 `/mnt/c` 或 `/mnt/f`。因此没有再做“从 Windows 挂载目录迁到 WSL”的重复试验。WSL 的虚拟磁盘仍经过 Windows 存储系统，本地 ext4 不代表完全绕过 Windows。
- 实际写入连接：`journal_mode=wal`、`synchronous=2`（FULL）、`page_size=4096`、`cache_size=-2048`、`foreign_keys=1`、`busy_timeout=5000`、`auto_vacuum=0`。原设置 `wal_autocheckpoint=256`，即日志达到约 1 MiB 后可能触发写回。
- 原程序已经有一个独立保存线程。分析端提交与后续图像处理相互独立的记录副本，等待队列最多 32 条，包含正在保存的记录。
- 保存线程只合并已经到达的最多 4 帧，不为了凑批而等待。这次原设置的 5238 帧对应 5232 次事务，其中 5229 次实际只保存一帧。典型每帧约 15 个区域，轮廓原始字节约 5.9 KiB，另有位置、时间和事件等字段。这不是数据库实际写入字节数：索引、数据库页和日志也需要写入。
- 一批中的帧、轮廓、编号及事件在同一事务内保存。确认完整提交成功后才通知分析端“已保存”；放进队列仅表示已接收。

普通保存顺序为：**等待保存线程 → 整理字段 → 执行数据库语句 → 提交并确认 → 发出成功通知**。原设置中，一部分提交还会同时把日志中的数据写回主数据库。没有运行 `VACUUM`，不能把这里的写回称为“数据库碎片整理”。

WAL 模式先写日志，主文件可以稍后更新。FULL 保留每次事务提交时的同步要求；自动写回可能由触发门限的提交线程执行。因此，不应把“推迟日志写回”和“降低保存确认要求”混为一谈。[SQLite WAL 说明](https://sqlite.org/wal.html)、[同步级别说明](https://sqlite.org/pragma.html#pragma_synchronous)。

每次运行的 `database_settings.json` 都在实际写入连接上记录设置、绝对路径及保存线程编号。保存过程中，已经确认的数据也可能仍在 `tracking.sqlite-wal`，不能只复制主文件作为完整备份。

## 2. 各步骤的实测耗时

以下为四组配对回放的全部结果，包含最后一组的异常，没有删除慢样本。每组同一录像按原速度送入，交替先后顺序：A 旧/新、B 新/旧、B 旧/新、A 新/旧。保留 8 次启动预热、转换内存复用、转换 1 线程、分析 24 线程。两种设置都记录分段耗时，没有同时运行系统调用追踪。

“P99”表示约 99% 的记录不超过该数值。数据库步骤按真正的事务去重；排队和提交完成时间按每帧统计，不能把一批四帧的提交耗时重复算四次。

| 步骤（ms） | 原设置中位数 / P99 | 分段写回中位数 / P99 |
| --- | ---: | ---: |
| 等待保存线程 | 0.143 / 0.485 | 0.147 / 0.598 |
| 保存线程内整理字段 | 0.048 / 0.114 | 0.050 / 0.179 |
| 数据库语句及编号、事件整理 | 0.610 / 1.376 | 0.626 / 2.095 |
| 提交调用 | 4.027 / 13.146 | 4.101 / 9.930 |
| 从提交给保存线程到确认完成，包含排队 | 4.901 / 14.857 | 5.006 / 12.968 |

中位数没有改善。总体 P99 有一定下降，但最终最慢值 **110.44 → 129.64 ms**，两边超过 50 ms 的帧各 5 条。因此不能只拿提交调用的最大值下降来宣称保存已经更稳定。

候选方案的独立写回中位数 9.93 ms、最大 109.12 ms。结束时，状态整理与数量核对耗时 4.32–5.36 ms，最终写回与关闭 7.64–20.36 ms。原设置在实验中发生的自动写回仍包含在提交调用内，不能拿原设置 CSV 中仅有的结束写回次数，与候选方案全部写回次数直接比较。

### 确认磁盘同步调用，而不只根据总耗时猜测

另做了两次 600 帧的系统调用追踪，只跟踪 `fdatasync/fsync`，按保存线程编号和本机时间对应到提交、写回阶段。它们会受诊断工具影响，**不计入上述速度比较**。

| 运行中的调用 | 原设置 | 分段写回 |
| --- | ---: | ---: |
| 实际保存帧 / 事务 | 595 / 595 | 584 / 583 |
| 提交阶段对 WAL 的同步调用 | 639 | 587 |
| 提交阶段对主数据库的同步调用 | 22 | 0 |
| 独立写回阶段对主数据库的同步调用，含结束 | 1 | 5 |

原设置确实在 22 次提交中同步主数据库。候选方案把这些工作移到独立写回阶段，但仍保留每次事务对日志的可靠提交。同步次数可能多于事务数，例如日志重新开始使用时还需要额外同步。

本次原设置追踪中，一次提交为 64.14 ms，其中一条 WAL `fdatasync` 占 47.50 ms；候选追踪中，一次提交为 30.95 ms，其中 WAL `fdatasync` 占 30.08 ms。这证明等待能发生在日志提交本身，不能仅靠推迟主文件写回消除。系统调用耗时包含系统调度与文件系统处理，不等于物理硬盘单独耗时。

证据见 [sync_comparison.json](sync_comparison.json)、`trace_*_sync_events.csv`、`trace_*_commit_sync.csv` 和原始 `trace_*_syscalls.log`。早先的 `baseline_trace` 追踪了更多系统调用，对运行干扰很大，另外保留，仅用于确认调用路径，未计入速度比较。

### 最慢一次具体等在哪里

`final_pair_4_A_deferred` 中：

1. 一次 128 帧后的日志写回持续 **109.12 ms**。
2. 来源帧 409 在此期间进入保存队列，因此等了 **106.20 ms**。
3. 随后与另外三帧合批，数据库操作 17.46 ms，提交 5.84 ms，从接收到确认共 **129.64 ms**。

这次写回的保存线程 CPU 时间也达到 **96.44 ms**，所以不能把 109.12 ms 全部说成“等硬盘”。这次没有同时采集原生调用栈，写回内部哪部分 CPU 工作变慢仍未分清。原设置最慢提交也出现 109.50 ms 总耗时、96.10 ms 线程 CPU 时间。两边这一组还出现分析计算的明显停顿；目前证据不能把全部跳帧都归因于数据库，也不能断言某个用户程序导致了停顿。

此前 1.76 秒停顿缺少当次完整的底层调用记录，本次不能倒推其每一毫秒，也没有证明其再次出现的可能性已消除。

## 3. 实现并测试的改进

沿用原保存线程、数据库结构和识别算法，增加了可选的 `deferred` 策略：

- 保留 WAL 和 FULL，只关闭隐藏在提交中的自动写回。
- 已提交至少 128 个视频帧、队列暂时为空时，用 PASSIVE 写回，保留日志文件空间供下一段循环使用。
- 没有新记录超过 100 ms 时，也可提前写回。
- 日志达到 64 MiB 门限时要求整理并收缩；这是检查门限，不是保证单批写入绝不超过 64 MiB。
- 结束时先排空、核对数量，再最终写回并关闭。
- 普通 PASSIVE 写回不等待外部读者退出，可以保留未写回部分；到空间门限或关闭时若仍被读者阻挡，明确报错、保留文件。不会直接删日志。[SQLite 写回接口说明](https://sqlite.org/c3ref/wal_checkpoint_v2.html)。

增加 `database_maintenance.csv` 独立记录写回时机、CPU 时间、经过时间、日志大小及错误；`writer_timing.csv` 增加真实事务编号、字段整理耗时、记录数量和轮廓字节数。`writer_report.json` 增加结束核对与关闭耗时。自动写回对照仍能使用这些计时。

还试过只在结束或大门限写回：日志不断扩展后，常见提交耗时约 6 ms，比原设置约 4 ms 更差，因此放弃该候选。原始 `pair_*`、`long_B_deferred` 结果保留；当时正在进行的 `B_batch16` 被正常取消，原因保存在 `stopped_candidate.json`。

最终另把合批上限从 4 改为 16 做了一次试验，1315 个已处理帧仍是 1315 次事务，没有合批收益。因此保持原上限 4，没有为了减少同步次数而额外拖延提交。

## 4. 完整性和持续运行检查

固定输入、逐帧处理且不允许跳帧的 B 视频复核：两种方式各 1320 帧。除处理耗时字段外，逐项比较全部科学记录，包括轮廓原始字节：

| 记录 | 完全一致的条数 |
| --- | ---: |
| 帧 | 1320 |
| 区域观测 | 17843 |
| 轨迹 | 75 |
| 事件 | 137 |
| 事件更新 | 274 |
| 轨迹更新 | 198 |

最终背景数组也完全相同，两份数据库完整性检查均通过。见 [identity_check.json](identity_check.json)。

最终自动测试 **119 项通过**，包括整批失败回滚、队列积压报错、取消排空、读者阻挡写回、确认先于可选写回，以及新建子进程确认 5 帧后直接退出、重新打开数据库仍能读回全部 5 帧。后者是进程异常退出检查，不是实际断电试验。

一次测试最初因给建库和关闭共用的期限都设置为 100 ms，提前触发启动超时。已把该测试改为正常完成建库后，只缩短待测的关闭期限；没有放宽正式程序的错误处理。错误日志保留，最终结果见 `tests_final_default_auto.log`。另一次从子目录启动测试导致包导入失败，正确入口是在项目根目录执行测试。

66 秒 B 视频重复回放：3960 帧送入，3939 帧处理并全部保存，21 帧在最新画面分析入口被替换；没有未交代的帧，也没有已接收保存记录丢失。保存最多积压 3 条，最后排空；保存确认最长 32.58 ms。分析进程内存采样最高约 184 MiB，送帧进程约 132 MiB，首末 5 秒结果延迟中位数 10.74 / 10.22 ms，没有持续上升。

但该长回放仍有一次分析结果超过时效门限，全部正式配对中也有跳帧：

| 配对 | 录像 | 原设置处理 / 替换 | 候选处理 / 替换 |
| --- | --- | ---: | ---: |
| 1 | A | 1320 / 0 | 1319 / 1 |
| 2 | B | 1319 / 1 | 1317 / 3 |
| 3 | B | 1317 / 3 | 1319 / 1 |
| 4 | A | 1282 / 38 | 1031 / 289 |

这些是分析入口“只保留最新帧”的替换，不是新录像丢帧。本轮没有实际录像负载，不能据此宣布“录像无新增丢帧”已经验证。

## 5. 当前采用状态与后续入口

**已采用：**详细计时、实际连接设置记录、结束核对耗时记录。保持原 `auto` 为默认，保存队列和合批上限不变。

**未采用为默认：**分段写回候选。它的多数记录保存更快一些，但最坏情况没有改善，尚不满足“长时间等待明显改善”的完成标准。诊断工具不能凭空消除系统调用或写回 CPU 停顿。

原 `paced_replay.py` 回放命令可明确追加 `--save-checkpoint-policy auto`，或用 `--save-checkpoint-policy deferred` 复测候选；`--save-wal-limit-mb 64` 指定候选日志门限。完整输入和参数见 `final_commands.json`。不要直接重复使用其中已经存在的输出目录。

性能对照应保持 Windows/WSL 背景负载尽量相近。快照时 Windows 可用内存约 1.4 GiB、WSL 可用约 5.2 GiB，两个数字不能相互替代；这也不能证明某一次停顿就由某个后台程序造成。下一步应针对写回内部 CPU 高耗时采集证据，并在相近负载下复测，而不是关闭页文件或降低 FULL 可靠性来换取更短数字。
