# 逐帧处理与真实速度回放

这一轮把现有识别与追踪整理成一个可以反复调用的模块：**送来一张画面，
处理这一张，把记录交给保存线程，再返回结果。** 它不采集相机画面、不启停录像，
也不发送 PZT 命令。工作区的相机入口现在通过 `parallel_camera_bridge.py` 将真实帧号、
视频时间和 Windows 接收时间交给本模块，`parallel_video_check.py` 管理预热与收尾。
当前使用已有录像走整条 Windows/WSL 路线验证；真实相机尚未连接验证。
运行命令、背景要求和结果说明见[工作区 README 第 7.5 节](../README.md#75-没有相机时验证新追踪接入)。

相机路线只替换输入接入，不复制识别或追踪算法。Windows 传递 H.264 压缩帧，WSL 独立
进程复用 `ReusableConversion`，解码后的灰度图经三块有明确所有权的共享空间交给分析。
分析和保存继续使用本文件描述的预热、内存复用、原自动清理设置以及有界异步保存。
`FrameStamp.decoded_windows_s` 在新路线留空；真实解码时间属于 WSL，单独写入
`analysis_frames.csv`、`video_frames.csv`，不能伪装成 Windows 时间。

## 开始送帧前的分析端准备

创建 `OnlineProcessor` 时，先申请区域编号图并实际写入一次。随后由真正执行
`process()` 的分析进程、分析线程调用 `start(sample_frame)`，完成其余准备：

1. 写入平滑图、暗度图、区域编号图、筛选图、编号转换索引和输出编号图的全部空间，
   并准备背景对应的计算缓存。
2. 用现有平滑、区域识别和追踪函数试跑 3 次。先用临时画面访问轮廓计算，
   再用已经取得的样例帧试跑；没有提供样例时，使用由背景生成的临时画面。
3. 追踪只使用独立的临时追踪器，不调用正式背景更新，不提交任何实验记录。
   结束后清空工作图，核对正式背景、编号和帧状态没有变化。
4. 执行原有的开始前完整内存清理，写出准备完成记录，然后返回。

样例帧不会被修改或作为已处理帧保存；调用方仍应把它按原始编号、时间送入正式
`process()`。正式目标编号从 1 开始，视频第 0 帧仍由真实输入决定。预热不读取未来帧。

`paced_replay.py` 的顺序是：分析模块构造 → 送帧端准备并等待 → 同一分析线程
执行 `start(first_gray)` → 分析端准备完成 → 设置正式计时起点 → 发出送帧开始信号。
分析预热失败或取消时，不设置正式起点、不发开始信号，按已有流程关闭保存线程。
构造时写入编号图失败，则连送帧进程也不会创建。

这些准备默认执行，不需要新的命令行开关。重复 `start()` 不重复预热或清理。
之后若换进程或线程调用 `start()` / `process()`，会明确报错，避免把其他进程的
预热误当作实际分析端已经准备好。

| 记录 | 内容 |
| --- | --- |
| `session.json` 的 `startup_preparation` | 构造时编号图准备及预热报告位置，数据库会话信息中也保存 |
| `analysis_preparation.json` | 预热进程、线程、图像尺寸、工作区大小、用时及状态核对；失败时保留原因 |
| `analysis_ready.json` | 预热和开始前清理全部完成之后的准备就绪时刻 |

上述时间使用分析主机的 `perf_counter`，不是曝光时间。预热减少首次访问资源的
额外开销，但不锁定物理内存，也不能保证操作系统以后永远不再回收页面或暂停进程。
普通运行仍不启用逐帧详细诊断。重复启动及结果一致性证据见
[分析端启动预热验证](../validation/analysis_startup_20261030-183814/REPORT.md)。

## 平滑结果的内存复用

`OnlineProcessor` 为本视频流准备一张与背景尺寸相同的 float32 平滑图。
`start()` 在实际分析线程写完这张图，并让 3 次预热调用都写入它。正式处理时，
仍使用同一个 `cv2.GaussianBlur`、同样的平滑强度和边缘处理，只通过 `dst` 指定
已经准备好的空间，避免每帧重新申请整幅结果图。

顺序固定为：平滑 → 识别 → 追踪 → 背景更新 → 提交记录 → 下一帧。
背景更新同步用完平滑图后，下一帧才可覆盖它。返回值和保存队列只包含独立的
轮廓、编号、位置及事件，不包含平滑图；不需要额外设置多张图的轮换队列。
一个分析实例仍只能由同一分析线程串行使用。

通用 `segment()` 只有显式提供 `blurred_out` 时才借用调用方空间；省略时仍返回
独立平滑图，下一帧不会覆盖旧返回值。若其他程序希望异步读取平滑图，必须先
复制，或等待读取结束后再复用。错误尺寸、类型、只读空间及与输入、背景或
内部工作图重叠的空间会被拒绝。

这只消除整幅输出图的反复分配，不保证 OpenCV 内部完全没有临时空间，也不改变
科学计算规则。完整 A/B 像素核对、交错计时和回放证据见
[平滑内存复用验证](../validation/blur_reuse_20261030-185211/REPORT.md)。

## 开始前与保存后的 Python 内存清理

实际分析线程调用 `processor.start(sample_frame)`，在内部完成预热后执行一次完整的
`gc.collect(2)`。`paced_replay.py` 在送帧端报告准备完成后调用它，再设定回放起点、
发出送帧信号，所以清理不占用正式第一帧的处理时间。重复调用 `start()` 不重复清理。
`with processor:` 会在进入代码块时执行同样的准备；直接调用接口时，应在开启输入前
显式调用 `start()`。为兼容旧调用，未调用 `start()` 的首次 `process()` 会补做准备，
但这种用法会让外部测到的首次调用包含预热和清理时间，不适合正式实时送帧。

分析期间继续使用原来的自动清理：不关闭它，不提高任何门槛。本轮环境是
`(700, 10, 10)`；模块保留调用者原有门槛，不强制改成这个数值。如果进入时自动清理
已关闭，启动明确报错，不默默改变整个进程的设置。正式流程不安装逐帧诊断或 GC 观察器。

停止接收画面后，`close()` 先排空已提交的记录、等待保存线程退出和数据库关闭，
再执行一次完整清理。正常结束、取消和分析出错都走这条收尾路线。如果保存超时且
线程还在运行，就报告保存未完成，并跳过结束清理，不能把它算作成功。清理自身出错
不会删除已保存的数据，也不会覆盖先前的分析错误。强制杀进程、断电不能保证执行收尾。

`gc_lifecycle.json` 记录两次清理的进程、线程、开始和结束时间、耗时、回收数量、
前后自动清理开关及门槛，以及保存结束时间。时间使用分析主机的 `perf_counter`，
不能与 Windows 时钟相减。这种做法把一次较大的准备工作移到实验前，不能保证运行中
永远不再发生较长清理，也不消除系统调度、磁盘或其他计算造成的停顿。

## 每次调用做什么

1. 核对实验编号、视频流编号、源帧号和画面时间，拒绝重复、倒序或混入另一段实验的输入。
2. 沿用 `bubble_tracker.py` 的背景更新、微泡识别、位置预测和区域匹配。
3. 用两次真正看到目标的位置差，除以两张画面的实际时间差，计算速度。
4. 复制这一帧的轮廓、位置、编号、状态和事件，放进有容量限制的保存队列，再返回。

历史记录在 `tracking.sqlite` 中。它是一个独立数据库文件，保存期间使用相邻的
`-wal` 文件记录新提交的数据，正常关闭时合并；运行中不要只复制主文件而漏掉日志。
默认由独立保存线程写入，沿用同一个数据库及记录规则。**分析返回不等于已经落盘**；
`poll_saved()` 或返回值中的 `saved_updates` 提供已落盘帧的确认。
结束时 `close()` 等待排空，再核对已接收和已保存帧数；保存失败不能作为正常结束返回。
需要同步对照时，使用 `save_mode="sync"`，它仍在返回前提交当前帧。

## 四项要求如何处理

### 真实帧号、跳帧和时间

相机的源帧号与视频里的帧号分开保存。例如本次录像的第 0 帧，对应源帧号 274，
不能把两者混用。假如收到源帧号 274、275、278，就明确记录中间少了 2 帧，
不会把 278 改叫 276，也不会为缺失画面编造轮廓。

`skipped_source_frames` 统计两张已收到画面之间的缺口。最后一张收到之后是否还缺帧，
需要录像端提供结束记录，单凭逐帧接口无法猜出。回放报告另列出人为跳过的总帧数；
例如每第 3 帧跳过一次时，末帧也可能被跳过，总数会比内部缺口数多 1。

速度单位为像素/秒。`raw_vx_px_s`、`raw_vy_px_s` 是两次位置差直接除以真实时间差；
`vx_px_s`、`vy_px_s` 是沿用原算法平滑后的预测速度，默认各取一半旧速度与新速度。
新目标第一次出现时没有可用速度，`velocity_valid=false`，原始速度留空。
这里不使用离线分析中“前三帧、后三帧”的计算，因为在线时还没有后面的画面。

旧目标能否继续匹配同时受帧号跨度和时间跨度限制：默认源帧号差不超过 8，
时间差不超过 `8 / nominal_fps` 秒；60 fps 下约 0.133 秒。这保留原算法的
帧号门限，并补上实际时间门限。超过任一门限，旧轨迹结束，重新出现的区域分配新编号。
这是一条保守的工程规则，并不证明消失前后的区域一定是不同微泡。

时间门限允许两个源时钟刻度的舍入余量，两端时间各占一个刻度；这个余量不会放宽
帧号门限。回放使用视频明确给出的时间刻度（本次为 1/90000 秒），并将它写入记录。
这是为了避免恰在 8 帧边界附近、只差十几微秒就无故换号。其他来源若未提供
`source_time_resolution_s`，默认余量为 0，不擅自假定时钟精度。

背景只按实际收到的画面更新，不为缺帧补做更新。`perf_counter()` 只用来测本地
计算耗时，不能用它代替画面时间，更不能拿它减 Windows 端的时间。

### 临时目标、稳定编号和延迟确认

新目标立即获得编号，状态先记为 `tentative`（待确认）。真正观察到 5 次后才记为
`confirmed`（算法确认），跳过的画面不计入这 5 次。编号不在结束时重新排号，
短暂出现后消失的目标也保留原记录，因此编号有空档是正常现象。

合并、分离、出现、消失等事件也先记下来，之后可追加确认或否决记录：

| 字段或状态 | 含义 |
| --- | --- |
| `anchor_frame` | 事件对应的画面；跟丢时是最后一次看到目标的画面 |
| `reported_frame` | 程序发现这件事时正在处理的画面 |
| `decided_frame` | 程序能够作出确认或否决时的画面 |
| `interval_from_s` / `interval_to_s` | 从之前的相关观测到本次发现的时间范围，不假定事件发生在中间某一精确时刻 |
| `pending` | 相关目标还没有观察够次数 |
| `confirmed_tracks` | 相关目标均达到确认次数；不等于人工确认事件真实发生 |
| `rejected_short_track` | 相关目标太短暂，不能作为可靠事件使用；原记录仍保留 |
| `unresolved_at_end` | 流已结束，信息还不够，保留未决 |
| `evidence_gap` | 相关观测之间存在源帧号缺口，不能把缺口里的过程当作已经看见 |

`events` 表保存最新判断，`event_updates` 保留历次判断及当时的帧号。
例如第 100 帧发现新目标、第 109 帧才观察够 5 次：事件仍属于第 100 帧，
确认发生在第 109 帧，不能把后来的确认写成第 100 帧时就已知道。

这些记录是现有算法的判断，仍可能把识别错误当成合并或分离。本轮没有引入新的
识别模型，也没有把算法确认改称人工审核。跨缺帧事件尤其需要保留谨慎解释。

### 历史写盘与内存清理

每帧的轮廓和所有观测都保存，包括待确认、后来被否决的短轨迹。
内存只留下当前仍可匹配的目标及背景；目标并入其他目标或超过等待期限后立即移出。
没有目标时也记录该帧。编号计数继续增加，但不会因此保留全部历史目标。

正常结束、取消或出错时保存各自状态，清空活跃目标。录像结束本身记为
`stream_completed` 或 `stream_cancelled`，不能凭空生成“微泡消失”事件。
若进程被强制终止，已提交记录仍在，数据库的会话状态可能停留在 `running`；
这种记录应视为中断，不当成完整结束。本轮不实现断点续跑。

### 录像、追踪与 PZT 的关联

一次处理使用三个身份：`experiment_id` 是原实验，`stream_id` 是这一份视频流，
`run_id` 是本次处理。重新分析同一实验会得到新的 `run_id`，不覆盖旧结果。
数据库的 `session` 表记录这些身份；导出的 CSV 每行都带上它们。

每张画面保存源帧号、视频帧号、视频时间，以及已有的 Windows 接收/解码时间。
回放工具核对原视频、动作文件和帧时间表的 SHA-256 文件指纹，并逐帧核对视频自带的
时间（PTS）。它只读取经过核对的旧动作记录，不向硬件发送任何内容。

`action_links.csv` 保留原动作发送时间、确认时间及其视频范围，并增加范围内实际
处理过的源帧号和视频帧号。缺帧时标记 `partial` 或 `none`，不借用附近帧冒充精确对应。
原有接收时间范围、时间误差和局限也继续保留。**这仍是软件时间对应，不是曝光或
超声实际生效的精确同步。** AFG 的后续读回确认也不等于电压恰好在那个时刻改变。

## 使用方法

逐帧接口及回放工具需要 Python 3.11 或更新版本；本轮使用项目现有的 Python 3.12。

在 `customer_workspace/microbubble_tracking` 目录运行以下命令，输出会自动放到
`customer_workspace/validation/online_replay_年月日-时分秒`，目录已经存在时拒绝覆盖。
此命令尽快顺序处理录像，没有按真实播放速度等待，不能据此宣称在线 60 fps 已通过。

```bash
../../.venv/bin/python online_replay.py \
  --video data/raw/expA.mp4 \
  --reference results/B_offline/background.npy \
  --pzt data/pzt/expA
```

实验 B 对应 `data/raw/expB.mp4`、`results/A_offline/background.npy`、`data/pzt/expB`。
这里使用的是已有实验的参考背景，用于软件回放验证。真实接入时需要在实验开始前
准备同一装片、同一视野的背景，不能使用尚未拍摄的实验结果。

可用 `--output-dir 新目录` 指定位置；`--drop-every 3` 会在回放中故意略过每第 3 帧，
用于检查跳帧记录，不修改原视频。核心接口不依赖 PyAV；仅这个回放入口需要 PyAV，
用于读取真实视频时间，已列入 `requirements.txt`。

接入其他程序时，调用 `OnlineProcessor.process(image, FrameStamp(...))`。构造时提供
实验/视频流编号、时间所属的时钟名称、已对齐的背景、标称帧率和新输出目录。
每次提供同一源端的真实帧号与时间。灰度图支持 uint8/float32（0–255），彩色图支持
uint8 BGR，尺寸必须与背景一致。只返回当前观测、轮廓、事件及编号状态更新；调用者
不要把每次返回值无限积存在内存中。视频映射尚未得到时可以留空，不能自行猜一个帧号。

相机断线后源帧号或计时重新开始，应结束旧实例并创建新 `stream_id`，不能把两段
不连续的流硬接成一段轨迹。调用须串行；第 2 轮增加独立的限速回放和单帧等待槽，
摄像头连接仍属于后续轮次。

## 第 2 轮：按真实播放速度送帧

这轮用已经保存的录像代替相机，按原来的画面时间以 **1 倍速** 送入。
送帧和处理是两个独立进程：处理变慢，录像的计划时刻仍照常向前走，
不会悄悄放慢播放速度、等待算法算完。每个计划时刻都由同一个开始时间加原视频
时间计算，前一帧晚了不会让后面的计划跟着顺延。

等待区只放最新的一张画面。假如算法正在处理第 100 帧，等待区先来了 101，
又来了 102，101 就被替换，并明确记录为 `replaced`。已经开始处理的 100
仍正常完成，接着处理 102。图像和时间记录在同一把短时间锁内交换；
识别和写盘不占这把锁。输入记录仍使用原始帧号及画面时间，不为跳帧重新编号。

一张待处理画面距离计划到达时刻超过 100 毫秒时，默认不再开始处理，记为
`expired`。这个门限是可设置的回放保护措施，不是已经证明的控制精度要求。
检查发生在开始处理前；如果计算中途变慢，完成时也可能超过门限，报告另列
`results_older_than_limit`。本轮没有用这些结果控制任何仪器。

两个进程都在同一台 WSL 主机，性能计时共同使用 `perf_counter()`。
原视频时间继续用于速度计算、视频定位和历史 PZT 记录对应；Windows 接收时间只
原样保存。**不拿 WSL 当前计时器减历史 Windows 时间，不称为曝光到结果的延迟。**

### 送帧进程的启动预热

送帧进程读到第一张真实画面后，先记录它的尺寸和格式，再用这同一张画面重复执行
彩色转换和灰度转换，默认 8 次。`allocate` 模式先申请并写入临时空间，
`reuse` 模式则在启动时准备好的固定空间中执行转换。预热图像不再使用后，
才正式转换、发送第 0 帧；固定空间仍保留供后续画面使用。

预热不继续读取后面的画面，不提交追踪记录，不占正式帧号，也不启动实验时间表。
只有预热和原有的准备工作完成后，回放才开始计时。取消或转换出错会留下原因并退出，
不会把测试图像作为正式结果送出。`source_warmup.json` 单独记录预热耗时；启用
`--diagnose-stalls` 时，它也作为 `startup_warmup` 单独列出，不混入正式转换耗时。

第一步只加入预热时，仍然每帧申请转换空间；释放的内存不保证以后每次都能复用，
因此后续帧仍出现过停顿。第二步增加下文的固定空间复用。系统仍可能等待，
不能把任一种方式当作绝对不会停顿的保证。目前仅接入 WSL 的录像送帧入口，
尚未部署到 Windows 相机程序。

实测记录见 [启动预热对照报告](../validation/conversion_warmup_20261030-133432/REPORT.md)。

### 转换空间如何安全复用

默认 `--conversion-memory reuse`。发送进程启动时准备一张彩色图和一张灰度图的
固定空间，实际写入以准备内存，并进行原有的 8 次预热。每次启动还会把真实首帧
与原 PyAV 转换逐像素比较；不一致时停止，不悄悄改变识别输入。

每一帧按照下面的顺序处理：

1. 确认转换空间空闲，转换新画面，标记为“正在使用”。
2. 用固定彩色空间生成固定灰度图。
3. 在原有短时间锁内，把灰度图和时间记录复制到共享等待区。
4. 等复制完成，归还转换空间；下一帧才允许覆盖它。
5. 追踪进程从等待区取得自己的图像副本，之后的转换不会改变这张副本。

**为什么发送端只需要一组转换空间？** 目前转换和复制在同一发送线程中按顺序完成，
同一时刻最多有一帧占用转换空间。共享等待区另有一张灰度图，追踪者另持自己的副本。
不是整套系统只有一块内存，也不是让追踪者一边读、发送者一边覆盖同一块内存。
若未来录像/网络程序改为异步持有转换图像，不能直接照搬这个归还时机；需要复制，
或等所有使用者明确归还后再复用，并按实际同时持有的帧数决定空间数量。

代码在 `frame_conversion.py`。借出的上一帧未归还时，禁止再次转换或关闭转换器；
其他线程不能使用该空间。尺寸、格式、色彩说明中途改变会明确报错。
取消或出错时，发送端归还自己仍持有的空间，再关闭转换器并保留运行记录。
异步保存线程保存的是独立的轮廓、编号和事件快照，不持有这里的图像视图。

PyAV 当前的 `to_ndarray(format="bgr24")` 没有指定目标空间的参数，因此复用路线
通过 FFmpeg 的公开 `sws_scale` 接口，直接写入固定的彩色空间；灰度转换使用 OpenCV
原方法的 `dst` 参数。使用的是当前 PyAV 已加载的同一套 FFmpeg，没有安装另一套库，
也没有修改 PyAV、系统库或相机程序。正式输入仍保留彩色转灰度的原像素结果。

当前复用路线只接受已验证的 Linux/WSL、`yuv420p`、未指定色彩空间和范围的输入，
覆盖现有实验 A/B 原视频。其他输入会停止并提示使用 `--conversion-memory allocate`，
不会静默退回慢路径后仍称为“已复用”。`--conversion-warmup-iterations 0` 仅关闭
额外的重复预热；复用模式必须进行的空间准备和首帧像素核对仍保留。

`source_report.json` 的 `conversion_memory` 记录空间大小、地址、转换库版本和
首帧核对结果；`conversion_preparation_ms` 包含整个空间准备、核对和预热。
`source_warmup.json` 只记录重复预热部分。转换以外的解码、分析取帧副本及系统等待
仍可能申请内存或造成停顿，本轮没有把它们改成无复制传递。

对照时两组均保留 8 次预热，仅改变 `--conversion-memory allocate/reuse`。
详见 [内存复用验证报告](../validation/conversion_reuse_20261030-134544/REPORT.md)。

### 分开测计算、整理和保存时间

两个回放入口现在都支持 `--measure-stages`。例如：

```bash
../../.venv/bin/python paced_replay.py \
  --video data/raw/expA.mp4 \
  --reference results/B_offline/background.npy \
  --pzt data/pzt/expA --measure-stages
```

真实速度回放把细分时间追加到 `consumer_timing.csv`。顺序回放
`online_replay.py --measure-stages` 另写 `stage_timing.csv`，完整处理同一批帧，
便于核查修改前后的轮廓、编号和事件是否相同。顺序回放不按真实速度送帧，
不能用它的计算时间倒数代替实际在线帧率。

| 字段 | 实际测量内容 |
| --- | --- |
| `input_ms` | 检查帧身份、时间、图像类型，并转换成需要的灰度格式 |
| `segment_ms` | 找出微泡区域并生成轮廓 |
| `track_ms` | 收集区域像素、测量形状、与之前目标对应、更新编号和事件 |
| `background_ms` | 按原规则更新背景 |
| `frame_setup_ms` / `pack_records_ms` | 整理帧信息、观测值及轮廓字节 |
| `database_write_ms` | 登记帧、目标、观测和事件，含这部分状态整理；不含最终提交 |
| `commit_ms` | 等待这一帧的数据库提交完成，包含系统写入等待及可能的日志整理 |
| `commit_cpu_ms` | 提交期间本线程真正使用 CPU 的时间；它是子项，不能重复相加 |
| `read_updates_ms` / `return_ms` | 取出当帧状态更新并组装返回内容 |
| `other_ms` / `process_total_ms` | 未单独划分的小段开销 / 本次函数完整时间 |

`seg_*`、`track_*` 是图像计算和追踪内部的进一步拆分，不应再加到上层总时间里。
提交等待不是“硬盘带宽”的直接测量，数据库操作时间也不能全部称为纯写盘。
这些计时只在本机相减，不改变画面的原始时间及 PZT 对应关系。

本次保留的两项改动是：追踪时只在轮廓的包围范围内查找对应像素；对已经是
0–255 整数类型的图像，省去重复的有限值和范围扫描。浮点图像仍检查范围和无效值。
像素顺序、识别阈值、匹配规则保持一致；保存方式在本轮改为下述异步模式。

曾试验复用亮度计算的临时数组，虽然该步骤变快，但其他图像步骤变慢，因此已撤回；
试验记录保留。详细数据见
[分项耗时分析与对照报告](../validation/online_profile_20261029-210836/REPORT.md)。

并行保存之前的测量结果：两段完整录像的平均每帧处理时间由约 21.09 降至 18.33 毫秒；
按真实速度回放各重复 3 次，约每秒处理 52–55 帧，仍有约 8.9%–12.7% 的分析帧被替换。
45 项检查通过；相同完整输入下的轮廓、数值、编号、事件及动作对应均与修改前一致。
这次提升尚不足以实现 60 fps 每帧完整处理，也没有验证实机同时录像的负载。

### 分析与保存并行

`OnlineProcessor` 和 `paced_replay.py` 默认启用异步保存。完整逐帧对照入口
`online_replay.py` 为方便复核，仍默认同步，可用 `--save-mode async` 切换。
没有改变识别阈值、背景更新、区域匹配或事件判断规则。

分析线程只复制数值、小量目标状态及轮廓字节；不把整幅画面、历史轨迹或可被下一帧
改动的追踪对象放进队列。保存线程复用 `OnlineStore`，数据库连接只打开一次。
轮廓保持原来的未压缩字节，不增加反复压缩或另存小文件。
最多把当前已到达的 4 帧合在一个事务中写入；仍保留 `synchronous=FULL`，
不通过降低保存可靠性来缩短等待。

返回值中：

- `frame`、`observations`、`contours` 属于刚分析的画面。
- `persistence.submitted_frames` 是已接收的数量，`committed_frames` 是已落盘的数量。
- `saved_updates` 每项带原 `source_frame`、本机 `committed_s` 及该帧的事件/编号更新。
- `events`、`track_updates` 是这些已落盘通知的汇总，可能来自前面的帧。
  必须读取其 `reported_frame` / `anchor_frame`，不能假定属于刚分析的画面。
  同批写入仍保留逐帧判断，不会把后面的确认提前填到前一帧。

没有新画面时，可定期调用 `poll_saved()` 领取保存确认、检查后台错误。
通知只是便利接口，完整历史始终保留在数据库；不要无限收集返回值。
`close()` 会领取剩余通知并核对帧数，关闭后的全部事件（包括结束状态）从数据库查询。

队列满或最老记录超过期限：停止接收，报告错误，并尽力保存先前已接收的记录。
数据库写入失败：整批回滚，报告中列出未保存帧，拒绝继续分析。
正常结束和取消：等待排空再关闭。默认最多等 30 秒；超时明确记为未完成。
超时快照另存 `writer_timeout.json`，保存线程真正退出后再写最终的 `writer_report.json`；
这样也保留超时经过，两个线程不会同时改写同一个报告文件。
强制杀进程或断电时，仍在内存队列里的记录可能丢失，不能把“已接收”当成“已保存”。

`writer_timing.csv` 中 `queue_ms` 是等待保存线程的时间；`database_ms` 是一批的数据库
操作时间；`commit_ms` 是一批的可靠提交等待；`durable_ms` 是本帧从入队到落盘的总时间。
同批各行共用一次提交耗时，不能把每行 `commit_ms` 相加冒充总磁盘工作量。
分析计时中的 `database_write_ms` 和 `commit_ms` 在异步模式为 0，仅表示移到了保存线程。
计时 CSV 采用缓冲写入，运行中末行可能稍晚更新；判断积压应看 `persistence`
计数或 `memory.csv` 中每秒采样的保存状态，不以计时文件末行猜测是否丢记录。

表示第几遍。该测试只检查长时间运行、内存和队列，接缝不能用于研究微泡行为。
真实的一遍回放始终保留原始实验、帧号和时间，PZT 关联方式不变。

### 数据库提交与日志整理分别处理

当前结果保存在运行目录的 `tracking.sqlite`。本项目默认路径属于 WSL 本地 ext4，
不是 Windows 挂载目录。运行中还有 `tracking.sqlite-wal` 日志，其中也可能保存着
**已经确认成功的数据**；不能把只复制主文件当成完整备份。正常结束会写回并收尾，
在收尾未完成或出错时应保留数据库及配套文件。

保存仍使用 `WAL` 和 `synchronous=FULL`。成功通知只在完整事务确认后发出；
同批任一帧失败会整批回滚。默认仍只合并已经在队列中的最多 4 帧，不为凑批额外等待。
所以保存速度比画面到达快时，实际常常仍是一帧一次提交。

旧设置是 `wal_autocheckpoint=256`，日志达到 256 个数据库页后，SQLite 可能在一次
提交调用里顺便把日志写回主文件。这不是整理微泡轮廓，也不是压缩录像；它会增加
文件写入和磁盘确认，因此旧 `commit_ms` 混合了提交与自动日志写回的耗时。

可选的 `deferred` 策略关闭这一隐含操作，保留 FULL 提交，再由原保存线程单独处理：

- 已提交至少 128 个视频帧、队列暂时为空时，进行一次 `PASSIVE` 日志写回，保留日志
  文件的空间供后续循环使用。这里的 128 是视频帧数，不是数据库页数。
- 没有新记录超过 100 ms 时，可提前完成待处理的日志写回。
- 日志达到默认 64 MiB 门限时必须整理并收缩，不能一直增长。
- 停止后先排空、核对数量，再完成最终写回及关闭。

普通写回不等待其他读者退出；若有长时间读取导致写回暂未完成，日志仍保留。
到空间门限或收尾时如果仍无法完成，会明确报错并保留文件，不伪称已整理成功。
这些操作也可能等磁盘，单独计时不是让等待消失。没有新增后台数据库连接或降低同步级别。

`database_settings.json` 在**实际写入连接**上读取 SQLite 版本、绝对文件位置、
日志模式、同步级别、自动写回设置、缓存大小及保存线程编号，避免拿另一连接的默认值
误当成运行设置。

| 记录 | 含义 |
| --- | --- |
| `writer_timing.csv: queue_ms` | 本帧等保存线程处理的时间 |
| `pack_records_ms` | 保存线程内整理一批记录的时间，分析端的快照准备另计 |
| `statements_ms` | 执行写入、查询及编号/事件整理；不能当成纯磁盘耗时 |
| `commit_ms` / `commit_cpu_ms` | 一批提交的经过时间 / 本线程 CPU 时间；`auto` 仍包含自动写回 |
| `transaction_id` / `batch_frames` | 区分真正的提交次数；同批多行不能重复累加 |
| `observations` / `events` / `contour_bytes` | 每批观测、事件数量及未压缩轮廓字节数 |
| `wal_bytes_after_commit` | 日志文件当时的大小，不等于本批新增写入字节数 |
| `database_maintenance.csv` | 单独的写回时机、耗时、CPU 时间、日志大小、完成情况和错误 |
| `writer_report.json: finalize_ms / database_close_ms` | 收尾状态整理和核对 / 最终写回及关闭耗时 |

磁盘确认本身的耗时需用系统调用记录确认，不能简单用“经过时间减 CPU 时间”冒充。
本轮四组对照中，包含排队的保存耗时 P99 从 14.86 ms 降到 12.97 ms，但最大值
从 110.44 ms 增到 129.64 ms；一次写回造成了约 106 ms 排队。因此候选方案尚未
达到“长时间等待明显改善”的标准，默认仍为 `auto`，并保留新增的计时记录。
如需复测，在原回放命令后追加 `--save-checkpoint-policy deferred`；这不是降低
数据可靠性的开关，两种方式均保留 FULL 提交。
本轮记录见 [数据库保存检查与优化报告](../validation/database_save_20261030-140229/REPORT.md)。

## 相对暗度计算：复用工作区

`bubble_tracker.py` 的 `SegmentationWorkspace` 管理同一视频流反复使用的计算空间。
现有整段录像入口和 `OnlineProcessor` 都已接入，不需要修改运行命令。
计算仍为 `D = 1 - fb / (B + 1)`，随后减去 `D[::8, ::8]` 的中位数；
识别阈值、观察范围、轮廓规则、追踪及保存方式不变。

具体做法：

1. 开始时计算一次整张背景的 `B + 1`，以后直接使用。
2. 背景每帧原本就只更新一条横向区域。更新结束后，只重算这一条区域的缓存，
   其余行继续有效。背景的更新公式和速度没有改变。
3. 除法和两次减法写入同一块暗度工作区，避免每一步建立新的整幅临时数组。
4. 后面的区域标号仍调用原来的 `connectedComponentsWithStats`，只给它提供预先
   分配的标号输出空间。实测仅复用暗度数组会拖慢该步骤，因此需一起复用这块空间。

这里仍是对整幅图计算，没有跳过亮区、缩小范围或降低图像分辨率。
没有把除法改为乘倒数：候选测试发现两者有微小浮点差异，最终保留与原式一致的运算。

一个 1280×1024、float32 视频流，上述暗度和初步标号的三块固定工作区共约 **15 MiB**，
不会按已处理帧数增长。下节的区域筛选工作区另计。
`segment()` 默认返回的轮廓、标签和模糊图不引用这些暂用空间，下一帧不会改写已返回结果。
直接调用 `workspace.compute()` 得到的是暂用暗度数组；需要长期保留时应自行复制。

缓存必须与背景一起管理：正常使用 `OnlineBackground.update()` 会自动刷新对应行。
若自行原地修改背景，必须调用 `workspace.refresh_rows(start, stop)` 刷新修改过的行；
若换了参考背景、尺寸或数据类型，应创建新的工作区，不复用旧缓存。不要跨线程共享一个工作区。
普通 `segment(..., workspace=None)` 调用仍保留原来的无缓存计算方式，兼容已有直接调用。

候选、整帧前后对照及逐像素核查结果见
[相对暗度优化报告](../validation/contrast_optimization_20261029-232239/report/REPORT.md)。

## 区域筛选与编号图：复用内存

`OnlineProcessor` 现在自动复用区域筛选和最终编号图的空间，运行命令不变。
识别参数、像素面积筛选、轮廓顺序、追踪编号及事件规则均保持原样。

- OpenCV 第一次生成区域编号图时，本来就使用 `workspace.component_labels`。
  新增复用的是后面的候选掩膜，以及绘制轮廓后得到的最终编号图。
- 剔除小区域后，不再通过 `remap[labels]` 重新申请整张图，而是每次取 64 行，
  先保留这部分旧编号，再写回新的编号。索引转换也使用提前准备的小块内存。
- 对 1280×1024 输入，这些固定空间分别为 1.25、2.5、0.625 MiB，合计约 4.375 MiB。
  这是用固定空间减少反复申请，不代表整个进程的内存占用减少了同样大小。

**为何不会覆盖尚未用完的上一帧：** 分析线程依次完成分割、追踪、背景更新，
这三步返回后整张编号图已用完。追踪保留的是独立的像素坐标，保存线程接收的是
位置、事件和已经转成独立字节的轮廓；它们都不持有这张编号图。
下一次 `process()` 才会清空并重写它，因此这里不需要用固定的“双缓冲”猜测等待长度。

直接调用 `segment()` 的默认行为不变，返回的编号图可以保留到下一帧之后。
只有明确传入 `labels_out` 才允许写入调用方的数组；它要求同尺寸、可写、连续的
`uint16` 数组以及相应 `workspace`，调用方必须先让所有使用者用完上一帧。
一个 `OnlineProcessor` 或工作区仍只由一个分析线程使用，不能并行调用。
详细诊断中的旧字段 `selection_allocate` 保留兼容；启用复用时，它包含清空候选
掩膜的时间，不能再把该字段全部解释为新申请内存。

检查过程本身包含逐像素比较，不把它的整帧用时当作正常在线处理速度。

`host_stall_watch.ps1` 是 Windows 只读内存/磁盘计数脚本；本机从 WSL 网络路径
直接执行曾被 Windows 策略拒绝，不能把它描述为已验证的一键入口。本次宿主机
数据由 PowerShell 的直接只读查询采集，未修改执行策略。

本次对照与证据见 `../validation/native_stalls_20261030-112035/REPORT.md`。

进一步区分宿主机换页与虚拟磁盘等待时，可以使用
`windows_stall_capture.ps1` 和同目录的 `windows_stall_capture.wprp`。
它们需要 Windows 管理员确认；脚本按 `-Output` 创建全新结果目录，默认记录
180 秒，或在该目录出现 `stop.request` 时提前结束。它使用独立的 WPR 会话名，
只停止自己的记录，不调整驱动、系统服务、仪器或数据库参数。配置使用约 32 MiB
的记录缓冲区；文件大小仍会随事件数增长，应保留限时运行。

本机已验证的运行方式是：经用户授权后，将这两个诊断文件放在 Windows 本地临时
目录，以管理员 PowerShell 调用脚本；没有更改 PowerShell 执行策略。`recording.json`
表示采集已开始；`finished.json` 的 `stop_exit_code` 必须为 0，并且 WPR 状态已停止，
才能确认采集结束。`error.json` 或非零退出码必须保留并报告。

Windows 的 `vmmemWSL` 换页记录和 Linux 内部的缺页计数不是同一层：Linux 没有
磁盘缺页，也不能排除 Windows 正在从页文件取回虚拟机内存。对应两侧事件时，
本次使用请求/回复采样关联 Windows QPC 与 WSL 计时器，并保留往返时间和插值
误差；不能把两台运行环境的计时值直接相减，也不能把插值当作精确同步。
进一步的原始证据见 `../validation/stall_root_cause_20261030-115117/REPORT.md`。

## 实验前的内存检查

`memory_pressure_check.py` 用同一段原录像进行离线回放，同时记录 Windows
剩余内存、WSL 内存、后台 Pylance 占用、换页累计数和每帧转换耗时。
它复用现有送帧、识别和保存程序，不改变微泡阈值，也不操作相机或 PZT。

在 `customer_workspace/microbubble_tracking` 中运行，例如：

```bash
../../.venv/bin/python memory_pressure_check.py \
  --video data/raw/expB.mp4 \
  --reference results/A_offline/background.npy \
  --pzt data/pzt/expB \
  --repeats 3 --label background_on \
  --output-dir ../validation/memory_background_on_YYYYMMDD-HHMMSS
```

输出目录必须不存在。默认将约 22 秒的原录像连续回放三遍；这些重复只用于
运行负载检查，不是三次新实验。原帧号与回放轮次仍由现有程序记录。
默认使用分析 24 线程、解码 1 线程、转换 1 线程；比较组必须保持这些参数相同。

`memory_pressure_check.py` 现在也默认关闭逐帧详细诊断，不再隐式追加
`--measure-stages --diagnose-stalls`。它仍记录 Windows/WSL 的整体内存与回放结果。
要检查每一帧的转换停顿，应明确添加 `--diagnostics`；未开启时，内存汇总中的
`conversion_timing_recorded=false`，细分转换时间和超时次数留空，不能理解成零停顿。
明确开启却缺少诊断文件时，汇总程序仍会报错。

文件用途：

| 文件 | 能看出什么 |
| --- | --- |
| `windows_before.json` / `windows_after.json` | Windows 内存、主要应用占用、实际 `.wslconfig` 内容 |
| `windows_memory.jsonl` | Windows 可用内存、WSL 宿主进程驻留内存、全机换页累计计数 |
| `linux_memory.jsonl` | WSL 可用内存、交换区变化、Pylance 内存以及采样时间 |
| `replay/source_stalls.csv` | 每帧解码、转换与等待的实际耗时 |
| `run.json` / `host.log` / `replay.log` | 运行是否完成，监测或回放失败的具体原因 |

比较前后两组时，分别传入各次运行目录：

```bash
../../.venv/bin/python memory_pressure_report.py \
  ../validation/memory_background_on_YYYYMMDD-HHMMSS \
  ../validation/memory_background_off_YYYYMMDD-HHMMSS \
  --output ../validation/memory_comparison_YYYYMMDD-HHMMSS.json
```

**检查顺序：**

1. 先保持日常环境测量，至少记录两段相同回放。
2. 如发现 Pylance 占用明显，在 VS Code 的工作区设置中把
   `Python: Language Server` 临时设为 `None`，再确认其进程已经退出。
   这会暂停 Python 补全和类型提示；实验后可恢复原设置。不能仅暂停进程就
   声称释放内存，因为暂停仍会保留它的内存。不要关闭未保存的编辑器或浏览器。
3. 保持录像、算法、线程数、预热、内存复用和保存方式相同，再做相同次数的回放。
4. 只有测量表明 WSL 内存配置不合适，才讨论调整上限。修改上限后需要重启 WSL
   才生效，会影响当前终端和程序；本工具不会自动修改配置或重启。

`PagesInputPerSec` 在这里来自 **RawData**，是累计计数而非已经算好的每秒速率。
它包含所有 Windows 进程的文件读取引起的缺页，不能直接称为“WSL 读页文件次数”。
要确认后者，需配合上文的 WPR 记录，并在 `xperf -a hardfault -bytes` 结果中
筛选 `vmmemWSL` 和 `pagefile.sys`。`memory_pressure_report.pagefile_reads()`
可以完成这项筛选。累计读入同一内存页多次会重复计数。

不要将 Windows 与 WSL 的独立程序计时值直接相减。内存采样也不是逐帧精确同步；
仅有一秒左右的内存计数，不能解释某一帧几十毫秒中每一毫秒的去向。
没有 WPR 明细时必须明确写成“系统总体缺页”，不能用它替代页文件证据。

当前诊断记录：
[2026-10-30 内存对照](../validation/memory_pressure_20261030-123155/REPORT.md)。
原有分割工作区复用和预热诊断入口保留；不通过取消页文件、取消交换区或改变
数据库安全写入方式来获得更好看的耗时。

### 继续拆分识别与帧间交接

`paced_replay.py --diagnostics` 仅用于离线诊断；原来的
`--diagnose-stalls --diagnose-details` 组合继续兼容。
它在原有记录之外，把相对暗度拆为除法、减法、中位数、减去中位数，
把区域筛选拆为强暗区筛选和区域填充。规则与运算顺序不变。

新增的 `consumer_handoff.csv` 连续记录上一帧分析结束到下一次取图完成之间的
操作，包括诊断日志、线程列表扫描、状态记录、取图锁、图像复制和事件清除。
`wait_for_frame` 表示画面尚未到来时的正常空闲等待，不算计算变慢。
文件按小批次写入；自身落盘通常发生在下一帧处理开始前，计入该帧的
`injected_ms`（这个既有列名还包含准备开销，不只表示人为注入的等待）。
这些细计时默认关闭，不能把带诊断的运行速度直接当成正式运行速度。

可以核对交接时间是否逐段闭合，并导出汇总：

```bash
../../.venv/bin/python stall_detail_report.py <运行目录> \
  --output <新的汇总目录>
```

需要底层函数样本时，现有 `native_stall_watch.py` 可指定
`--perf-targets consumer --frequency 999`；这与默认仅观察源和保存线程不同。
采样记录必须与同一次运行的帧时间对应。它没有采到某个短函数，不代表该函数
没有执行；它也不能单独说明 Windows 是否把 WSL 的内存换到了硬盘。
